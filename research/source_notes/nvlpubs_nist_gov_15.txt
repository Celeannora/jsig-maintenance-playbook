| Information Security Continuous Monitoring (ISCM) definition | - “maintaining ongoing awareness of information security, vulnerabilities, and threats to support organizational risk management decisions” |
| ISCM process steps | - Define an ISCM strategy<br>- Establish an ISCM program<br>- Implement an ISCM program<br>- Analyze data and Report findings<br>- Respond to findings<br>- Review and Update the ISCM strategy and program |
| Chapter 3 process description | - Define an ISCM strategy based on risk tolerance that maintains clear visibility into assets, awareness of vulnerabilities, up-to-date threat information, and mission/business impacts<br>- Establish an ISCM program determining metrics, status monitoring frequencies, control assessment frequencies, and an ISCM technical architecture<br>- Implement an ISCM program and collect the security-related information required for metrics, assessments, and reporting; automate collection, analysis, and reporting where possible<br>- Analyze the data collected and Report findings, determining the appropriate response; additional information may be collected to clarify or supplement monitoring data<br>- Respond to findings with technical, management, and operational mitigating activities or acceptance, transference/sharing, or avoidance/rejection<br>- Review and Update the monitoring program, adjusting the ISCM strategy and maturing measurement capabilities to increase visibility into assets and awareness of vulnerabilities, further enable data-driven control of the security of an organization’s information infrastructure, and increase organizational resilience |
| Tiers | - Tier 1 = organization<br>- Tier 2 = mission/business processes<br>- Tier 3 = information systems |
| Tier 1 focus | - High-level information security governance policy as it relates to risk to the organization as a whole, its core missions, and its business functions<br>- Criteria for ISCM defined by the organization’s risk management strategy, including how the organization plans to assess, respond to, and monitor risk, and oversight required to ensure the strategy is effective |
| Tier 2 focus | - Criteria for continuous monitoring defined by how core mission/business processes are prioritized with respect to the organization’s overall goals and objectives, the types of information needed to execute mission/business processes, and the organization-wide information security program strategy<br>- Controls in the Program Management (PM) family are an example of Tier 2 security controls |
| Tier 3 focus | - Ensuring all system-level security controls (technical, operational, and management controls) are implemented correctly, operate as intended, produce the desired outcome, and continue to be effective over time<br>- Assessing and monitoring hybrid and common controls implemented at the system level<br>- Security status reporting may include security alerts, security incidents, and identified threat activities |
| Primary ISCM governance roles | - Head of Agency<br>- Risk Executive (Function)<br>- Chief Information Officer (CIO)<br>- Senior Information Security Officer (SISO)<br>- Authorizing Official (AO)<br>- Information System Owner (ISO)/Information Owner/Steward<br>- Common Control Provider<br>- Information System Security Officer (ISSO)<br>- Security Control Assessor |
| Head of Agency role | - Likely to participate in the organization’s ISCM program within the context of the risk executive (function) |
| Risk Executive (Function) role | - Oversees the organization’s ISCM strategy and program<br>- Reviews status reports from the ISCM process as input to information security risk posture and risk tolerance decisions<br>- Provides input to mission/business process and information systems tier entities on ISCM strategy and requirements<br>- Promotes collaboration and cooperation among organizational entities<br>- Facilitates sharing of security-related information<br>- Provides an organization-wide forum to consider all sources of risk<br>- Ensures that risk information is considered for continuous monitoring decisions |
| CIO role | - Leads the organization’s ISCM program<br>- Ensures that an effective ISCM program is established and implemented by establishing expectations and requirements<br>- Works closely with authorizing officials to provide funding, personnel, and other resources to support ISCM<br>- Maintains high-level communications and working group relationships among organizational entities |
| SISO role | - Establishes, implements, and maintains the organization’s ISCM program<br>- Develops organizational program guidance (policies/procedures) for continuous monitoring of the security program and information systems<br>- Develops configuration management guidance for the organization<br>- Consolidates and analyzes POA&Ms to determine organizational security weaknesses and deficiencies<br>- Acquires or develops and maintains automated tools to support ISCM and ongoing authorizations<br>- Provides training on the organization’s ISCM program and process<br>- Provides support to information owners/information system owners and common control providers on how to implement ISCM for their information systems |
| AO role | - Assumes responsibility for ensuring the organization’s ISCM program is applied with respect to a given information system<br>- Ensures the security posture of the information system is maintained<br>- Reviews security status reports and critical security documents<br>- Determines if the risk to the organization from operation of the information system remains acceptable<br>- Determines whether significant information system changes require reauthorization actions<br>- Reauthorizes the information system when required |
| ISO / Information Owner / Steward role | - Establishes processes and procedures in support of system-level implementation of the organization’s ISCM program<br>- Develops and documents an ISCM strategy for the information system<br>- Participates in the organization’s configuration management process<br>- Establishes and maintains an inventory of components associated with the information system<br>- Conducts security impact analyses on changes to the information system<br>- Conducts, or ensures conduct of, assessment of security controls according to the ISCM strategy<br>- Prepares and submits security status reports in accordance with organizational policy and procedures<br>- Conducts remediation activities as necessary to maintain system authorization<br>- Revises the system-level security control monitoring process as required<br>- Reviews ISCM reports from common control providers to verify common controls continue to provide adequate protection<br>- Updates critical security documents based on ISCM results |
| Common Control Provider role | - Establishes processes and procedures in support of ongoing monitoring of common controls<br>- Develops and documents an ISCM strategy for assigned common controls<br>- Participates in the organization’s configuration management process<br>- Establishes and maintains an inventory of components associated with the common controls<br>- Conducts security impact analyses on changes that affect the common controls<br>- Ensures security controls are assessed according to the ISCM strategy<br>- Prepares and submits security status reports in accordance with organizational policy/procedures<br>- Conducts remediation activities as necessary to maintain common control authorization<br>- Updates/revises the common security control monitoring process as required<br>- Updates critical security documents as changes occur<br>- Distributes critical security documents to individual information owners/information system owners, and other senior leaders in accordance with organizational policy/procedures |
| ISSO role | - Supports the organization’s ISCM program by assisting the ISO in completing ISCM responsibilities<br>- Participates in the configuration management process |
| Security Control Assessor role | - Provides input into the types of security-related information gathered as part of ISCM<br>- Assesses information system or program management security controls for the organization’s ISCM program<br>- Develops a security assessment plan for each security control<br>- Submits the security assessment plan for approval prior to conducting assessments<br>- Conducts assessments of security controls as defined in the security assessment plan<br>- Updates the security assessment report as changes occur during ISCM<br>- Updates/revises the security assessment plan as needed |
| Other roles mentioned | - Information system administrator<br>- ISCM program manager |
| Organization-wide ISCM strategy policies/procedures/templates | - Policy that defines key metrics<br>- Policy for modifications to and maintenance of the monitoring strategy<br>- Policy and procedures for the assessment of security control effectiveness (common, hybrid, and system-level controls)<br>- Policy and procedures for security status monitoring<br>- Policy and procedures for security status reporting (on control effectiveness and status monitoring)<br>- Policy and procedures for assessing risks and gaining threat information and insights<br>- Policy and procedures for configuration management and security impact analysis<br>- Policy and procedures for implementation and use of organization-wide tools<br>- Policy and procedures for establishment of monitoring frequencies<br>- Policy and procedures for determining sample sizes and populations and for managing object sampling<br>- Procedures for determining security metrics and data sources<br>- Templates for assessing risks<br>- Templates for security status reporting (on control effectiveness and status monitoring) |
| Training requirements tied to ISCM roles | - Policies, procedures, and templates address manual and automated monitoring methodologies<br>- Organizations establish policy and procedures for training of personnel with ISCM roles<br>- Training may include management and use of automated tools, establishing baselines, tuning measurements, recognition of and appropriate response to triggers and alerts from metrics indicating risks beyond acceptable limits, and internal or external reporting requirements |
| Expected inputs / outputs: Tier 1 & 2 strategy development | **Expected Input:** Organizational risk assessment and current risk tolerance; current threat information; organizational expectations and priorities; available tools from OMB lines of business and/or third-party vendors<br>**Expected Output:** Updated information on organizational risk tolerance; organization-wide ISCM strategy and associated policy, procedures, templates, tools |
| Expected inputs / outputs: Tier 3 strategy development | **Expected Input:** Organizational risk tolerance information; organizational ISCM strategy, policy, procedures, templates; system-specific threat information; system information (e.g., System Security Plan, Security Assessment Report, Plan of Action and Milestones, Security Assessment Plan, System Risk Assessment, etc.)<br>**Expected Output:** System-level ISCM strategy that complements the Tier 1 and 2 strategies and the organizational security program and that provides security status information for all tiers and real-time updates for ongoing system authorization decisions as directed by the organizational ISCM strategy |
| Required or cited artifacts / evidence | - System Security Plan<br>- Risk Assessment Report<br>- Security Assessment Report<br>- Plan of Action and Milestones (POA&M)<br>- Hardware and software inventories<br>- Security Assessment Plan<br>- Security status reports<br>- Critical security documents<br>- Security-related information from assessments and monitoring<br>- Evidence needed for ongoing authorization decisions |
| Ongoing authorization artifacts | - System Security Plan together with Risk Assessment Report, Security Assessment Report, and POA&M are kept up to date on an ongoing basis |
| POA&M use | - POA&M resource and prioritization decisions<br>- Consolidated POA&M information used to determine common weaknesses/deficiencies among information systems<br>- Aggregate POA&M information used to allocate risk mitigation resources organization-wide and to make adjustments to the monitoring strategy<br>- Risk response implementation plans documented in the system’s POA&M<br>- Weaknesses found are evaluated and mitigation actions are conducted immediately or are added to the POA&M |
| Analysis/reporting procedures | - Organizations develop procedures for analyzing and reporting assessment and monitoring results<br>- Procedures include specific staff/roles to receive ISCM reports, content and format of the reports, frequency of reports, and any tools to be used<br>- Includes requirements for analyzing and reporting results of controls that are not easily automated<br>- May require additional data to supplement or clarify security-related information under analysis or provided in initial reports |
| Analyze data (3.4.1) | - Security-related information resulting from ISCM is analyzed in the context of stated risk tolerances, potential impact of vulnerabilities on information systems, mission/business processes, and organization as a whole, and potential impact of mitigation options<br>- Evolving vulnerability and threat data is always considered during analysis<br>- Organizational officials review analyzed reports to determine whether to conduct mitigation activities or to transfer, avoid/reject, or accept risk<br>- Authorizing officials may determine accepting some specific risk is preferable to implementing a mitigating response<br>- Rationale for determinations may include organizational risk tolerance, negative impact to mission/business processes, or cost-effectiveness/return on investment<br>- Resolution of risk and the rationale for the decision is recorded in accordance with organizational policies and procedures |
| Analyze data expected outputs | - Analysis of security status information for all tiers<br>- Updated System Security Plan, Security Assessment Report, and Plan of Action and Milestones<br>- Revised organizational risk management decisions |
| Report on security control assessments (3.4.2) | - Organizations report on assessments of all implemented security controls for effectiveness in accordance with organizational requirements<br>- Security-related information from assessments may be conveyed in templates or spreadsheets or collected and reported in an automated fashion<br>- At the system level, security-related information from assessments directly supports ongoing authorization decisions and plans of action and milestones creation and tracking<br>- Some security controls or elements of security controls are security metrics (e.g., SI-4 Information System Monitoring), so assessing them results in monitoring the related metric |
| Report on security control assessments frequencies/examples | - Risk executive (function) may receive a general report on all systems annually and a detailed report on specific high-impact systems quarterly<br>- CIO and SISO may receive more granular technical data on all systems quarterly<br>- AO may receive monthly comprehensive reports on the systems for which s/he is responsible<br>- CIRT lead may receive exception reports when alerts are generated<br>- Network administrators may review dashboards showing network activity updated every minute, with summary metrics updated hourly or daily |
| Report on security status monitoring (3.4.3) | - Organizations develop procedures for reporting on security status monitoring<br>- Security status data is derived from monitoring predefined metrics across the organization using output generated by organization-wide tools (often implemented as common controls)<br>- Organization-wide tools may be part of a specific system or systems, but the security-related information generated may not be system-specific |
| Reporting requirements recorded in ISCM strategy | - Specific staff/roles to receive ISCM reports<br>- Content and format of the reports<br>- Frequency of reports<br>- Any tools to be used |
| Respond to findings | - Response to findings at all tiers may include risk mitigation, risk acceptance, risk avoidance/rejection, or risk sharing/transfer, in accordance with organizational risk tolerance<br>- Responses are coordinated with appropriate security management activities such as the security-focused configuration management program |
| Tier 1 response | - May result in changes to security policies around organizational governance<br>- May be constrained by mission/business needs and the limitations of the enterprise architecture (including the human components), immutable governance policies, or other external drivers |
| Tier 2 response | - May include requests for additional security-related information, new or modified metrics, changes in mission/business processes, or Tier 3 reporting requirements, and/or additions or modifications to common control implementations<br>- May be constrained by organizational governance policies and strategies as well as mission/business goals and objectives and limitations of organizational resources and infrastructure |
| Tier 3 response | - May include implementation of additional controls, modifications to previously implemented controls, removal of systems’ authorization to operate, changes to the frequency of monitoring, and/or additional or more detailed analysis of security-related information<br>- System-level mitigations are made within constraints set by Tier 1 and 2 policies, requirements, and strategies |
| Response documentation | - Response strategies may be implemented over a period of time, documenting implementation plans in the system’s Plan of Action and Milestones<br>- As weaknesses are found, response actions are evaluated and any mitigation actions are conducted immediately or are added to the POA&M<br>- Other key system documents are updated accordingly<br>- Security controls modified, enhanced, or added as part of response are assessed to ensure new or revised controls are effective in their implementations<br>- Going forward, new or revised controls are included in the overall continuous monitoring strategy |
| Review/update monitoring program and strategy | - ISCM strategies and programs are not static<br>- Security control assessments, security status metrics, and monitoring and assessment frequencies change in accordance with organizational needs<br>- Continuous monitoring strategy is reviewed to ensure it supports operating within acceptable risk tolerance levels, metrics remain relevant, and data is current and complete<br>- The organization establishes a procedure for reviewing and modifying all aspects of the ISCM strategy, including relevance of the overall strategy, accuracy in reflecting organizational risk tolerance, accuracy/correctness of measurements, and applicability of metrics, reporting requirements, and monitoring and assessment frequencies |
| Factors precipitating monitoring strategy changes | - Changes to core missions or business processes<br>- Significant changes in the enterprise architecture (including addition or removal of systems)<br>- Changes in organizational risk tolerance<br>- Changes in threat information<br>- Changes in vulnerability information<br>- Changes within information systems (including changes in categorization/impact level)<br>- Increase/decrease in POA&Ms related to specific controls<br>- Trend analyses of status reporting output<br>- New federal laws or regulations<br>- Changes to reporting requirements |
| Review/update outputs | - Revised ISCM strategy<br>- Or a brief documented report noting review details and that modifications to the strategy were not necessary (in accordance with the established review process) |
| ISCM strategy review criteria | - Relevance of the overall strategy<br>- Accuracy in reflecting organizational risk tolerance<br>- Accuracy/correctness of measurements<br>- Applicability of metrics<br>- Reporting requirements<br>- Monitoring and assessment frequencies |
| Monitoring and assessment frequency criteria | - Security control volatility<br>- System categorizations/impact levels<br>- Security controls or specific assessment objects providing critical functions<br>- Security controls with identified weaknesses<br>- Organizational risk tolerance<br>- Threat information<br>- Vulnerability information<br>- Risk assessment results<br>- Output of monitoring strategy reviews<br>- Reporting requirements |
| Security control volatility examples | - CM-6 Configuration Settings and CM-8 Information System Component Inventory may require more frequent assessment and monitoring<br>- PS-2 Position Categorization and PS-3 Personnel Screening typically require less frequent assessment |
| Critical function examples | - Log management server<br>- Firewalls |
| Weaknesses and POA&M monitoring | - Existing risks documented in SARs are considered for more frequent monitoring to ensure risks stay within tolerance<br>- Controls documented in the POA&M as having weaknesses are monitored more frequently until remediation of the weakness is complete<br>- Minor or low-impact weaknesses are monitored less frequently than higher-impact weaknesses |
| Organizational risk tolerance examples | - Low tolerance organizations include those processing, storing, or transmitting large amounts of proprietary and/or personally identifiable information (PII), organizations with numerous high-impact systems, organizations facing specific persistent threats |
| Threat information examples | - Known exploits and attack patterns<br>- Temporary or permanent increases to monitoring frequencies may be used if a specific attack exploits a vulnerability of an implemented technology |
| Vulnerability information example | - If a specific product manufacturer provides software patches monthly, an organization might consider vulnerability scans on that product at least that often |
| Reporting requirements example | - If OMB policy requires quarterly reports on the number of unauthorized components detected and corrective actions taken, the organization would monitor the system for unauthorized components at least quarterly |
| AC-2 example | - AC-2, Account Management, has ten separate requirements (a. through j.) within the base control and four control enhancements [(1) through (4)]<br>- AC-2a (identification of account types) is a candidate for relatively infrequent assessment<br>- AC-2h (deactivation of temporary accounts and accounts of terminated or transferred users) would most likely be assessed more frequently than AC-2a<br>- AC-2 (3) automatically disables accounts after a specified time period of inactivity and is a candidate for relatively frequent monitoring |
| Sampling guidance | - Organizations may find collecting data from every object of every system impractical or cost-prohibitive<br>- Sampling may make ISCM more cost-effective<br>- Risk: sample population may fail to capture variations in assessment outcomes that would be obtained from full population assessment<br>- NIST SP 800-53A describes how to achieve satisfactory coverage for examine, interview, and test<br>- Coverage criteria: types of objects; number of each type; specific objects per type assessed |
| Sampling considerations | - Desired information<br>- Cost and practicality of making the assessment<br>- Information already known about the objects, organization, or operating environments<br>- Anticipated variability across the total population<br>- Desired confidence in resulting statistics and conclusions drawn about the total population |
| Sampling roles | - Primary Roles: Information System Owner, Common Control Provider, Information System Security Officer, Security Control Assessor<br>- Supporting Roles: Risk Executive (Function), Authorizing Official, Chief Information Officer, Senior Information Security Officer |
| Sampling expected input/output | - Expected Input: Organizational- and system-level policy and procedures on ISCM strategy, metrics, and the Security Assessment Plan updated with assessment and monitoring frequencies<br>- Expected Output: Security Assessment Plan documentation on acceptable sample sizes, security-related information |
| ISCM architecture requirements | - Data collection<br>- Data storage<br>- Data analysis capabilities<br>- Retrieval and presentation (reporting) capabilities |
| ISCM architecture characteristics | - Methodologies standardized to facilitate efficiencies, intra- and inter-tier information exchange, correlation, and other analysis<br>- Policies and procedures designed to minimize data calls and maximize data reuse<br>- Data feeds come from a heterogeneous mix of sources (e.g., authorization packages, training records, system logs) and accommodate different stakeholder views<br>- Interoperable data specifications (e.g., SCAP, XML) enable data to be collected once and reused many times |
| Implementation stage data sources | - People<br>- Processes<br>- Technologies<br>- The computing environment<br>- Existing relevant security control assessment reports |
| Implementation stage output | - Security-related information |
| Analysis/reporting deliverable formats | - Recurring reports<br>- Automated reports<br>- Ad hoc reports<br>- Data feeds<br>- Database views |
| Event-driven assessments | - Events may trigger the immediate need to assess security controls or verify security status outside of requirements expressed in the ISCM strategy<br>- May require an unplanned assessment of the type defined in the ISCM strategy or a customized assessment tailored to address an emerging need (e.g., a change in planned assessment or monitoring frequency)<br>- Criteria consider incidents, new threat information, significant changes to systems and operating environments, new or additional mission responsibilities, and results of a security impact analysis (SIA) or assessment of risk<br>- Depending on significance, an event-driven assessment may trigger one or more system reauthorizations |
| Event-driven assessment output | - Documented criteria and thresholds for event-driven assessments/authorizations (e.g., significant change procedures, policy and procedures on event-driven authorizations) |
| ISCM roles and responsibilities in process | - Tier 1 and Tier 2 officials provide input to development of the organizational ISCM strategy, including establishment of metrics, policy, procedures, compiling and correlating Tier 3 data into security-related information usable at Tiers 1 and 2, policies on assessment and monitoring frequencies, and provisions for ensuring sufficient depth and coverage when sampling methodologies are utilized<br>- Review monitoring results to determine security status in accordance with organizational policy and definitions<br>- Analyze potential security impact to organization and mission/business process functions resulting from changes to information systems and their environments of operation, along with security impact to the enterprise architecture resulting from addition or removal of information systems<br>- Determine whether current risk is within organizational risk tolerance levels<br>- Take steps to respond to risk as needed (e.g., request new or revised metrics, additional or revised assessments, modifications to existing common or PM security controls, or additional controls)<br>- Update relevant security documentation<br>- Review new or modified legislation, directives, policies, etc., for changes to security requirements<br>- Review monitoring results to determine if organizational plans and policies should be adjusted or updated<br>- Review monitoring results to identify new information on vulnerabilities<br>- Review new or emerging threats as evidenced by threat activities present in monitoring results, threat modeling (asset- and attack-based), classified and unclassified threat briefs, US-CERT reports, and other information available through trusted sources, interagency sharing, and external government sources |
| Tier 3 responsibilities in process | - Provide input to development and implementation of the organization-wide ISCM strategy along with development and implementation of the system level ISCM strategy<br>- Support planning and implementation of security controls, deployment of automation tools, and how those tools interface with one another in support of the ISCM strategy<br>- Determine security impact of changes to the information system and its environment of operation, including commissioning or decommissioning the system<br>- Assess ongoing security control effectiveness<br>- Take steps to respond to risk as needed (e.g., request additional or revised assessments, modify existing security controls, implement additional security controls, accept risk, etc.) based on results of ongoing monitoring activities, assessment of risk, and outstanding items in the plan of action and milestones<br>- Provide ongoing input to the security plan, security assessment report, and plan of action and milestones based on results of the ISCM process<br>- Report the security status of the information system including the data needed to inform Tiers 1 and 2 metrics<br>- Review the reported security status of the information system to determine whether the risk to the system and the organization remains within organizational risk tolerances |
| Roles and outputs for tier activities | - Tiers 1 and 2 output: Updated information on organizational risk tolerance; organization-wide ISCM strategy and associated policy, procedures, templates, tools<br>- Tier 3 output: System-level ISCM strategy that complements the Tier 1 and 2 strategies and the organizational security program and that provides security status information for all tiers and real-time updates for ongoing system authorization decisions as directed by the organizational ISCM strategy |
| Policies/procedures/templates developed at higher tiers | - Lower tiers fill in gaps related to their tier-specific processes<br>- Decisions and activities by Tier 1 and 2 officials may be constrained by mission/business needs, limitations of the infrastructure (including human components), immutable governance policies, and external drivers |

| SCAP purpose | - Standardizes the format and nomenclature by which security software products communicate security flaw and security configuration information<br>- Supports automated vulnerability and patch checking<br>- Supports security control compliance activities<br>- Supports security measurement<br>- Used for maintaining security by automatically verifying installation of patches, checking system security configuration settings, and examining systems for signs of compromise |
| SCAP product validation | - Validates two types of vulnerability and patch scanners: authenticated and unauthenticated |
| Authenticated scanner capability | - Scan a target system using target system logon privileges<br>- Locate and identify the presence of known vulnerabilities<br>- Evaluate software patch status to determine ongoing security status based on an organization’s defined patch policy |
| Unauthenticated scanner capability | - Determine presence of known vulnerabilities by evaluating the target system over the network without authenticated access |
| SCAP-validated scanner capability | - Scan connected systems at regular intervals<br>- Provide quantitative and repeatable measurement and scoring of software flaws across systems<br>- Enable interoperability among vulnerability scanners and reporting tools to provide consistent detection and reporting of flaws and supports comprehensive remediation capabilities |
| FDCC / USGCB examples | - Federal Desktop Core Configuration (FDCC)<br>- United States Government Configuration Baseline (USGCB) profiles |
| SCAP-expressed checklist capabilities | - Can be customized as appropriate to meet specific organizational requirements<br>- Can map individual system security configuration settings to corresponding security requirements<br>- Embedded mappings allow SCAP-validated tools to generate assessment and compliance evidence automatically |
| OCIL | - Framework for expressing a set of questions to be presented to a user and corresponding procedures to interpret responses<br>- Can be used in conjunction with XCCDF to help handle cases where OVAL is unable to automate a particular check<br>- Defines questions, possible answers, actions to be taken resulting from a user’s answer, and enumerate the result set<br>- Answers can be returned in a standardized format, allowing statistical analysis and other calculations to be performed in an automated manner |
| NVD | - U.S. government repository of standards-based vulnerability management data represented using SCAP specifications<br>- Includes security checklists, security-related software flaws, misconfigurations, product names, and impact metrics<br>- Content is dynamic; vulnerabilities updated with patch content, checklists updated, and new checklists added<br>- XML data feeds available and updated at two-hour intervals |
| NCP | - U.S. government repository of publicly available security checklists<br>- Provides checklists both in prose format and in SCAP-expressed format<br>- A subset of checklists also provides embedded CCEs mapped to NIST SP 800-53 security controls |
