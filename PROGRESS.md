## Change log

- 2026-08-06 — Fixed a report-generation gap plus a DCN-modeling error in the ISV toolchain, reported after a live-host run still didn't produce an HTML file. Three changes: (1) **`Invoke-ISVCollection.ps1` now auto-chains into `New-ISVReport.ps1`** at the end of a successful run (opt out with the new `-SkipReport` switch) — this removes the entire "forgot to run the second command" failure mode structurally, regardless of whether that was the original cause (the original root cause on the user's specific host was never directly reproduced/confirmed, since only a non-Windows sandbox was available for testing; this fix eliminates the failure class either way). (2) **DCN is now modeled as per-drive, not system-wide** — `IsvDefinitions.ps1`'s old single `DCN` identification field is replaced by a `$Script:DriveFields` schema (Index/Make/Model/Capacity/Serial/Dcn) and a new `Get-DiskInventory` function (`Win32_DiskDrive` in live mode, two canned drives in `-SampleMode`); `-Dcn` is now `[string[]]`, mapped positionally to detected drives, and the rendered report gained a new "Hard Drives (Drive Control Numbers -- DCN)" table between System Identification and Summary. (3) **Manual prompting moved to after the automated run** (drive detection + all 41 checks first, then the 6 remaining identification fields, then one DCN prompt per detected drive last) specifically so the drive count is known before deciding how many DCN prompts to ask; a host with zero detected drives (e.g. CIM unavailable) falls back to one generic DCN prompt and a single synthetic drive row. Caught two real bugs during this pass's own verification, both fixed before shipping: (a) `Format-DrivesTable` used `$value -eq ''` to detect missing fields, but PowerShell's `-eq` coerces `''` to the left operand's type, so integer `0` (a perfectly valid drive Index) compared equal to `''` and got wrongly replaced with an "N/A" placeholder — fixed by only doing the empty-string check when the value is already a `[string]`; (b) `Get-DiskInventory`'s `return @()` (zero-drive case) and effectively any single-element return collapse to `$null`/a bare scalar at the call site due to PowerShell's pipeline output-unrolling, which would have thrown `The property 'Count' cannot be found` under `Set-StrictMode` — fixed by wrapping the call site as `$disks = @(Get-DiskInventory)`. Re-validated: PowerShell parser check on all three edited files; a `-SampleMode` run confirming the 2-canned-drive table renders correctly (items-array digest unchanged at `c37efa0af75bde7330703b556febc6e0b472548c313cbf8e0df8faf72cd58237`, confirming zero drift in the 41 checklist items despite the meta/schema restructuring); an interactive live-mode run on a 0-detected-drive host confirming the single generic-DCN fallback path; a mocked 3-physical-drive Windows scenario (fake `Get-CimInstance`) confirming three distinct per-drive DCN prompts fire in the correct order and populate the correct rows; a mixed test confirming the `-Dcn` array parameter pre-fills specific drives by position while still prompting only for the remainder; and a Playwright/Chromium visual QA pass on both the sample and mocked 3-drive reports confirming the new Hard Drives table renders with correct column widths and no overflow.
- 2026-08-06 — Fixed two issues in `Invoke-ISVCollection.ps1` found during a real live-host test run: (1) the 7 site-specific identification fields (Inspector, Area/Location, Program, Asset Tag, SCAP Score, DCN, Prior Win10 Upgrade) are now prompted for interactively via `Read-Host` whenever not supplied as a parameter, instead of silently defaulting to `SAMPLE placeholder` text in a live run — parameters still work and are preferred over the prompt when supplied, so unattended/scripted use is unaffected; (2) native command invocations (`reg query`, `icacls`) now redirect STDERR into the captured evidence (`2>&1` at the per-item invocation point) instead of letting it print directly to the console — on Windows, a missing registry key or path previously wrote messages like `ERROR: The system was unable to find the specified registry key or value.` straight to the terminal (bypassing the try/catch, since native-EXE stderr does not respect `$ErrorActionPreference` the way cmdlet errors do), which looked like a crash even though the run completed and the item was already correctly scored; that text now lands cleanly in the item's own evidence field. Root cause confirmed by reproducing the exact stderr-passthrough behavior with an equivalent native command locally before and after the fix. Also clarified in the README that the collector and renderer are two separate steps — a user who only ran `Invoke-ISVCollection.ps1` and didn't see an HTML file had not yet run `New-ISVReport.ps1`, which was the actual cause of "it did not generate a report" (the collector itself ran to completion and wrote `evidence.json` correctly). Re-validated: PowerShell parser check, an interactive run with piped answers confirming clean STDERR and correct evidence capture, sample-mode regeneration confirming the digest is unchanged (`c37efa0af75bde7330703b556febc6e0b472548c313cbf8e0df8faf72cd58237`) so this is a pure bug fix with no behavioral drift in sample output, and a visual re-check of the rendered HTML report.
- 2026-08-06 — Added the Initial System Validation (ISV) audit toolchain at `execution-plan/initial-system-validation/`: a PowerShell-only collector (`Invoke-ISVCollection.ps1`) that executes all 41 checklist items against a live Windows 11 endpoint (or `-SampleMode` for a placeholder dry run) and writes a SHA-256 tamper-evidence-digested `evidence.json`, plus a PowerShell renderer (`New-ISVReport.ps1`) that turns that evidence into the main HTML report and the two vendor BIOS reference guides (Dell/HP). This replaces an earlier Python-based version of the same tooling that was drafted locally but never committed to this repo; the deliverable is PowerShell end-to-end per explicit instruction, not Python. Shared item/BIOS-reference definitions live in `IsvDefinitions.ps1`, dot-sourced by both scripts. Digest is computed over the evidence items array only (never the meta block) using a hand-rolled canonical-JSON serializer matching Python's `json.dumps(sort_keys=True, separators=(",",":"))` behavior, so the format is independently re-verifiable by any tool that can canonicalize JSON the same way. Smoke-tested: sample-mode and live-mode (on a non-Windows host, confirming every check safely degrades to `N/A` with captured error text rather than crashing) collection runs, full HTML rendering of all three deliverables, and a deliberate tamper test confirming the digest-mismatch warning banner fires correctly. The original Python prototype remains, untouched and outside git, in the separate local `initial-system-validation/` project directory used for early drafting; it is not part of this repo.
