### Recurring security / compliance task execution
- **SecCM phases**
  - **Planning**
  - **Identifying and Implementing Configurations**
  - **Controlling Configuration Changes**
  - **Monitoring**
- **Planning phase activities**
  - Develop policy and procedures
  - Disseminate policy throughout the organization
  - Establish a Configuration Control Board (CCB)
  - Create a component inventory
  - Identify configuration items
  - Develop baseline configuration
  - Develop configuration change control process
  - Develop monitoring and reporting process
  - Develop SecCM monitoring strategy
  - Define changes that do not require configuration change control
  - Develop SecCM training
  - Identify approved IT products
  - Identify tools
  - Establish configuration test environment and program
- **System-level planning phase outputs**
  - Completed SecCM Plan
  - Established Configuration Control Board
  - Accurate system component inventory
  - Defined configuration items for the system
- **Identifying and Implementing Configurations**
  - Establish secure configurations
  - Prioritize configurations
  - Test configurations
  - Resolve issues and document deviations
  - Record and approve the baseline configuration
  - Deploy the baseline configuration
- **Controlling Configuration Changes**
  - Implement access restrictions for change
  - Implement configuration change control process
  - Conduct security impact analysis
  - Record and archive
- **Monitoring**
  - Assessment and reporting
  - Implement and manage tools for SecCM monitoring
- **SCAP use**
  - Automate configuration management
  - Produce assessment evidence
  - Automatically verify installation of patches
  - Check system security configuration settings against an expected baseline
  - Examine systems for signs of compromise

### Roles and responsibilities
| Role | Responsibilities explicitly stated |
|---|---|
| **Chief Information Officer (CIO)** | Designates and/or provides a SecCM Program Manager for the organization; approves the organizational SecCM plan and policies. |
| **Senior Agency Information Security Officer (SAISO)** | May act as the SecCM Program Manager for the organization; may provide staff with security expertise to serve on the CCB and/or conduct security impact analyses. |
| **Authorizing Official (AO)** | Manages or participates in the CCB for systems s/he authorizes; may provide technical staff to conduct and/or review security impact analyses; coordinates with the Risk Executive (Function) on SecCM issues; makes final determination whether a given change or set of changes continues to be an acceptable security risk. |
| **System Owner** | Identifies, defines, and ensures implementation of the aspects of SecCM for the information system not defined by the organization; ensures implementation of organizational-level SecCM requirements for the system. |
| **SecCM Program Manager** | Develops SecCM policies and procedures; provides direction; oversees implementation of the SecCM program for the organization and/or system level; facilitates communications; considers dashboard/web site/email/newsletter communications; provides knowledge and direction in policies, procedures, communications, training, defined roles and responsibilities, support, oversight of program activities, and coordination with stakeholders. |
| **System Security Officer (SSO)** | Assists the system owner with implementation of SecCM for the system; conducts configuration monitoring activities (reporting and analysis); may serve on the CCB. |
| **System Administrator (SA)** | Implements agreed-upon secure baseline configurations; incorporates secure configuration settings for IT products; assists with security impact analyses and configuration monitoring activities as needed; may be included in determining baseline configuration for each CI; may serve on the CCB; responsible for complying with SecCM policies and implementing/following SecCM procedures. |
| **System/Software Developer** | Ensures secure configuration settings are built into applications in accordance with security requirements; assists with security impact analyses and configuration monitoring activities as needed; may be included in determining baseline configuration for relevant CIs; may serve on the CCB; responsible for complying with SecCM policies and implementing/following SecCM procedures. |
| **System User (SU)** | Initiates change requests; assists with functional testing; complies with SecCM requirements. |
| **Configuration Control Board (CCB)** | Review and approve changes to an information system; acts as a check and balance on configuration change activity; ensures changes are held to organizationally defined criteria before implementation; gatekeeper for changes introduced into a system. |

### CCB / escalation / exception handling / decisioning
- **CCB**
  - Typically consists of **two or more individuals**
  - Represents various perspectives from within the organization
  - May be less formal for systems with limited size, scope, and criticality
  - Organization determines size and formality appropriate for a given system or systems
  - Establishment is part of the Planning phase
  - Supports **CM-3 Configuration Change Control**
- **CCB charter**
  - May define:
    - Membership
    - Roles and responsibilities of members
    - Reporting relationship to oversight body like an **Executive Steering Committee** or the **Risk Executive (Function)**
    - How the CCB operates
    - How to handle changes
    - Range of dispositions: **approved, not approved, on hold, etc.**
    - Evaluation criteria
    - Quorum required to make configuration change control-related decisions
- **CCB size/formality**
  - Low-impact and/or small, uncomplicated systems: CCB may be composed of as few as **two members** (typically the system owner and the SSO)
  - High-impact systems and complex moderate-impact systems: CCB may be composed of at least **three individuals**, at least one of whom is a system owner or SSO
- **Decision escalation / risk acceptance**
  - AO coordinates with the Risk Executive (Function) on SecCM issues
  - AO makes final determination whether a given change or set of changes continues to be an acceptable security risk
  - If change is significant enough that system authorization is in question, meet with AO and System Owner to determine if re-authorization is necessary; **CCB or RE(F) may also be involved**
- **Exception / unscheduled / unauthorized changes**
  - Some changes may be **preapproved** or **exempt from configuration control**
  - If exempt or pre-approved, note this on the change request and allow the change to be made without further analysis or approval
  - System documentation may still require updating
  - Unscheduled changes are still managed and controlled
  - Instructions for handling unscheduled changes and unauthorized changes discovered later are included in configuration change control procedures
  - Unscheduled changes are reviewed/resolved by the CCB as soon as is practical after they are made
  - Requirements for retroactive analysis, testing, and approval of changes implemented outside of the change control process are included in procedures
- **Approval / escalation criteria**
  - Criteria for changes that are preapproved or exempt from configuration control
  - Criteria to determine whether a change is significant enough to trigger consideration of system reauthorization activities
  - Criteria for elevating a change request from system level approval to organizational approval
  - Requirements for rollback of changes
  - Requirements for management of unscheduled changes tailored to support expedited reviews and approvals

### Cadence / frequencies / schedules
- **SecCM monitoring strategy**
  - Includes a **schedule** for SecCM monitoring and associated reporting
  - Includes **scheduled and ad hoc assessments**
  - Monitoring schedule may coincide with scheduled releases such that assessments are performed **before and after deployments**
  - Schedule includes provisions for reviewing and revising the SecCM monitoring strategy
- **CCB charter sample**
  - State the **frequency of regularly scheduled CCB meetings**
  - State the conditions that trigger a **special meeting**
- **SecCM policy**
  - Policies are **periodically reviewed and updated**
- **Monitoring strategy**
  - Strategy and procedures are **reviewed and revised** to ensure organizational security requirements continue to be met
- **Tools**
  - If automated tools are used for component inventory, procedures may describe **how often they will run**
- **Tests**
  - Configuration test environment used for testing IT products, tools, and proposed changes prior to rollout
  - Virtual environments are recommended for testing secure configurations
  - Monitoring can coincide with release cycles

  - Security Assessment Reports
  - Security Status Reports
  - Risk Assessments
  - Plans of Action & Milestones
  - Technical designs

  - Audit records
  - Inventory reports
  - Monitoring reports
  - Security assessment reports
  - Output from automated tools
  - Media library records
  - Archived baseline configurations
- **Security impact analysis / monitoring evidence**
  - Evidence can be produced automatically by SCAP-enabled tools
  - SCAP-expressed checklists can automatically generate standardized assessment and compliance evidence
  - Monitoring reports can support metrics and continuous monitoring requirements
  - Results of monitoring are reported to management
  - Archived baseline configurations are useful for incident response and traceability support during formal audits
- **Configuration change control evidence**
  - Record the change request
  - Document security impact analysis findings
  - Document testing results
  - Document implemented changes to baseline
  - Retain several iterations of baselines for audit, incident response, and historical purposes
- **Configuration monitoring evidence**
  - Systems inconsistent with baseline configuration
  - Unapproved components
  - Disparities between approved baseline and actual configuration
  - Querying audit records/log monitoring to identify unauthorized change events
  - Reviewing configuration change control records including security impact analyses
  - Reports used as input to RMF continuous monitoring
- **Media library**
  - Stores, protects, and controls all authorized versions of media CIs
  - May include commercially licensed software, custom-developed software, and other artifacts and documents generated throughout the SDLC

### Security / compliance task execution specifics
- **Secure configuration establishment may include**
  - Secure values for OS and application features
  - Services and ports
  - Network protocols and network interfaces
  - Methods of remote access
  - Access controls
  - Management of identifiers/accounts
  - Authentication controls
  - Audit settings
  - System settings
  - Cryptography using [FIPS 140-3]-validated cryptographic protocols and algorithms
  - Vendor-released patches in response to vulnerabilities
  - Approved, signed software, if supported
  - Safeguards through software for endpoint machines
  - Network protections
  - Physical/logical location of component
  - Maintaining technical specification and design documentation, system security documentation, system procedures
- **Configuration change control steps**
  - Request the change
  - Record the request for the proposed change
  - Determine if the proposed change requires configuration control
  - Analyze the proposed change for its security impact on the system
  - Test the proposed change for security and functional impacts
  - Approve the change
  - Implement the approved change
  - Verify that the change was implemented correctly
  - Close out the change request
- **Security impact analysis steps**
  - Understand the change
  - Identify vulnerabilities
  - Assess risks
  - Assess impact on existing security controls
  - Plan safeguards and countermeasures
- **Monitoring activities**
  - Scanning to discover components not recorded in the inventory
  - Scanning to identify disparities between the approved baseline configuration and the actual configuration for a system
  - Implementation of automated change monitoring tools
  - Querying audit records/log monitoring to identify unauthorized change events
  - Running system integrity checks
  - Reviewing configuration change control records including security impact analyses
  - Taking remedial action such as quarantining unregistered device(s), blocking insecure protocols, sending alerts, rolling back changes, restoring from backups, updating inventory, updating baseline configurations

### Notifications / communication
- **SecCM Program Manager**
  - Facilitates communications regarding SecCM policies, procedures, issues, etc., within the organization
  - Considers security information management console or “dashboard”
  - Considers Web site updates, emails, and newsletters
- **CCB sample charter “COMMUNICATING STATUS”**
  - Communicate each decision to:
    - the individual who requested the change
    - senior management
    - project management
    - affected team members who must implement the change
    - higher- or lower-level CCBs
    - any other stakeholders
  - Indicate where decisions and supporting information, rationale, or data will be stored

### Absence notes
- **No SLAs, severity bands, or response-time SLAs** are stated for operational handling.
- **No ticket workflow system names** are stated beyond help desk, email, paper-based requests, and automated tools.
- **No explicit remediation POA&M workflow** is defined beyond Plans of Action & Milestones being updated in record-and-archive activities.
