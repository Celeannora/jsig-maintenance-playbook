# Operational Runbook and Audit Artifact Standards Reference

This document is a source-cited reference scaffold for day-to-day security/compliance operations runbooks, evidence records, role assignment, task tickets, and exception handling.

## 1. Runbook/SOP structure conventions used by high-reliability organizations

### 1.1 Common structure pattern

| Runbook element | Convention observed in high-reliability / regulated sources | Why it matters for zero-judgment execution |
|---|---|---|
| Purpose / desired outcome | AWS defines a runbook as a documented process to achieve a specific outcome and says runbooks should contain the desired outcome, necessary tools and permissions, and error-handling instructions ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). | The executor should know the exact end state before starting, so the runbook is not merely a list of actions but a checklist tied to an outcome ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Trigger / use condition | Jira Service Management playbook templates are organized by “Use when” conditions such as high CPU, major incident, change rollback, stakeholder communications, service restart, or software-license provisioning ([Atlassian Jira Service Management playbook templates](https://support.atlassian.com/jira-service-management-cloud/docs/playbook-templates-for-jira-service-management/)). | A runbook should tell the operator when to start it and should avoid requiring the operator to infer whether the task applies ([Atlassian Jira Service Management playbook templates](https://support.atlassian.com/jira-service-management-cloud/docs/playbook-templates-for-jira-service-management/)). |
| Preconditions / prerequisites | Microsoft incident response playbooks include prerequisites such as required logging and required roles and permissions before the investigation starts ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). | A novice operator needs all access, telemetry, and permission requirements stated up front so execution does not stall mid-task ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). |
| Numbered or stepwise actions | AWS says runbooks consist of steps someone follows and, at minimum, can be a step-by-step text document or checklist ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). | A new hire can execute numbered actions without selecting a method or inventing a sequence ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Workflow / phases | Microsoft playbooks include a workflow, a checklist, and detailed investigation steps ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). | The workflow gives the logical path, while the checklist verifies task completion in regulated contexts ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). |
| Task groups / states | ServiceNow security incident playbooks group tasks into phases such as Analysis, Contain, Eradicate, Recover, and Review, and subsequent tasks are presented based on choices made ([ServiceNow Security Incident Response Playbook](https://www.servicenow.com/docs/r/security-management/security-incident-response/use-the-playbook.html)). | Phase gates reduce ambiguity by telling the operator what to do next and when the incident can move to the next state ([ServiceNow Security Incident Response Playbook](https://www.servicenow.com/docs/r/security-management/security-incident-response/use-the-playbook.html)). |
| Expected results / validation | NIST contingency plan validation examples include fields for Procedure, Expected Results, Actual Results, Successful?, and Performed by ([NIST SP 800-34 Rev. 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf)). | Expected-vs-actual result fields make the pass/fail decision observable rather than judgment-based ([NIST SP 800-34 Rev. 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf)). |
| Error handling / exceptions / escalation | AWS says runbooks should include guidance on error handling, tools, permissions, exceptions, and escalations if a problem occurs ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). | Exception paths should be documented in the runbook so an inexperienced operator does not decide whether to continue, stop, roll back, or escalate ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Evidence capture | Microsoft says the checklist in its incident response playbooks can help highly regulated environments verify what was done ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). | Evidence capture should be built into the procedure rather than reconstructed after the task is complete ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). |
| Versioning / testing metadata | PagerDuty’s public security incident response checklist includes `Last Reviewed: YYYY-MM-DD` and `Last Tested: YYYY-MM-DD` metadata ([PagerDuty security incident response checklist](https://github.com/PagerDuty/incident-response-docs/blob/master/docs/during/security_incident_response.md)). | Review and test dates signal whether the runbook is current and operationally exercised ([PagerDuty security incident response checklist](https://github.com/PagerDuty/incident-response-docs/blob/master/docs/during/security_incident_response.md)). |
| Central publication and maintenance | AWS says runbooks should be published in a central location, stored in a central location such as version control, updated frequently, and updated as processes evolve ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). | Centralized version-controlled runbooks reduce drift and reduce the chance that different team members execute different procedures ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |

### 1.2 “So clear a new hire can execute it” criteria

| Criterion | Source-backed convention |
|---|---|
| No reliance on memory | AWS identifies “relying on memory to complete each step” and “manually deploying changes without a checklist” as anti-patterns ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Same result regardless of operator | AWS says runbooks provide consistent outcomes no matter who uses them and that operations are performed consistently when runbooks are used ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Faster new-team-member execution | AWS lists “new team members can start performing tasks sooner” as a benefit of runbooks ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Pre-written troubleshooting steps | Google SRE says thinking through and recording best practices in a playbook produces roughly a 3x improvement in MTTR compared with “winging it,” and it emphasizes clear and thorough troubleshooting steps for high-stakes or time-sensitive pages ([Google SRE Book introduction](https://sre.google/sre-book/introduction/)). |
| Explicit handoff process | Google SRE describes on-call engineers reading the previous shift handoff at the start of a shift and sending a handoff email to the next on-call engineer at the end of the shift ([Google SRE Workbook: On-Call](https://sre.google/workbook/on-call/)). |
| Explicit escalation process | Google SRE notes that on-call guidelines specified when to escalate to others and how to write postmortems for large incidents ([Google SRE Workbook: On-Call](https://sre.google/workbook/on-call/)). |
| Predesignated roles | Atlassian lists “establish predesignated roles” as one of five incident response playbook steps ([Atlassian incident response playbook guidance](https://www.atlassian.com/incident-management/incident-response/how-to-create-an-incident-response-playbook)). |
| Consistent process enforcement | Atlassian lists “enforce a consistent process” as one of five incident response playbook steps ([Atlassian incident response playbook guidance](https://www.atlassian.com/incident-management/incident-response/how-to-create-an-incident-response-playbook)). |
| Stop/continue rule when unsure | PagerDuty’s security incident response checklist says to trigger the process anyway if unsure whether something is a security incident, and says the Incident Commander will determine whether response is needed ([PagerDuty security incident response checklist](https://github.com/PagerDuty/incident-response-docs/blob/master/docs/during/security_incident_response.md)). |

### 1.3 Operational runbook fields that recur across sources

| Field | Practical form | Source basis |
|---|---|---|
| Title / unique identifier | `Runbook name`, `control/task ID`, `ticket ID`, or `POAM ID`. | FedRAMP POA&M uses a unique `POAM ID`, and NIST SP 800-53A assessment procedures use control identifiers and granular determination statements ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx), [NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Trigger / cadence | `Monthly`, `annually`, `ad hoc`, `upon finding`, `when alert X fires`, or `when control Y is due`. | FedRAMP continuous monitoring deliverables include monthly, annual, every-three-year, and ad hoc submissions, and the deliverables template includes a `Frequency` column ([FedRAMP Continuous Monitoring Playbook](https://www.fedramp.gov/resources/documents/Continuous_Monitoring_Playbook.pdf), [FedRAMP Continuous Monitoring Deliverables Template](https://www.fedramp.gov/resources/templates/FedRAMP-Continuous-Monitoring-Deliverables-Template.xlsx)). |
| Scope | `Systems`, `assets`, `control IDs`, `population`, `period reviewed`, and `exclusions`. | NIST SP 800-53A assessment planning uses controls to be assessed, assessment objects, assessment methods, depth, and coverage ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Preconditions | `Required access`, `tools`, `logging enabled`, `roles/permissions`, and `input artifacts`. | Microsoft playbooks include prerequisites such as logging, roles, and permissions ([Microsoft Incident Response Playbooks](https://learn.microsoft.com/en-us/security/operations/incident-response-playbooks)). |
| Step-by-step actions | Numbered steps with one action per step and no implied decisions. | AWS says runbooks should be a series of steps and at minimum a step-by-step text document ([AWS Well-Architected Operational Excellence](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)). |
| Expected output | `Expected result`, `pass/fail rule`, `artifact path`, and `evidence file name`. | NIST contingency testing examples include Expected Results, Actual Results, Successful?, and Performed by ([NIST SP 800-34 Rev. 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf)). |
| Evidence capture | `Screenshots`, `reports`, `logs`, `scan exports`, `signed checklist`, `ticket link`, and `repository location`. | FedRAMP requires ConMon deliverables to be posted in the designated repository, and NIST SP 800-53A lists policies, procedures, plans, records, audit records, system monitoring records, change control records, and prior assessment results as assessment objects ([FedRAMP Continuous Monitoring Deliverables Template](https://www.fedramp.gov/resources/templates/FedRAMP-Continuous-Monitoring-Deliverables-Template.xlsx), [NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Exception path | `If failed`, `if evidence missing`, `if out of scope`, `if false positive`, `if operational requirement`, `if risk adjustment`, and `who approves`. | FedRAMP POA&M includes risk adjustment, false positive, operational requirement, deviation rationale, supporting documents, and comments fields ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Escalation owner | `Responsible party`, `reviewer`, `approver`, `Incident Commander`, `AO`, `CCB`, or `manager`. | PagerDuty assigns an Incident Commander for security incidents, FedRAMP roles include CSP, AO, PMO, and 3PAO responsibilities, and NIST configuration management uses a Configuration Control Board for change decisions ([PagerDuty security incident response checklist](https://github.com/PagerDuty/incident-response-docs/blob/master/docs/during/security_incident_response.md), [FedRAMP Continuous Monitoring Playbook](https://www.fedramp.gov/resources/documents/Continuous_Monitoring_Playbook.pdf), [NIST SP 800-128](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-128.pdf)). |

## 2. Audit artifact / evidence standards

### 2.1 What counts as compliant evidence

| Evidence standard | Source-backed description | Operational implication |
|---|---|---|
| Evidence must support an assessment method | NIST SP 800-53A defines assessment methods as Examine, Interview, and Test, and describes Examine as reviewing, inspecting, observing, studying, or analyzing assessment objects to obtain evidence ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). | Each artifact should state whether completion was proven by document review, interview, or test output ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Evidence should tie to assessment objects | NIST SP 800-53A names assessment objects such as specifications, mechanisms, activities, individuals, policies, procedures, plans, records, administrator/operator manuals, system documentation, prior assessment results, audit records, system monitoring records, configuration settings, and change control records ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). | A proof record should identify exactly which object was examined, interviewed, or tested ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Assessment results may be reused if documented | NIST SP 800-53A encourages reuse of prior control assessment results, documentation, artifacts, and evidence, including independent third-party testing, audits, vulnerability scans, physical security inspections, developmental testing, vendor flaw remediation, and ISO 15408 evaluations ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). | Reused evidence should preserve source, date, scope, and prior assessment context so reuse is traceable ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Findings should support risk decisions | NIST SP 800-53A says assessment findings help determine control effectiveness and help the authorizing official make an informed risk-based decision ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). | Completion records should separate “performed” from “effective / passed / failed” so management can act on findings ([NIST SP 800-53A Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53Ar5.pdf)). |
| Audit records must be reconstructable | IRS guidance says audit trails are chronological sequences of audit records and each audit record contains evidence from a business process or system function, including date/time, unique user ID, event type, success/failure, request origin, object introduced/deleted, and security database modification description ([IRS Safeguards audit requirements](https://www.irs.gov/privacy-disclosure/meeting-irs-safeguards-audit-requirements)). | Evidence should be sufficient to reconstruct who did what, when, from where, and with what result ([IRS Safeguards audit requirements](https://www.irs.gov/privacy-disclosure/meeting-irs-safeguards-audit-requirements)). |
| Logs may require long retention | IRS STAX audit-log guidance says audit information must be archived for six years to recreate computer-related accesses to operating systems and applications wherever FTI is stored ([IRS STAX audit logs memo](https://www.irs.gov/privacy-disclosure/safeguards-technical-assistance-memorandum-stax-audit-logs)). | Runbook evidence should record retention class and archive location when the artifact is a log or log-derived report ([IRS STAX audit logs memo](https://www.irs.gov/privacy-disclosure/safeguards-technical-assistance-memorandum-stax-audit-logs)). |

### 2.3 Evidence patterns by recurring task type

| Task type | Evidence artifacts and fields commonly expected |
|---|---|
| Account review | Evidence should include account population, reviewer, date, personnel/status comparison, exceptions, disabled/remediated accounts, and next review date because IRS Publication 1075 requires annual user-account reviews and semiannual privileged-account reviews ([IRS Publication 1075](https://www.irs.gov/pub/irs-pdf/p1075.pdf)). |
| Audit log review | Evidence should include date/time period reviewed, reviewer role, log source, event types reviewed, anomalies, violations, management notifications, and retention/archive location because IRS audit guidance defines audit-record event fields and gives daily, weekly/monthly, and quarterly review examples by role ([IRS Safeguards audit requirements](https://www.irs.gov/privacy-disclosure/meeting-irs-safeguards-audit-requirements)). |
| Vulnerability scanning | Evidence should include scanner name, scan authorization/authenticated status, raw scan output, finding identifiers, asset identifiers, CVEs, risk rating, POA&M linkage, and repository location because FedRAMP requires vulnerability and configuration scans as ConMon deliverables and the POA&M template captures scanner/source, source identifier, asset, risk rating, CVE, and supporting documents ([FedRAMP Continuous Monitoring Deliverables Template](https://www.fedramp.gov/resources/templates/FedRAMP-Continuous-Monitoring-Deliverables-Template.xlsx), [FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Patch management | Evidence should include software/asset inventory basis, patch priority, schedule, test/validation results, deployment verification, issues encountered, and post-deployment monitoring because NIST SP 800-40r4 describes patch lifecycle steps including acquire, validate, test, deploy, verify deployment, and monitor deployed patches ([NIST SP 800-40 Rev. 4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-40r4.pdf)). |
| POA&M update | Evidence should include POAM ID, controls, weakness name/description, detector source, source identifier, asset, POC, resources required, remediation plan, original detection date, scheduled completion date, status date, risk rating, deviation status, supporting documents, and comments because those are fields in the FedRAMP POA&M template ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Contingency plan testing | Evidence should include test plan, test date, participants, objectives, methodology, activities, expected results, actual results, action item assessment, after-action report, lessons learned, and plan-update actions because IRS Publication 1075 lists contingency testing template content and NIST SP 800-34 identifies After Action Report and Lessons Learned artifacts ([IRS Publication 1075](https://www.irs.gov/pub/irs-pdf/p1075.pdf), [NIST SP 800-34 Rev. 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf)). |
| Incident response drill | Evidence should include plan, participants, test type, results, communications/decision log, work notes, gaps, and corrective actions because FedRAMP requires incident response test plans and results, ServiceNow instructs analysts to enter work notes as tasks are performed, and Microsoft incident planning emphasizes roles, decisions, and recorder responsibilities ([FedRAMP Continuous Monitoring Deliverables Template](https://www.fedramp.gov/resources/templates/FedRAMP-Continuous-Monitoring-Deliverables-Template.xlsx), [ServiceNow Security Incident Response Playbook](https://www.servicenow.com/docs/r/security-management/security-incident-response/use-the-playbook.html), [Microsoft incident response planning](https://learn.microsoft.com/en-us/security/operations/incident-response-planning)). |
| Configuration baseline review | Evidence should include baseline configuration, component inventory, change requests, approvals, security impact analyses, assessment/reporting results, and archived records because NIST SP 800-128 defines SecCM phases, configuration baseline concepts, CCB approvals, monitoring, records, and archive expectations ([NIST SP 800-128](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-128.pdf)). |
| STIG compliance review | Evidence should include STIG rule status, finding details, comments, asset/target data, evaluator attribution, timestamps, and accepted/rejected review status because STIG Manager maps `.ckl` fields to STIG Viewer Status, Finding Detail, and Comments, and describes review content and status attribution ([STIG Manager terminology and concepts](https://stig-manager.readthedocs.io/en/1.3.7/reference/)). |

## 3. RACI / role-assignment matrix conventions for security operations tasks

### 3.1 Role-assignment conventions across frameworks

| Convention | Source-backed rule |
|---|---|
| Use explicit role ownership, not implied team ownership | ISO 27001 implementation guidance says information security roles and responsibilities should be defined and allocated to specific people or teams, and it recommends job descriptions or RACI matrices as documentation methods ([TCSA ISO 27001 A.5.2 guidance](https://www.tcsa.in/frameworks/iso-27001/controls/5-2-information-security-roles-and-responsibilities)). |
| RACI meanings should be fixed | RACI is defined as Responsible, Accountable, Consulted, and Informed, with Responsible doing the work, Accountable owning the outcome, Consulted providing two-way input, and Informed receiving one-way updates ([Advisera ISO 27001 RACI guidance](https://advisera.com/27001academy/blog/2018/11/05/raci-matrix-for-iso-27001-implementation-project/)). |
| Accountability should not vanish when work is delegated | NIST SP 800-37 Rev. 2 says RMF tasks identify primary responsibility and supporting roles, and that primary-responsibility roles remain accountable even when completion is delegated unless delegation is prohibited or disallowed ([NIST SP 800-37 Rev. 2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-37r2.pdf)). |
| RMF role matrices commonly use primary/supporting responsibility | NIST SP 800-37 uses `Primary Responsibility` and `Supporting Roles` for RMF tasks instead of a formal RACI label ([NIST SP 800-37 Rev. 2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-37r2.pdf)). |
| Control ownership should specify origin and shared responsibility | FedRAMP SSP templates define control origination categories such as Service Provider Corporate, Service Provider System Specific, Service Provider Hybrid, Configured by Customer, Provided by Customer, Shared, and Inherited from pre-existing FedRAMP Authorization ([FedRAMP SSP Moderate Baseline Template](https://www.fedramp.gov/resources/documents/rev4/REV_4_FedRAMP-SSP-Moderate-Baseline-Template.docx)). |
| Continuous monitoring has program-level roles | FedRAMP ConMon assigns CSPs responsibility for implementing, maintaining, monitoring controls, identifying vulnerabilities, responding to incidents, providing information, maintaining the repository, and addressing findings, while Agency AOs review ConMon activities, monthly POA&Ms, deviation requests, significant changes, annual assessments, and ongoing authorization decisions ([FedRAMP Continuous Monitoring Playbook](https://www.fedramp.gov/resources/documents/Continuous_Monitoring_Playbook.pdf)). |
| DoD RMF assigns formal authority and repository/status responsibilities | DoDI 8510.01 assigns responsibilities for RMF execution, maintaining assessment and authorization status in automated tools or repositories, managing POA&Ms, appointing AOs, and maintaining authorized systems under RMF ([DoDI 8510.01](https://www.esd.whs.mil/Portals/54/Documents/DD/issuances/dodi/851001p.pdf)). |

## 5. Escalation and exception-handling patterns

### 5.1 Failure-handling pattern for recurring checks

| Failure / exception condition | Standard response pattern |
|---|---|
| Check fails or weakness is found | FedRAMP CA-5 requires CSPs to develop and maintain a POA&M to document remediation plans for correcting risks identified during security assessments and ConMon activities ([FedRAMP Continuous Monitoring Playbook](https://www.fedramp.gov/resources/documents/Continuous_Monitoring_Playbook.pdf)). |
| Finding needs remediation tracking | FedRAMP POA&M is used to facilitate tracking of risk remediation and mitigation activities and includes security findings from periodic assessments and ongoing continuous monitoring ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| High/critical, moderate, or low risk finding exceeds timeline | FedRAMP POA&M instructions state high and critical findings must be remediated within 30 days of discovery, moderate findings within 90 days, and low findings within 180 days of discovery ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Item is believed false positive | FedRAMP POA&M includes a `False Positive` field with pending/approved handling and says approved false-positive deviation requests can be moved to the closed tab ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Remediation cannot be completed without operational impact | FedRAMP POA&M defines an operational requirement as a weakness that cannot be corrected without impacting full operation of the system and requires operational requirement status and deviation rationale fields ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Risk rating needs adjustment | FedRAMP POA&M includes `Adjusted Risk Rating`, `Risk Adjustment`, and `Deviation Rationale` fields to document mitigating factors or compensating controls ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Evidence is complete and remediation applied | FedRAMP POA&M instructions allow moving a POA&M item to the closed worksheet when corrective actions have been applied and evidence of remediation is collected and available for inspection ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Closure needs independent validation | FedRAMP POA&M instructions state evidence of remediation must be verified by a 3PAO during periodic assessments and may be requested by the AO at any time ([FedRAMP POA&M Template](https://www.fedramp.gov/resources/templates/FedRAMP-POAM-Template.xlsx)). |
| Security incident classification is uncertain | PagerDuty says to trigger the security incident process anyway if unsure, and the Incident Commander will decide whether response is needed ([PagerDuty security incident response checklist](https://github.com/PagerDuty/incident-response-docs/blob/master/docs/during/security_incident_response.md)). |
| Change introduces uncertainty or risk | NIST SP 800-128 says a CCB may use dispositions such as approved, not approved, or on hold, and may define evaluation criteria, quorum, membership, and special-meeting triggers ([NIST SP 800-128](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-128.pdf)). |
