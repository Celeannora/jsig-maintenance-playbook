## 5. Procedure

**Pattern E — Documentation / Policy Review and Update** (assignment from `runbooks/ISSM.md`)

1. Export the current list of audited event categories/IDs from the Windows Security event log configuration by running `auditpol /get /category:*` on representative domain-joined systems (the `auditpol` command-line surface is documented alongside other Windows Server administration commands — see [Microsoft Learn Windows Commands reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/dcdiag)). — Expected result: a current per-category audit-policy export from a representative system sample. — Capture: the `auditpol` output, with hostnames and pull date. — Stop/continue: continue.
2. Compare the exported audit policy against the auditable-events list currently ingested and indexed by Splunk (confirm via the relevant index's saved searches/scheduled alerts, per the [Splunk Enterprise Alerting Manual](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts)) to confirm all required event types are being collected. — Expected result: a gap list of any audited-but-not-ingested or ingested-but-not-audited event categories (may be empty). — Capture: the comparison record. — Stop/continue: continue regardless of whether gaps are found — a no-change review still requires documented re-approval.
3. Review recent Splunk incident and audit findings to identify any event types that should be added to or removed from the auditable-events list based on operational need, consistent with the **weekly audit-record review** cadence documented as an analogous federal requirement in [IRS Publication 1075](https://www.irs.gov/pub/irs-pdf/p1075.pdf) (no JSIG-specific AU-2 review-frequency ODP is available in this repository's sourced references — this is cited as a documented analogue, not a confirmed JSIG value). — Expected result: a list of needed additions/removals with rationale (may be empty). — Capture: the review notes. — Stop/continue: continue.
4. Update the auditable-events list document to reflect any additions, removals, or reclassifications, noting the rationale for each change. — Expected result: draft list ready for routing, or a no-change re-approval memo if none are needed. — Capture: the draft/memo. — Stop/continue: continue.
5. Apply corresponding `auditpol` / Group Policy audit-policy changes via the Group Policy Management Console (GPMC) where the list update requires new event categories to be enabled. — Expected result: policy updated to match the revised list, or no change required. — Capture: the GPO change record/ticket ID. — Stop/continue: if the change requires an approved maintenance window not yet available, stop and document the compensating control/interim risk acceptance rather than leaving the gap silently open.
6. Route the updated list through the ISSM/ISSO for review and approval. — Expected result: documented approval or rejection with rationale. — Capture: approval record/signature. — Stop/continue: if rejected, return to step 4; do not publish an unapproved revision.
7. File the approved auditable-events list in the repository with the reviewer's name and date. — Expected result: cycle record filed, prior version archived, not deleted. — Capture: both version files/locations. — Stop/continue: cycle complete.
