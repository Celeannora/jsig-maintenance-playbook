## 5. Procedure

**Pattern B — Manual Review of a List or Log** (assignment from `runbooks/Privileged-Users.md`)

1. Export the current firewall/boundary-device rule base for the SAP enclave: for the Windows Defender Firewall with Advanced Security GPO, run `Get-NetFirewallRule` (optionally piped through `Get-NetFirewallPortFilter` or `Get-NetFirewallApplicationFilter` to resolve port/application scope) ([Microsoft Learn — Windows Defender Firewall command-line configuration](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure-with-command-line)); for a non-Windows network boundary device, pull its ACL export through its own management console/CLI. — Expected result: a complete, current export of every active rule/ACL entry. — Capture: the export file, with pull timestamp. — Stop/continue: if the export is incomplete, stop and remediate the collection gap before reviewing partial data.
2. Review each rule for business justification, confirming source/destination/port/protocol restrictions still match the approved System Security Plan network diagram. — Expected result: every rule maps to a documented, currently-valid business justification. — Capture: the annotated rule-by-rule review. — Stop/continue: continue regardless of discrepancy count; log every unjustified rule for step 5.
3. Run a Splunk search against boundary-device/firewall logs (e.g., `search index=<firewall_index> earliest=-90d` filtered/transformed to identify traffic matching overly permissive rules such as any-any, or rules with zero hit-count over the review period) using standard SPL comparison/time-range syntax ([Splunk Enterprise Search Manual / Alerting Manual](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts)); save it as a scheduled search/alert if not already in place for recurring review. — Expected result: a list of rules with zero-hit-count or overly permissive matches (may be empty). — Capture: the Splunk search results/export. — Stop/continue: continue.
4. Cross-check the rule set against the CCB-approved firewall change log to confirm no undocumented rule additions or modifications occurred. — Expected result: every active rule traces to an approved CCB change record. — Capture: the cross-check worksheet. — Stop/continue: if an undocumented rule addition/modification is found, stop and escalate immediately per the Escalation block — this is a potential unauthorized-change finding, not a routine discrepancy.
5. Flag unused, overly permissive, or undocumented rules and submit a rule-removal/tightening request through the CCB. — Expected result: every flagged rule has a submitted CCB change request. — Capture: CCB request ID(s). — Stop/continue: continue.
6. Export the rule-set review report and Splunk query results and file them in the repository location specified in the Task Index, alongside the reviewer's name and date. — Expected result: complete evidence package filed for the cycle. — Capture: the filed report and query results. — Stop/continue: cycle complete.
