## 5. Procedure

**Pattern D — Test / Exercise** (assignment from `runbooks/ISSO.md`)

1. Schedule and pull the current, approved semi-annual incident-response tabletop or functional test plan, using a scenario drawn from the current IR plan. — Expected result: current test plan/scenario in hand, version confirmed. — Capture: test plan version/date and selected scenario. — Stop/continue: if no current approved plan exists, stop — do not improvise an untested procedure; escalate the missing-plan gap first.
2. Execute the exercise: inject simulated indicators into Splunk (or validate against existing saved searches/alert rules) to confirm the IR team can detect, triage, and escalate within the plan's required timelines ([Splunk Enterprise Alerting Manual](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts)); if the scenario involves simulated data loss/ransomware, also validate recovery-time expectations against the backup solution's job console or restore-verification feature (NetBackup Activity Monitor/`bpimagelist` or Veeam Backup & Replication job history/SureBackup) ([Veritas NetBackup Administrator's Guide](https://www.veritas.com/support/en_US/doc/150157642-165935937-0/v130722414-165935937); [Veeam Backup & Replication User Guide](https://helpcenter.veeam.com/docs/vbr/userguide/session_results_web.html)) without performing an actual production restore. — Expected result: every planned step executed with a recorded actual result against each expected result in the plan. — Capture: step-by-step execution log, including detection timestamps and (if applicable) recovery-time-objective validation notes. — Stop/continue: if a step risks the production environment, stop the test immediately and document the abort point.
3. Time and record each phase of the response (detection, containment, eradication, recovery, reporting) against the IR plan's target metrics, and compare aggregate actual results against the plan's overall success criteria. — Expected result: a pass/fail determination per phase and overall. — Capture: the timing table and determination. — Stop/continue: continue regardless of outcome.
4. Draft an after-action report documenting exercise participants, scenario, timeline performance against target metrics, and any gaps in detection, escalation, or (if tested) recovery-time performance. — Expected result: a complete AAR. — Capture: the AAR file. — Stop/continue: continue.
5. For any gap identified, open a POA&M entry and assign a remediation owner and date; update the IR plan and Splunk detection/alerting rules to address identified gaps, routing changes through the ISSM for approval. — Expected result: every gap has a tracking ID and, where the IR plan or detection rules themselves need correction, a routed change request. — Capture: POA&M ID(s) and ISSM approval record for any plan/rule changes. — Stop/continue: continue.
6. File the test plan, execution log, and AAR in the repository location specified in the Task Index; update the plan itself if the test surfaced a procedural error in it. — Expected result: complete cycle package filed. — Capture: filed package. — Stop/continue: cycle complete.
