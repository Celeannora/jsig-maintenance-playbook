## 5. Procedure

**Pattern A — Automated Monitoring / Scan Confirmation** (assignment from `runbooks/Privileged-Users.md`)

1. Open the Splunk SIEM dashboard and review audit storage capacity for all in-scope log-source indexes (AU-4), checking each index's current size against its configured `maxTotalDataSizeMB` and its data age against `frozenTimePeriodInSecs` in `indexes.conf` ([Splunk index retirement/archiving policy documentation](https://help.splunk.com/en/data-management/manage-splunk-enterprise-indexers/9.1/back-up-and-archive-your-indexes/set-a-retirement-and-archiving-policy)). — Expected result: no in-scope index is within its warning threshold of `maxTotalDataSizeMB`, and no index's `frozenTimePeriodInSecs` setting would cause required audit data to roll to (unsearchable, and by default deleted) frozen storage before the organization's retention requirement is met. — Capture: the dashboard export/screenshot and the reviewed `indexes.conf` retention settings. — Stop/continue: if any index is projected to breach its size or age threshold before the next review cycle, continue to step 5 for that index.
2. Confirm current index disk utilization is below the configured warning threshold and review retention/rollover (hot → warm → cold → frozen bucket lifecycle) settings for each index ([Splunk index management documentation](https://help.splunk.com/en/data-management/manage-splunk-enterprise-indexers/9.1/back-up-and-archive-your-indexes/set-a-retirement-and-archiving-policy)). — Expected result: bucket lifecycle settings are documented and consistent with organizational audit-retention policy; frozen data is configured to archive rather than silently delete if required for retention. — Capture: the retention-configuration review notes. — Stop/continue: continue.
3. Run the Splunk saved search/scheduled alert for audit processing-failure events (forwarder disconnects, indexing queue blocks, dropped events) for the reporting period (AU-5), using SPL to search the relevant internal/monitoring indexes (e.g. `index=_internal source=*splunkd.log* (component=TailingProcessor OR component=Metrics) (blocked OR disconnect)`, adapted to the organization's actual monitoring index/sourcetype naming) per [Splunk's saved-search/alert scheduling documentation](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts) and [SPL search syntax reference](https://help.splunk.com/en?resourceId=Splunk_SearchReference_Search&version=splunk-9_4). — Expected result: a complete list of this period's processing-failure events (may be empty). — Capture: the saved-search results export. — Stop/continue: continue to step 4 for each event found.
4. Investigate and document root cause and resolution for any processing-failure alert triggered during the period. — Expected result: every processing-failure event has a documented root cause and resolution status. — Capture: the investigation notes/ticket. — Stop/continue: if any processing failure resulted in an actual gap in required audit-record collection, treat as a finding and escalate per Section 6.
5. Adjust index storage allocation or retention policy if utilization trend or age projects a threshold breach before the next review cycle, opening a change ticket for the `indexes.conf` update through the organization's standard change-control process. — Expected result: a tracked remediation action for any index at risk of breaching capacity/retention thresholds. — Capture: the change ticket ID. — Stop/continue: continue.
6. Export the Splunk capacity and processing-failure dashboard reports and file them in the repository location specified in the Task Index, alongside the reviewer's name and date. — Expected result: a complete, filed evidence package for the cycle. — Capture: the filed report package. — Stop/continue: cycle complete.
