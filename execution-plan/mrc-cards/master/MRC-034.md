## 5. Procedure

**Pattern H — Governance / Authorization Decision** (assignment from `runbooks/ISSM.md`). CM-3 requires a documented configuration change control process; no reference doc in `reference/external-sources/` specifies a CCB meeting cadence or quorum mechanic, so the steps below keep the CCB's own procedural mechanics (quorum rule, minute format) at the organization-defined level per the governance-card convention rather than inventing a specific figure.

1. Pull open change requests from the configuration/ticketing system queued for CCB review this cycle, in the local GRC/ticketing/documentation repository used for change management. — Expected result: a complete, current queue of change requests pending CCB disposition. — Capture: the queue export, with pull timestamp. — Stop/continue: if no changes are queued this cycle, log a no-meeting-required cycle per the card's title ("when changes proposed") and close; otherwise continue.
2. Convene the CCB meeting per the charter, with the CCB Chair confirming quorum of designated voting members. — Expected result: quorum confirmed and meeting convened, or meeting deferred/rescheduled if quorum is not met. — Capture: attendance/quorum record. — Stop/continue: if quorum is not met, stop and reschedule rather than rendering decisions without quorum.
3. Present each proposed change with its security-impact analysis and testing/rollback plan for CCB discussion. — Expected result: every queued change has been presented and discussed. — Capture: the meeting agenda and supporting change packages. — Stop/continue: continue.
4. Record CCB voting decisions (approve, reject, deferred) for each change in the meeting minutes. — Expected result: every discussed change has a recorded disposition. — Capture: the signed meeting minutes/decision record. — Stop/continue: continue.
5. Route approved changes to the ISSM for authorization sign-off and update the change's status in the ticketing system. — Expected result: every approved change has ISSM sign-off and an updated ticket status. — Capture: the sign-off record and updated ticket. — Stop/continue: if the ISSM does not sign off, the change reverts to pending/rejected status rather than proceeding.
6. Notify the AO/DAO of any changes affecting the system's approved security baseline. — Expected result: AO/DAO notified for every baseline-affecting change. — Capture: notification record. — Stop/continue: continue.
7. Export the signed CCB meeting minutes and decision record and file it in the repository location specified in the Task Index, alongside the reviewer's name and date. — Expected result: evidence package filed and retrievable for audit. — Capture: the filed export and its repository path. — Stop/continue: cycle/event complete.
