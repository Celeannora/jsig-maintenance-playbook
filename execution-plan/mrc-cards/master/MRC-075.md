## 5. Procedure

**Pattern D — Test / Exercise** (assignment from `runbooks/ISSM.md`)

Applies to tasks that execute a planned test against a written procedure (e.g., backup restoration, contingency plan exercise, incident response exercise, information system recovery/reconstitution, fire-suppression test).

1. Define the penetration test scope, rules of engagement, and authorized test window, and obtain AO/DAO written authorization prior to testing. — Expected result: signed rules-of-engagement/authorization document in hand. — Capture: the signed authorization. — Stop/continue: if AO/DAO authorization is not obtained, stop — do not begin testing without written authorization.
2. Execute external and internal penetration testing against in-scope systems, using Tenable Nessus scan results (credentialed vulnerability/compliance scan output, per the [Tenable Nessus User Guide](https://docs.tenable.com/nessus/10_12/Content/PDF/Nessus_10_12.pdf)) as the vulnerability baseline to prioritize exploitation attempts. — Expected result: a prioritized target list of vulnerabilities/hosts for exploitation attempts. — Capture: the Nessus scan export used as the baseline. — Stop/continue: continue.
3. Attempt exploitation of identified vulnerabilities and privilege-escalation/lateral-movement paths, documenting each successful and attempted technique with timestamps. — Expected result: every planned technique executed with a recorded actual result (success/failure, timestamp). — Capture: step-by-step execution log. — Stop/continue: if an exploitation attempt risks production availability/integrity beyond the agreed rules of engagement, stop immediately and document the abort point.
4. Correlate testing activity against Splunk logs (Windows Security event log, firewall/boundary-device logs) using a search such as the field-value and time-bounded SPL patterns described in the [Splunk Enterprise Search Reference](https://help.splunk.com/en?resourceId=Splunk_SearchReference_Search&version=splunk-9_4) to validate detection and alerting coverage during the test. — Expected result: a determination of which test activities were/were not detected by existing logging and alerting. — Capture: the SPL search results/exported evidence. — Stop/continue: continue regardless of outcome.
5. Compile a penetration test report detailing findings, exploited vulnerabilities, risk ratings, and recommended remediations. — Expected result: completed penetration test report. — Capture: the report file. — Stop/continue: continue.
6. Brief the ISSM and SCA on findings and open POA&M entries for any critical or high-risk findings requiring remediation, sized using a defensible severity-to-timeline convention (e.g., the [CMS POA&M Handbook](https://security.cms.gov/learn/cms-plan-action-and-milestones-poam-handbook)'s Critical 15-day/High 30-day tiers) where the organization has not defined its own. — Expected result: every critical/high finding has a tracking ID, severity, and target remediation date. — Capture: POA&M ID(s) and severity ratings. — Stop/continue: continue.
7. File the signed penetration test report and POA&M updates in the repository location specified in the Task Index with the SCA/SCAR's name and test date. — Expected result: complete cycle package filed. — Capture: filed package. — Stop/continue: cycle complete.
