## 5. Procedure

**Pattern A — Automated Monitoring / Scan Confirmation** (assignment from `runbooks/Privileged-Users.md`)

1. On each domain controller, confirm the Windows Time service (W32Time) is running and check its current sync status by running `w32tm /query /status /verbose`; on a sample of member servers, confirm they are correctly chaining to the domain hierarchy. — Expected result: every DC reports a current, in-tolerance time source and offset; member servers show a healthy last-sync time. — Capture: console output/export of the `w32tm` status for each checked host. — Stop/continue: if any host shows no recent successful sync, continue to step 2 but flag that host for priority remediation.
2. Run `dcdiag /test:frsevent` and `repadmin /replsummary` against all domain controllers to confirm AD DS replication and the FRS/DFSR event log show no time-service-related errors, using [Microsoft's `dcdiag`/`repadmin` command reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/dcdiag) for expected output and switches. — Expected result: `dcdiag` reports passed tests with no time-skew-flagged replication failures, and `repadmin /replsummary` shows no DC with a Kerberos/time-related error code. — Capture: redirected `dcdiag`/`repadmin` output files. — Stop/continue: if a DC shows a replication failure tied to a time-skew signature, escalate that DC for immediate remediation before continuing the cycle.
3. Run the scheduled Splunk saved search (or, if none yet exists, an ad hoc equivalent configured per the [Splunk Enterprise scheduling documentation](https://help.splunk.com/en/splunk-enterprise/search/search-manual/9.4/save-and-schedule-searches/scheduling-searches)) against the Windows Security/System event log index for time-service Event IDs 36 (time provider) and 129/142 (W32Time service errors) over the review period. — Expected result: search returns zero unreviewed time-provider/service-error events, or a fully dispositioned list. — Capture: exported Splunk search results (CSV/PDF). — Stop/continue: continue to step 4 regardless of findings; findings are documented, not gated, at this step.
4. Confirm the authoritative time source configured on the PDC emulator (e.g., a GPS appliance or external NTP source) is still correctly set via `w32tm /query /configuration` run on that DC. — Expected result: `NtpServer` and `Type` values match the organization's approved authoritative source configuration. — Capture: `w32tm /query /configuration` output. — Stop/continue: if the configured source has drifted from policy, stop and open a change-control ticket in the local ticketing/GRC system before making any configuration change.
5. For any host identified in steps 1–3 with clock drift exceeding the organization's allowed threshold, run `w32tm /resync` and re-verify with `w32tm /query /status` that the offset has corrected. — Expected result: post-resync offset is within tolerance. — Capture: before/after `w32tm` status output. — Stop/continue: if drift persists after resync, escalate to the ISSM as a potential hardware clock or network-path issue.
6. Log cycle completion (date, reviewer, hosts checked, any drift findings and remediation) and export the Splunk search results and `w32tm`/`dcdiag`/`repadmin` output, filing them in the repository location specified in the Task Index. — Expected result: cycle record filed. — Capture: the consolidated evidence bundle. — Stop/continue: cycle complete.
