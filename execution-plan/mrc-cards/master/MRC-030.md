## 5. Procedure

**Pattern D — Test / Exercise** (assignment from `runbooks/Privileged-Users.md`)

1. Select a sample of backup sets (full and incremental) from the past month per the backup testing schedule in the Contingency Plan, which at minimum must satisfy the [GSA Contingency Planning Guide](https://www.gsa.gov/system/files/Contingency-Planning-(CP)-%5BCIO-IT-Security-06-29-Rev-7%5D.pdf)'s and [NIST SP 800-34 Rev. 1](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf)'s at-least-annual backup reliability/integrity testing floor (this card's monthly cadence exceeds that floor). — Expected result: a defined, documented sample selected for this cycle. — Capture: the sample list with selection rationale. — Stop/continue: continue.
2. Perform a test restoration of the sampled backup data to an isolated recovery/test environment using your backup solution's restore workflow — NetBackup's Recovery page **Start recovery** wizard (Regular recovery, with **Preview media** to confirm source images) per the [Veritas NetBackup Web UI Administrator's Guide](https://www.veritas.com/support/en_US/doc/150157642-165935937-0/v130722414-165935937), or Veeam's **SureBackup** job (full recoverability testing in an isolated virtual lab) per the [Veeam Backup & Replication User Guide](https://helpcenter.veeam.com/docs/vbr/userguide/session_results_web.html). — Expected result: restore/SureBackup job completes with a successful status (NetBackup job status `0`, or a passed Veeam SureBackup heartbeat/ping/application test). — Capture: the restore/SureBackup job's detailed status log. — Stop/continue: if a step fails in a way that risks the production environment, stop the test immediately and document the abort point.
3. Verify file/data integrity and completeness of the restored data by comparing checksums or record counts against the source system — for NetBackup, this can be corroborated with a `bpverify` catalog-integrity check (confirms media readability against the catalog, not a byte-for-byte content compare) per the [Veritas NetBackup Administrator's Guide](https://www.veritas.com/support/en_US/doc/150157642-165935937-0/v130722414-165935937); Veeam SureBackup's CRC-based backup file validation provides an equivalent content check per the [Veeam Backup & Replication User Guide](https://helpcenter.veeam.com/docs/vbr/userguide/session_results_web.html). — Expected result: restored data matches source in checksum/record count, with no unexplained discrepancy. — Capture: the comparison/validation results. — Stop/continue: continue regardless of outcome; a failed comparison becomes a documented finding in step 5.
4. Time the restoration process and compare it against the Recovery Time Objective (RTO) defined in the Contingency Plan, consistent with the RTO/RPO-driven backup-frequency and recovery framing in the [GSA Contingency Planning Guide](https://www.gsa.gov/system/files/Contingency-Planning-(CP)-%5BCIO-IT-Security-06-29-Rev-7%5D.pdf). — Expected result: measured restoration duration is within the documented RTO. — Capture: timing record (start/end timestamps) alongside the RTO value. — Stop/continue: continue.
5. Document any restoration failures, data corruption, or RTO shortfalls and initiate corrective action with the backup administrator; open a POA&M entry with a remediation owner and date for any gap identified (see [MRC-025](MRC-025.md)). — Expected result: every gap has a tracking ID and assigned owner. — Capture: POA&M ID(s) and corrective-action notes. — Stop/continue: if a CAT I-level gap is found (e.g., backups are not restorable at all), stop and escalate immediately per the Escalation block below.
6. Export the restoration test results and file them in the repository location specified in the Task Index alongside the reviewer's name and date; update the Contingency Plan's backup testing schedule if the test surfaced a procedural error in it. — Expected result: complete cycle package filed. — Capture: the filed evidence package. — Stop/continue: cycle complete.
