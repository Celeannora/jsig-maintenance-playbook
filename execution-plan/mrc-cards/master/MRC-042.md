## 5. Procedure

**Pattern A — Automated Monitoring / Scan Confirmation** (assignment from `runbooks/Privileged-Users.md`)

1. In the ePO console, go to **Menu | Reporting | Queries** and run (or build via the Query Builder wizard) an Agent Wake-Up/communication-status query against the Managed Systems result type to confirm all managed endpoints checked in and executed scheduled self-tests within the cycle ([Trellix ePO Product Guide](http://b2b-download.trellix.com/PRODUCTS/naibeta-download/epo_460/previous%20postings/epo_460_beta2_productguide.pdf)). — Expected result: last-check-in timestamp for every managed endpoint is within one cycle of due date. — Capture: export the query results (CSV/PDF) from ePO. — Stop/continue: if any endpoint's tool did not check in/run, stop and open a missed-cycle ticket in the local ticketing/GRC system before proceeding.
2. Review the ePO Threat Event Log and a Policy Compliance query (**Menu | Reporting | Queries**, Policy Management feature group) for any endpoints reporting failed or disabled security-function self-tests (AV engine, firewall, HIPS) ([Trellix ePO Product Guide](http://b2b-download.trellix.com/PRODUCTS/naibeta-download/epo_460/previous%20postings/epo_460_beta2_productguide.pdf)). — Expected result: no unreviewed non-compliant/failed-self-test rows older than the cycle window. — Capture: export the Threat Event Log and Policy Compliance query results. — Stop/continue: continue to step 3 regardless of findings; findings are documented, not gated, at this step.
3. Cross-reference any Tenable Nessus credentialed scan results flagging disabled or non-functional security agents on scanned hosts ([Tenable Nessus User Guide](https://docs.tenable.com/nessus/10_12/Content/PDF/Nessus_10_12.pdf)). — Expected result: every Nessus-flagged host is reconciled against the ePO self-test findings from step 2. — Capture: the Nessus scan export. — Stop/continue: continue.
4. Run a Splunk saved search (scheduled per the standard saved-search/alert pattern) against the Windows Security event log for Service Control Manager events indicating unexpected stopping of security services ([Splunk Enterprise documentation](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts)). — Expected result: every unexpected security-service-stop event is identified for the cycle window. — Capture: the saved-search results export. — Stop/continue: if any true positive is CAT I (e.g., security function disabled fleet-wide or on a high-value host), stop and escalate immediately per the Escalation block below before continuing routine triage.
5. For any host with a failed or missing self-test result, open a remediation ticket and verify the agent is restarted/reinstalled and re-checks in to ePO. — Expected result: every affected host shows a passing self-test and current check-in status after remediation. — Capture: the remediation ticket and post-fix ePO check-in confirmation. — Stop/continue: continue.
6. File or update the corresponding POA&M/tracking entry for any open finding, with CAT (I/II/III) assigned per the finding's own severity source (STIG CAT rating, CVSS-derived CAT per `execution-plan/templates/VARIANCE-RISK-ACCEPTANCE-TEMPLATE.md`, or organizational policy for non-STIG/CVE findings). — Expected result: every open finding has a tracking ID and assigned CAT. — Capture: POA&M ID and CAT assignment. — Stop/continue: continue.
7. Export the ePO compliance summary, Nessus cross-reference, and Splunk search results, and file them in the repository location specified in the Task Index alongside the reviewer's name and date. — Expected result: cycle record filed with full supporting evidence. — Capture: the filed evidence bundle and log entry. — Stop/continue: cycle complete.
