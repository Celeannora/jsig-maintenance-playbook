## 5. Procedure

**Pattern A — Automated Monitoring / Scan Confirmation** (assignment from `runbooks/Privileged-Users.md`)

1. In Splunk, run the boundary/firewall SIEM dashboard (a saved search or scheduled report per the [Splunk Enterprise Alerting Manual](https://help.splunk.com/en/splunk-enterprise/alert-and-respond/alerting-manual/9.1/create-alerts/create-scheduled-alerts)) to review inbound traffic-volume and connection-rate metrics for anomalies indicating a denial-of-service condition against SC-5 thresholds. — Expected result: the scheduled search/dashboard shows a run within the current cycle with no unreviewed anomaly older than the cycle window. — Capture: export or screenshot the dashboard/search results. — Stop/continue: if the scheduled search did not run on cadence, stop and open a missed-cycle ticket in the local ticketing/GRC system before proceeding.
2. In Splunk, query TLS/session-layer logs (an SPL search over the relevant sourcetype/index, e.g. `search sourcetype=<session-log> (status=4* OR status=5*)` style field-value filtering per the [Splunk Search Reference](https://help.splunk.com/en/splunk-enterprise/search/search-manual/9.4/search-overview/types-of-searches)) to confirm session tokens are being validated and no session-hijacking or spoofing indicators are present per SC-23. — Expected result: no unexplained session-authenticity anomalies in the query results. — Capture: the saved search results/export. — Stop/continue: continue to step 3 regardless of findings; findings are documented, not gated, at this step.
3. Check the boundary device (firewall/IPS) dashboard for active rate-limiting, SYN-flood protection, or blackhole/sinkhole rules and confirm they remain enabled. — Expected result: all expected DoS-mitigation rules show an enabled/active state. — Capture: screenshot or export of the boundary device's rule/status view. — Stop/continue: if a mitigation rule is unexpectedly disabled, stop and escalate immediately per the Escalation block below.
4. Review any Splunk-triggered DoS or session-anomaly alerts from the shift and confirm each was acknowledged and dispositioned (true positive vs. false positive) by the Network Administrator. — Expected result: every alert is dispositioned with supporting rationale. — Capture: annotated alert list with disposition. — Stop/continue: if any true positive is CAT I, stop and escalate immediately per the Escalation block before continuing routine triage.
5. If an anomaly or alert required action, verify the mitigating control (rate limit, ACL change, session reset) was applied and logged, and determine CAT (I/II/III) per the finding's own severity source or organizational policy. — Expected result: mitigating action confirmed and CAT assigned. — Capture: change record and CAT assignment. — Stop/continue: continue.
6. File or update the corresponding POA&M/tracking entry for any open finding. — Expected result: every open finding has a tracking ID. — Capture: POA&M ID. — Stop/continue: continue.
7. Export the Splunk dashboard/alert review as a PDF or CSV and file it, along with cycle completion details (date, reviewer, finding count, tracking IDs), in the repository location specified in the Task Index. — Expected result: cycle record filed. — Capture: the exported dashboard/alert file and log entry. — Stop/continue: cycle complete.
