## 5. Procedure

**Pattern E — Documentation / Policy Review and Update** (assignment from `runbooks/ISSM.md`)

Applies to tasks that periodically revise a governing document (e.g., System Security Plan, Contingency Plan, Incident Response Plan, Configuration Management Plan, family policies/procedures, privacy notices/SORNs). Per [GSA's CP Guide](https://www.gsa.gov/system/files/Contingency-Planning-(CP)-%5BCIO-IT-Security-06-29-Rev-7%5D.pdf) and [NIST SP 800-34 Rev.1](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf), the contingency plan must be reviewed/updated and tested at least annually, matching this card's frequency.

1. Retrieve the current signed Contingency Plan (CP) document from the compliance/GRC document repository and note its last-approved revision date. — Expected result: current CP version and revision history in hand. — Capture: version number/date. — Stop/continue: continue.
2. Review the plan's recovery procedures, alternate processing/storage site details, and system component inventory against the current Windows Server environment, including any changes to backup targets, failover hosts, or recovery-point/recovery-time objectives. — Expected result: a list of needed revisions (may be empty). — Capture: the review notes. — Stop/continue: continue regardless of whether revisions are needed — a no-change review still requires documented re-approval per the annual cadence in [NIST SP 800-34 Rev.1](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf).
3. Cross-check the plan's system inventory and dependencies against current `Get-ADComputer` output and the backup job configuration in your backup solution's console (NetBackup Activity Monitor/Jobs list per the [NetBackup Web UI Administrator's Guide](https://www.veritas.com/support/en_US/doc/150157642-165935937-0/v130722414-165935937), or the Veeam Backup & Replication job History/Logs and Events view per the [Veeam Backup & Replication User Guide](https://helpcenter.veeam.com/docs/vbr/userguide/session_results_web.html)) to confirm no drift. — Expected result: system inventory and backup-job scope confirmed consistent with the CP, or discrepancies identified. — Capture: the `Get-ADComputer` export and backup-console screenshot/export. — Stop/continue: if drift is found (decommissioned servers, new applications, changed backup targets), continue to step 4 to draft a correction; otherwise proceed to the no-change path in step 4.
4. Draft revisions to the CP addressing any identified gaps (e.g., changed IP schemes, decommissioned servers, new applications), or draft a no-change re-approval memo if the annual review finds the plan still accurate. — Expected result: draft ready for routing. — Capture: the draft. — Stop/continue: continue.
5. Route the updated CP through the ISSM for review and the AO/DAO for approval signature. — Expected result: documented approval or rejection with rationale. — Capture: approval record/signature. — Stop/continue: if rejected, return to step 4; do not publish an unapproved revision.
6. Publish the approved CP to the document repository, superseding the prior version, and notify system administrators of any procedural changes. — Expected result: new version live, prior version archived (not deleted), administrators notified. — Capture: both version files/locations and the notification record. — Stop/continue: continue.
7. File the signed approval record and updated CP in the repository location specified in the Task Index with the ISSM's name and approval date. — Expected result: complete, auditable cycle package. — Capture: the filed evidence package. — Stop/continue: cycle complete.
