## 5. Procedure

**Pattern C — Update / Patch / Signature Refresh** (assignment from `runbooks/Privileged-Users.md`)

1. Pull the current cryptographic key inventory (PKI certificates, VPN pre-shared keys/IPsec keys, BitLocker recovery keys, disk/data encryption keys) from the key management log in the GRC/documentation repository. — Expected result: current, complete key inventory in hand. — Capture: the inventory export, with pull date. — Stop/continue: continue.
2. Identify all keys approaching or past their scheduled rotation/expiration date per the organization's key management plan. — Expected result: a list of due/overdue keys and certificates (may be empty). — Capture: the gap list. — Stop/continue: if no keys are due, skip to step 5.
3. Generate/rotate expiring keys and certificates using the applicable mechanism — e.g., PKI reissuance for certificates, an IPsec policy update reviewed/confirmed via `Get-NetIPsecRule`/the NetSecurity PowerShell module ([Microsoft Learn — Windows Defender Firewall command-line management](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure-with-command-line)), or `manage-bde`-driven recovery-key rotation for BitLocker volumes, then confirmed via `Get-BitLockerVolume` ([Microsoft Learn — BitLocker Management](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/operations-guide)) — and confirm the corresponding cryptographic protection configuration (e.g., approved FIPS-validated algorithms) remains unchanged. — Expected result: every due/overdue key or certificate rotated, with FIPS-validated algorithm configuration unchanged. — Capture: rotation confirmation output (e.g., `Get-BitLockerVolume` post-rotation status, PKI reissuance record). — Stop/continue: if a rotation requires an approved maintenance window not yet available, stop and document the compensating control/interim risk acceptance per `execution-plan/templates/VARIANCE-RISK-ACCEPTANCE-TEMPLATE.md` rather than leaving the gap silently open.
4. Securely retire and destroy or archive superseded keys per the key management plan's disposal procedures. — Expected result: every superseded key disposed of per the documented procedure. — Capture: disposal record. — Stop/continue: continue.
5. Update the key inventory log with new key identifiers, issuance dates, and expiration dates. — Expected result: inventory log reflects the current cycle's rotations. — Capture: the updated inventory log. — Stop/continue: continue.
6. Route the updated key inventory to the ISSM/ISSO for review. — Expected result: documented review/acceptance. — Capture: the review record. — Stop/continue: continue.
7. File the updated key inventory and rotation record in the repository location specified in the Task Index with the System Administrator's name and date. — Expected result: cycle record filed. — Capture: the filed inventory and rotation record. — Stop/continue: cycle complete.
