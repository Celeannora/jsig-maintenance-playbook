## 4. Safety / Handling Precautions

This task has two distinct halves with very different risk profiles. Identifying stale/inactive computer and user objects (the companion script, Section 5.1, and the equivalent manual queries, Section 5.2) is entirely **read-only** — it never disables, moves, or deletes any object, and carries no operational risk on its own. Actually acting on the resulting candidate list (disabling an account, moving it to a quarantine OU, or eventually deleting it) is a **separate, deliberate change-control action** that must never be performed as an automatic or unattended step of this cycle. Stale-object heuristics have known false positives — a laptop that was powered off during an extended trip, a seasonal or contractor account that is intentionally dormant between engagements, or a service account whose activity does not update `lastLogonTimestamp` the way a normal interactive user account does — so every candidate must be reviewed by a human, and where practical cross-checked with the account owner or their manager, before any disable/delete action. Never bulk-delete based solely on this report. If using the companion PowerShell script, review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT (Active Directory Domain Services and Lightweight Directory Services Tools) installed, and an account permitted to read computer/user object attributes across the domain (a standard authenticated domain account can read these attributes by default; no elevated rights are required for the read-only identification steps below).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a DC itself, open a PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-008.ps1`](../scripts/MRC-OPS-008.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-008.ps1
   ```
   — Expected result: the script queries the current domain for enabled computer objects whose password has not changed in more than 90 days (default `-ComputerInactiveDays`), and enabled user objects with no recorded logon activity (via `lastLogonTimestamp`) in more than 90 days (default `-UserInactiveDays`). — Capture: the script writes a timestamped candidate report to `.\reports\MRC-OPS-008_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it to a shared evidence location. — Stop/continue: if the script errors before producing any report (e.g., the ActiveDirectory module is not installed), fall back to the manual path in Section 5.2 and log the tooling gap as a routine finding.
4. Adjust thresholds if the organization's local policy differs from the 90-day default, e.g.:
   ```powershell
   .\MRC-OPS-008.ps1 -ComputerInactiveDays 60 -UserInactiveDays 120
   ```
   — Expected result: candidate lists reflect the organization's own inactivity policy. — Capture: note which thresholds were used in this cycle's evidence, since they affect what appears (or does not appear) on the list. — Stop/continue: continue.
5. Open the report file. It lists every stale computer and user candidate with its distinguished name and the attribute that triggered inclusion (`PasswordLastSet` for computers, `LastLogonTimestamp`/`whenCreated` for users). — Expected result: either an empty candidate list (nothing to review this cycle) or a named list of candidates. — Capture: the full report filed as this cycle's evidence. — Stop/continue: proceed to step 6 for every non-empty candidate list.
6. For each candidate, perform a human review before taking any action: confirm the object is not a known exception (service account, seasonal/contractor account, long-term-leave user, a machine account for hardware in cold storage, etc.) — check with the object owner, their manager, or the local asset inventory if ownership is unclear. — Expected result: each candidate is classified as "confirmed stale — proceed to disable per local change-control" or "known exception — document and exclude from future reports/exclusion list." — Capture: the review decision and rationale per candidate, added to the evidence package. — Stop/continue: only disable/move/delete a confirmed-stale object via the organization's standard change-control process — never as part of this MRC cycle directly.

### 5.2 Manual path (fallback / spot-check verification)

1. On a DC or RSAT-enabled workstation, open PowerShell and query stale computer objects:
   ```powershell
   $cutoff = (Get-Date).AddDays(-90)
   Get-ADComputer -Filter { Enabled -eq $true -and PasswordLastSet -lt $cutoff } -Properties PasswordLastSet, OperatingSystem |
       Select-Object DistinguishedName, PasswordLastSet, OperatingSystem
   ```
   — Expected result: a list of enabled computer objects whose password has not changed in over 90 days. — Capture: the returned list (copy/export to CSV via `Export-Csv`). — Stop/continue: continue.
2. Query stale user objects:
   ```powershell
   $cutoff = (Get-Date).AddDays(-90)
   Get-ADUser -Filter { Enabled -eq $true } -Properties LastLogonTimestamp, whenCreated |
       Where-Object {
           $lastLogon = if ($_.LastLogonTimestamp) { [datetime]::FromFileTime($_.LastLogonTimestamp) } else { $null }
           (-not $lastLogon -and $_.whenCreated -lt $cutoff) -or ($lastLogon -and $lastLogon -lt $cutoff)
       } | Select-Object DistinguishedName, @{N='LastLogon';E={ if ($_.LastLogonTimestamp) { [datetime]::FromFileTime($_.LastLogonTimestamp) } else { 'never recorded' } }}, whenCreated
   ```
   — Expected result: a list of enabled user objects with no recorded logon (or, for objects never logged in, an old creation date) beyond 90 days. — Capture: the returned list. — Stop/continue: continue. Note `lastLogonTimestamp` is a domain-wide-replicated approximation (accurate to within the domain's `msDS-LogonTimeSyncInterval`, typically 9–14 days by default) — acceptable precision for a monthly sweep, but do not rely on it for same-day precision.
3. Review each candidate per the guidance in Section 5.1 step 6 before any disable/delete action. — Expected result: reviewed, classified candidate list. — Capture: review notes filed alongside the raw query output. — Stop/continue: this cycle's data collection is complete once every candidate has a documented review decision.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Situation | Typical meaning | Immediate action |
|---|---|---|
| A candidate is a known service account or scheduled-task account | Not a real stale object — activity signals for service accounts (no interactive logon) often look identical to a genuinely stale account | Document as a known exception; add to a local exclusion list for future cycles rather than re-flagging every month |
| A candidate is a user confirmed to have left the organization (per HR/offboarding record) | A legitimate stale object that was missed by the offboarding process | **Escalate as a process gap** — offboarding should disable an account same-day, not leave it for this monthly sweep to catch; also route to whoever owns the offboarding checklist |
| A large, unexpected spike in stale-computer candidates versus prior cycles | Could indicate a fleet retirement/refresh event, or could indicate a broader problem (e.g., a GPO or radius/NAC issue preventing normal password rotation) | Cross-check against IT asset management records; if unexplained, escalate to the System Administrator's lead for investigation |
| A candidate is a disabled trust account, `krbtgt`, or other built-in system account inadvertently matched | Query/exclusion list gap — built-in accounts should be excluded from the review scope | Refine the script's exclusion logic locally; do not action the account |

This table reflects general practice for the assumed Windows Server/AD baseline and is not exhaustive. Use organizational context and account-owner confirmation to judge each candidate on its own merits.
