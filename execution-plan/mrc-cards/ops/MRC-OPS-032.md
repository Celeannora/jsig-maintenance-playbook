## 4. Safety / Handling Precautions

This is a read-only verification task. The companion script (Section 5.1) never creates, modifies, deactivates, or deletes any scope, reservation, or lease, and never changes DHCP server configuration — it only calls `Get-DhcpServerv4Scope` and `Get-DhcpServerv4ScopeStatistics`. Do not use a finding from this task as justification to resize a scope, add exclusions, or shorten lease durations during the review itself — scope-sizing changes are separate, deliberate change-management actions since they affect every client currently leasing from that scope and should follow normal network-change procedures. Note that a scope reporting a `State` other than `Active` is flagged informationally by the script, not as a failure — an intentionally deactivated scope is a design decision, not a health issue, but is worth confirming was intentional.

## 5. Procedure

This card assumes network access to the target DHCP server and an account with read access to the DHCP Server service (typically membership in the local `DHCP Users` or equivalent read-only group, or Domain Admins/DHCP Administrators for full access).

### 5.1 Automated path (recommended)

1. On a Windows PowerShell host with the `DhcpServer` module available (installed with the DHCP Server role, or the DHCP Server Tools RSAT feature) and network access to the target DHCP server, obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-032.ps1`](../scripts/MRC-OPS-032.ps1) from this repository.
2. Run:
   ```powershell
   .\MRC-OPS-032.ps1 -DhcpServer dhcp01.example.mil -ScopeUtilizationWarnPercent 85
   ```
   — Expected result: the script enumerates configured IPv4 scopes via `Get-DhcpServerv4Scope`, reports (informationally) any scope whose `State` is not `Active`, and for each Active scope pulls utilization via `Get-DhcpServerv4ScopeStatistics`, flagging Warning if `PercentageInUse` meets or exceeds `-ScopeUtilizationWarnPercent` (default 85). **It never creates, modifies, deactivates, or deletes any scope, reservation, or lease.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-032_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script cannot connect (commonly a firewall/RPC issue or an account lacking DHCP read rights), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
3. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every check passed. `1` = any check returned Warning or could not be queried). — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 4.
4. Open the report file's `SUMMARY` table and locate every row with `Result = Warning` or `Fail`. — Expected result: either a clean cycle (file the report and close) or an identified near-exhausted-scope issue needing follow-up. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any Warning/Fail, proceed to Section 5.3 for triage.

### 5.2 Manual path (fallback / spot-check verification)

1. On the DHCP server, open the **DHCP** console (`dhcpmgmt.msc`), expand the server node and **IPv4**, and review the list of configured scopes. — Expected result: every expected scope is present and shows the intended **Status** (Active, unless intentionally deactivated). — Capture: a screenshot of the scope list. — Stop/continue: an unexpectedly deactivated scope, or a missing expected scope, is a finding worth confirming with the network team.
2. For each Active scope, right-click and select the scope's statistics, or view the columns in the console, to check **Percentage of scope in use**. — Expected result: utilization comfortably below the organization's warning threshold (this card's default is 85%). — Capture: the utilization percentage for each scope. — Stop/continue: any scope at or above the threshold is a finding — clients may soon fail to obtain a lease.
3. Cross-reference against the prior cycle's report (if available) to see whether any scope's utilization trend is climbing steadily toward exhaustion. — Expected result: stable utilization, or a known/expected seasonal pattern. — Capture: note the trend in this cycle's findings. — Stop/continue: a scope climbing toward exhaustion over multiple consecutive weekly cycles should be escalated for a capacity/resize review even before it crosses the threshold outright.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Scope `PercentageInUse` at or above threshold | Address pool sized too small for current client population, or lease duration set too long relative to churn | Review lease duration and exclusion ranges before assuming the scope needs to be resized outright — shortening an overly long lease duration can reclaim addresses from stale/offline clients faster |
| Scope reports `State` other than `Active` unexpectedly | Scope was deactivated intentionally (decommissioned VLAN/segment) or accidentally during a change | Confirm with the network team whether deactivation was intentional; an unintentional deactivation will cause every client on that segment to fail DHCP |
| Utilization climbing steadily across multiple consecutive weekly cycles | Organic growth in device count on that segment (e.g. new VLAN onboarding, expanding wireless population) outpacing scope sizing | Escalate for a proactive capacity/resize review rather than waiting for the scope to cross the warning threshold |
| Script cannot query statistics for a specific scope while others succeed | Scope may be in a transitional state, or an RPC/permissions issue is specific to that scope's server-side object | Retry the query for that scope specifically before assuming a server-wide DHCP service issue |

This table reflects general practice for the assumed Windows Server DHCP Server role baseline and is not exhaustive.
