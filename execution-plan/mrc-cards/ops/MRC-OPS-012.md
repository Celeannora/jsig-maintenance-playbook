## 4. Safety / Handling Precautions

**This is the single most important safety note across all MRC-OPS cards produced to date: a full `ntdsutil` "semantic database analysis" or "integrity" check requires either stopping the NTDS service or rebooting the domain controller into Directory Services Restore Mode (DSRM), and can take from minutes to several hours depending on database size.** During that window the DC cannot authenticate users, issue Kerberos tickets, or replicate — it is effectively offline for AD purposes. This is a **planned, outage-window activity requiring explicit change-control approval**, never a routine unattended quarterly script. The companion automation script for this card (Section 5.1) deliberately does **not** run `ntdsutil` integrity checks — it only reads file size, volume free space, and scans the event log for ESE/JET engine errors, none of which require taking the database offline. The `ntdsutil`-based deep integrity check is documented in Section 5.2 as a clearly separated, explicitly-scheduled procedure — do not run it as part of a routine quarterly cycle without first securing a maintenance window and stakeholder approval, and never run it against the only reachable DC for a site without first confirming another DC can serve that site's authentication traffic during the outage.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation able to query file size and registry values remotely, and an account with local read access on each target DC for the routine review portion (Section 5.1/5.2 steps 1–2). The `ntdsutil` deep-analysis portion (Section 5.2 step 3) requires local Administrator rights on the DC and, for the DSRM-based variant, the DSRM local administrator credentials.

### 5.1 Automated path (recommended) — routine, non-disruptive review only

1. On a domain-joined management workstation or a DC itself, open a PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-012.ps1`](../scripts/MRC-OPS-012.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-012.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain (requires the ActiveDirectory PowerShell module; falls back to the local host if unavailable), reads the `ntds.dit` file size and its volume's free-space percentage (Warning below 15% free by default), and scans the Application/Directory Service logs for ESE/JET (`ESENT` provider) Critical/Error events in the last 90 days by default (Fail on any match). **It never stops a service or runs `ntdsutil`.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-012_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors before producing any report, fall back to the manual path in Section 5.2 (steps 1–2 only) for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = free space and ESE/JET checks clean on every target; `1` = low free space, an ESE/JET error found, or an unreachable target). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of low-free-space or ESE/JET-error findings per DC. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3. An ESE/JET error finding (`Fail`) warrants considering the deep-analysis procedure in Section 5.2 step 3 — but only after securing a maintenance window, per the Safety section above.

### 5.2 Manual path (fallback / spot-check verification, plus the separate deep-analysis procedure)

1. On each target DC, open PowerShell and check the `ntds.dit` file size and volume free space:
   ```powershell
   $ntdsPath = (Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Services\NTDS\Parameters' -Name 'DSA Database file').'DSA Database file'
   $file = Get-Item -LiteralPath $ntdsPath
   $vol = ($ntdsPath -split ':')[0]
   Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DeviceID='$vol`:'" |
       Select-Object DeviceID, @{N='NtdsSizeGB';E={[math]::Round($file.Length/1GB,2)}}, @{N='PercentFree';E={[math]::Round(($_.FreeSpace/$_.Size)*100,1)}}
   ```
   — Expected result: the current `ntds.dit` size and the free-space percentage on the volume hosting it. — Capture: the returned values. — Stop/continue: continue.
2. Check for ESE/JET database engine errors in the last 90 days:
   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName='Application','Directory Service'; ProviderName='ESENT'; Level=1,2; StartTime=(Get-Date).AddDays(-90) } |
       Select-Object TimeCreated, Id, LevelDisplayName, Message
   ```
   — Expected result: an empty list (no ESE/JET errors) or a list of specific error events for review. — Capture: the returned list. — Stop/continue: if this list is non-empty, or if free space from step 1 is below the organization's threshold, consider step 3 below — but only after securing a maintenance window.
3. **(Separate, explicitly-scheduled procedure — requires an approved maintenance window, never run as part of a routine cycle.)** To run a full offline integrity check: stop the NTDS service (or boot the DC into DSRM for a more thorough check that also validates the SYSVOL-related database), then run:
   ```
   ntdsutil
   activate instance ntds
   files
   integrity
   quit
   quit
   ```
   followed by, if `integrity` reports problems, a semantic database analysis (`semantic database analysis`, then `go` — add `go fixup` only under guidance from Microsoft support or a very experienced AD administrator, since `fixup` can itself alter the database). Restart the NTDS service (or reboot out of DSRM) when complete. — Expected result: an integrity report indicating whether the database's physical structure and internal AD semantics are consistent. — Capture: the full `ntdsutil` session transcript, filed as evidence for this specific scheduled procedure (tracked separately from the routine quarterly cycle's evidence). — Stop/continue: any problem reported by `integrity` or `semantic database analysis` is a significant finding — escalate immediately per Section 5.3 and do not proceed with `fixup` without expert guidance.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Volume free space below the Warning threshold (default <15%) | `ntds.dit` can grow unexpectedly (bulk imports, replication/tombstone buildup); AD can fail unpredictably if the volume fills | Log as a routine finding; trend growth across quarters; escalate if trending toward exhaustion before the next quarterly cycle |
| One or more ESENT Critical/Error events found in the lookback window | Indicates a database engine-level problem — could range from a transient disk I/O hiccup to actual corruption | **Escalate for review**; do not ignore even a single event. Depending on severity, this may justify scheduling the Section 5.2 step 3 deep-analysis procedure sooner than the next routine quarter |
| `ntds.dit` size growing much faster than user/computer object count growth would explain | Could indicate excessive logging, an unresolved replication/tombstone issue, or an application writing excessive data into AD-integrated storage | Log as a routine finding; investigate the growth driver before it becomes a free-space emergency |
| `integrity` or `semantic database analysis` (Section 5.2 step 3) reports actual problems | A confirmed database health issue requiring expert remediation | **Escalate immediately** to the most experienced available AD administrator or Microsoft support; do not run `fixup` without that guidance |

This table reflects general practice for the assumed Windows Server/AD baseline and is not exhaustive. Any finding from the offline `ntdsutil` procedure should be treated as high-severity given the operational cost of running that check in the first place.
