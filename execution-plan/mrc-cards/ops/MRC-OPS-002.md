## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. `dcdiag.exe` (run without `/fix` or any repair switch, as specified below) is read-only against Active Directory, DNS, and replication state — it does not modify configuration. Running it against a production domain controller does not require a change-control window on its own, but if a failure is found and remediation is attempted afterward, that remediation follows the organization's standard change-control/maintenance-window process. Do not export diagnostic output (which can include hostnames, site topology, and service-account names) to unauthorized media or systems. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT (Active Directory Domain Services and Lightweight Directory Tools) installed, and an account permitted to run `dcdiag.exe` against the domain's DCs (local Administrators on the target DC, or an equivalent delegated read-level account per organizational RBAC — `dcdiag` itself does not require Domain Admin rights to run its default read-only test suite).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or the target DC itself, open an elevated PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-002.ps1`](../scripts/MRC-OPS-002.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-002.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain via `Get-ADDomainController -Filter *` (requires the ActiveDirectory PowerShell module) and runs a verbose DCDIAG (`dcdiag /s:<DC> /v`) against each one in turn. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-002_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere, e.g. a shared evidence drive). — Stop/continue: if the script errors before producing any report (e.g., the ActiveDirectory module is not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line (`DCDIAG check complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = every test on every DC passed; `1` = at least one failure, warning, or unreachable target). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section (near the bottom, above the raw per-DC `dcdiag` output) lists every test result as a table with `Target`, `CheckName`, and `Result` columns. Locate every row where `Result = Fail`. — Expected result: either zero `Fail` rows (clean cycle, file the report and close the cycle) or an identified list of failing tests per DC. — Capture: the full report file (summary table + raw output) filed as this cycle's evidence. — Stop/continue: for any `Fail` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely.
6. Optional deeper check: to run the comprehensive enterprise-wide test set (adds non-default tests such as `DcPromoReadiness`, which takes noticeably longer), run `.\MRC-OPS-002.ps1 -Comprehensive` instead of the default invocation. This is not required every week — use it if a prior cycle surfaced ambiguous results, or per local policy for a periodic deep check.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify every domain controller in scope: on a DC or RSAT-enabled workstation, open PowerShell and run:
   ```powershell
   Get-ADDomainController -Filter * | Select-Object HostName
   ```
   — Expected result: the full list of DC hostnames in the domain. — Capture: the returned list. — Stop/continue: continue.
2. For each DC in the list, open an elevated Command Prompt or PowerShell session — either locally on that DC, or remotely from another DC/workstation using the `/s:` switch — and run:
   ```
   dcdiag /s:<DCName> /v > DCDIAG_<DCName>_<yyyy-MM-dd>.txt
   ```
   (omit `/s:<DCName>` if running locally on the DC itself). — Expected result: `dcdiag` runs through its default test suite — `Connectivity`, `Advertising`, `FrsEvent`, `DFSREvent`, `SysVolCheck`, `KccEvent`, `NCSecDesc`, `NetLogons`, `ObjectsReplicated`, `Replications`, `RidManager`, `Services`, `SystemLog`, `VerifyReferences`, plus partition-level tests (e.g. `CheckSDRefDom`) and enterprise-level tests (e.g. `LocatorCheck`, `Intersite`) — and prints a `passed test` or `failed test` line for each, redirected into the named text file. — Capture: the redirected output file, one per DC, added to the evidence package. — Stop/continue: continue to the next DC regardless of this DC's result; do not stop the cycle mid-way on a single DC's failure.
3. Open each saved output file and note every line containing the text `failed test` or `Warning:`. — Expected result: a complete list of failing/warning lines per DC (may be empty for a clean DC). — Capture: the annotated list (highlight or copy the matching lines into the cycle's findings notes). — Stop/continue: check every failing test name against the triage table in Section 5.3 to decide escalate-now vs. log-routine.
4. If a specific test's `/v` output is ambiguous, re-run just that test in isolation for a clearer read:
   ```
   dcdiag /s:<DCName> /test:<TestName> /v
   ```
   for example `dcdiag /s:DC01 /test:Replications /v`. — Expected result: focused output for that one test only. — Capture: append this output to the same DC's evidence file. — Stop/continue: continue.
5. File all per-DC output files (from either path) in the cycle's evidence location (Section 6). — Expected result: a complete file set covering every DC in scope for this cycle. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Failed test | Typical meaning | Immediate action |
|---|---|---|
| `Replications` | AD replication is failing or stalled between DCs — directly threatens directory consistency across the domain | **Escalate immediately** per Section 6; do not wait for the next cycle |
| `NetLogons` | Netlogon share or service issue — can block Group Policy processing and user logon | **Escalate immediately** |
| `Advertising` | The DC is not advertising itself as available (commonly a DNS SRV-record or service-startup issue) | **Escalate immediately** |
| `KccEvent` | Knowledge Consistency Checker errors in the Directory Service event log — a replication-topology generation problem | **Escalate immediately** |
| `SysVolCheck` | SYSVOL share is missing or misconfigured on this DC — Group Policy objects may not apply domain-wide | **Escalate immediately** |
| `Services` | A required Active Directory–related service is stopped on the DC | **Escalate immediately** |
| `FrsEvent` / `DFSREvent` | Legacy FRS or DFSR replication event-log errors — often lower urgency, but still track (see also [MRC-OPS-004](MRC-OPS-004.md), the dedicated SYSVOL/DFSR check) | Log as a routine finding; monitor next cycle |
| `SystemLog` | Unrelated system-level errors/warnings surfaced in the System event log during the diagnostic window | Log as a routine finding; review the System log directly for root cause |

This table reflects general `dcdiag` test semantics for the assumed Windows Server/AD baseline and is not exhaustive. For a failure not listed here, use the plain-language context DCDIAG itself prints under `/v` for that test, together with organizational AD-support experience, to judge urgency.
