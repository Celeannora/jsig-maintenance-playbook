## 4. Safety / Handling Precautions

This is a read-only reporting task. The companion script (Section 5.1) never creates, modifies, enables, disables, or removes a transport rule or connector — it only collects current configuration and flags two specific known-risky patterns (an enabled, undocumented transport rule; a Receive connector combining anonymous submission with no TLS requirement). **This script's clean exit code does not mean the review is complete.** Transport rule and connector review has an irreducible human-judgment component this card cannot automate away: whether a given rule or connector is still needed for a current, legitimate business purpose is a decision only a human reviewer familiar with the organization's mail-flow requirements can make. Removing or disabling a connector or rule that turns out to still be needed can silently break mail flow for a specific business partner or workflow — always confirm with the rule/connector's original requester or a change record before disabling anything found during this review, and make any such change through the organization's standard change-control process, never directly during the review itself.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to transport configuration for the organization.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-019.ps1`](../scripts/MRC-OPS-019.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-019.ps1
   ```
   — Expected result: the script reads every transport rule, Receive connector, and Send connector in the organization, flagging an enabled transport rule with no `Comments`/description as Warning and a Receive connector that allows anonymous submission without requiring TLS as Warning. **It never modifies any rule or connector.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-019_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = no undocumented enabled rule and no anonymous-without-TLS Receive connector found; `1` = one or both patterns found, or the organization's rules/connectors could not be queried). — Capture: console output. — Stop/continue: regardless of exit code, proceed to step 5 — this task's human-review component applies to every cycle, not only ones with a `1` exit code.
5. Open the full report and, for every transport rule and connector listed (not only flagged ones), confirm with the responsible business owner or a prior change record that it is still needed and correctly configured for current requirements. — Expected result: every rule/connector accounted for, with any no-longer-needed item identified for a separate change-controlled removal. — Capture: the full report, annotated with this cycle's human-review conclusions, filed as this cycle's evidence.

### 5.2 Manual path (fallback / spot-check verification)

1. In Exchange Management Shell, list transport rules:
   ```powershell
   Get-TransportRule | Select-Object Name, Enabled, Priority, Comments
   ```
   — Expected result: every rule with its enabled state and description. — Capture: the returned table. — Stop/continue: an enabled rule with no `Comments` is a finding; continue reviewing every rule's continued relevance regardless.
2. List Receive connectors and their security-relevant settings:
   ```powershell
   Get-ReceiveConnector | Select-Object Name, Enabled, PermissionGroups, AuthMechanism, TlsDomainCapabilities
   ```
   — Expected result: every connector's permission and authentication configuration. — Capture: the returned table. — Stop/continue: a connector with `PermissionGroups` including `AnonymousUsers` and no TLS requirement is a finding requiring immediate review.
3. List Send connectors:
   ```powershell
   Get-SendConnector | Select-Object Name, Enabled, AddressSpaces, TlsAuthLevel
   ```
   — Expected result: every outbound connector's address space and TLS posture. — Capture: the returned table. — Stop/continue: continue to step 4 regardless of findings.
4. For every rule/connector listed in steps 1–3, confirm continued business need per Section 4's guidance before considering any change.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Enabled transport rule with no description | Rule was created ad hoc without documenting its purpose, making future review difficult | Log as a finding; require the rule's owner to add a `Comments` description at minimum, even if the rule itself is otherwise fine |
| Receive connector allows anonymous submission with no TLS requirement | Common accidental open-relay or unencrypted-submission misconfiguration, sometimes left from an application-relay connector that was never hardened | Escalate for immediate review — verify whether anonymous relay is actually required (e.g. for a scanner/printer) and if so, restrict it by IP and add a TLS requirement rather than leaving it open broadly |
| Disabled transport rule or connector found | Likely a temporary change that was never followed up on, or a deliberately retired configuration left in place | Log as informational; confirm with the rule/connector's owner whether it should be removed entirely or is intentionally kept disabled for reference |
| Send connector with an overly broad `AddressSpaces` (e.g. `*`) alongside a weak `TlsAuthLevel` | Outbound mail to arbitrary domains may not be encrypted in transit | Review whether `TlsAuthLevel` should be tightened for this connector's actual use case |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
