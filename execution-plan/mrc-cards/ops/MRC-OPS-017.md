## 4. Safety / Handling Precautions

This is a read-only reporting task. The companion script (Section 5.1) never deletes a transaction log file, forces log truncation, or changes the circular logging setting on any database. **Never manually delete `.log` files from an Exchange database's log folder to "fix" a full volume** — doing so can make the database unable to recover from an unexpected shutdown and is one of the most common causes of unrecoverable Exchange data loss in the field. Truncation happens automatically once every database copy (for DAG members) or the last successful backup (for standalone databases) has consumed the log; if truncation is not occurring, the correct remediation is to fix whatever is preventing that consumption (a stalled passive copy, per [MRC-OPS-014](MRC-OPS-014.md), or a failed/missing backup job) — never to delete the logs directly. Likewise, never enable circular logging on a DAG member database as a quick fix for a full log volume without first understanding that circular logging is incompatible with point-in-time recovery beyond the last full backup and can complicate continuous replication.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to mailbox database information, plus the ability to query CIM/WMI volume information and enumerate files in the log folder on each database's hosting server (local admin or an equivalent remote-management right).

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-017.ps1`](../scripts/MRC-OPS-017.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-017.ps1
   ```
   — Expected result: for every mailbox database, the script checks free space on the volume(s) hosting the database and log files (Fail below 10% free by default, Warning below 20%), confirms circular logging is disabled on every DAG member database (Fail if enabled), and reports the transaction log file count in each database's log folder as a diagnostic data point (Warning above 5,000 files by default). **It never deletes a log file, forces truncation, or changes any database setting.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-017_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell, or without remote access to a database's hosting server), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every volume above the Critical free-space threshold, circular logging disabled on every DAG member, and no database over the log-count threshold; `1` = any of those conditions fails, or a database could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of disk-space, circular-logging, or log-count findings. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3; given the Daily frequency, escalate any low-free-space Fail the same day.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify each database's file and log paths, and their hosting volumes:
   ```powershell
   Get-MailboxDatabase -Status | Select-Object Name, Server, EdbFilePath, LogFolderPath
   ```
   — Expected result: the on-disk path for every database's `.edb` file and log folder. — Capture: the returned table. — Stop/continue: continue.
2. Check free space on each of those volumes (on the relevant server):
   ```powershell
   Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DeviceID='<DriveLetter>:'" |
       Select-Object DeviceID, @{N='PercentFree';E={[math]::Round(($_.FreeSpace/$_.Size)*100,1)}}
   ```
   — Expected result: free-space percentage for each database/log volume. — Capture: the returned values. — Stop/continue: below 20% free is a finding; below 10% is an urgent finding.
3. Confirm circular logging is disabled on any database that is a DAG member:
   ```powershell
   Get-MailboxDatabase -Status | Select-Object Name, MasterServerOrAvailabilityGroup, CircularLoggingEnabled
   ```
   — Expected result: `CircularLoggingEnabled = False` for every database with a non-empty `MasterServerOrAvailabilityGroup` (i.e., a DAG member). — Capture: the returned table. — Stop/continue: `CircularLoggingEnabled = True` on a DAG member is a finding — escalate, since it indicates either a deliberate but risky configuration choice or an accidental change.
4. Count log files in a database's log folder as a truncation indicator:
   ```powershell
   (Get-ChildItem -Path '<LogFolderPath>' -Filter '*.log').Count
   ```
   — Expected result: a log file count consistent with recent history for that database (a large jump since the last check is the signal to watch for, more than the absolute number). — Capture: the count and a brief comparison to the prior cycle's count if available. — Stop/continue: a large, growing count is a finding — cross-reference [MRC-OPS-014](MRC-OPS-014.md) for a stalled DAG copy, or verify the database's backup job completed successfully, before escalating.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Volume free space below the Warning threshold (default <20%) | Log or database growth is consuming available space faster than it is being reclaimed | Log as a finding; monitor trend; escalate same day if below the Critical threshold (default <10%) given the Daily frequency |
| Circular logging enabled on a DAG member database | Either a deliberate but risky configuration choice, or an accidental change — breaks the ability to replay logs to passive copies for anything beyond the current state | **Escalate**; confirm whether this was an intentional, documented change; if not, treat as a configuration-drift finding |
| Growing transaction log file count without a corresponding backup or DAG-replay explanation | Logs are not being truncated — the classic precursor to a volume-full outage | Cross-reference [MRC-OPS-014](MRC-OPS-014.md) for a stalled passive copy, and confirm the database's backup job completed successfully; escalate if neither explains the growth |
| Volume free space and log count both stable/healthy, but the log folder contains unusually old `.log` files | May indicate a long-stalled passive copy that has not caught up in a long time, or a backup job that has not run successfully in a long time | Escalate for investigation even though the routine thresholds were not tripped, since old un-truncated logs are still a latent risk |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
