## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. The steps in this card are read-only queries of DNS Server configuration and zone data — they do not enable/disable scavenging, change zone aging settings, or force a scavenging pass (`Start-DnsServerScavenging` / the console's "Scavenge Stale Resource Records" action). Any change to scavenging or aging configuration, if a finding calls for it, is a separate, deliberate, documented change-control action taken outside this card's routine cadence, since scavenging changes can affect DNS record lifecycle domain-wide. Do not export zone data (which can reveal internal hostnames and network topology) to unauthorized media or systems. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server DNS server (typically a domain controller running the DNS Server role in this baseline), or a management workstation with RSAT: DNS Server Tools installed, and an account permitted to query DNS Server configuration (local Administrators on the target server, or an equivalent delegated read-level account per organizational RBAC).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a DNS server itself, open an elevated PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-003.ps1`](../scripts/MRC-OPS-003.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-003.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain via `Get-ADDomainController -Filter *` (requires the ActiveDirectory PowerShell module) and, for each one, checks the DNS Server service state, server-wide scavenging configuration, and per-zone aging settings for every non-auto-created zone. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-003_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere). — Stop/continue: if the script errors before producing any report (e.g., the DnsServer or ActiveDirectory module is not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line (`DNS health/scavenging check complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = DNS service running everywhere with no stuck-scavenging warnings; `1` = a stopped service, a likely-stuck scavenging cycle, or an unreachable target). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section lists every check as a table with `Target`, `CheckName`, and `Result` columns. Locate every row where `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of failing/warning checks per DNS server. — Capture: the full report file filed as this cycle's evidence. — Stop/continue: for any `Fail` or `Warning` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely.
6. Review the `DNS-ZoneAging` rows in the report (these are always `Pass` — they are informational, not judged pass/fail by the script) to confirm aging settings match organizational policy for each zone. — Expected result: aging enabled/disabled state and refresh/no-refresh intervals per zone match what this organization has documented as its intended configuration. — Capture: note any zone whose aging configuration appears to have drifted from documented policy. — Stop/continue: a configuration drift here is a routine finding, not an availability incident — log it for the next scheduled configuration-change discussion rather than escalating.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify every DNS server in scope. In this baseline, DNS runs on every domain controller, so:
   ```powershell
   Get-ADDomainController -Filter * | Select-Object HostName
   ```
   — Expected result: the full list of DNS server hostnames. — Capture: the returned list. — Stop/continue: continue.
2. For each DNS server, open an elevated PowerShell session and confirm the DNS Server service is running:
   ```powershell
   Get-Service -ComputerName <DNSServerName> -Name DNS
   ```
   — Expected result: `Status = Running`. — Capture: the returned status. — Stop/continue: if the service is not running, this is an immediate escalation (Section 5.3) — do not proceed with the remaining checks on that server until it is addressed.
3. Check server-wide scavenging configuration:
   ```powershell
   Get-DnsServerScavenging -ComputerName <DNSServerName>
   ```
   — Expected result: a `ScavengingState`, `ScavengingInterval`, and `LastScavengeTime` value. — Capture: the returned object. — Stop/continue: if `ScavengingState` is `True` but `LastScavengeTime` is empty/never, or is older than roughly 2x the `ScavengingInterval`, treat this as a possible stuck scavenging cycle (Section 5.3).
4. List the non-auto-created zones and check each one's aging configuration:
   ```powershell
   Get-DnsServerZone -ComputerName <DNSServerName> | Where-Object { -not $_.IsAutoCreated }
   Get-DnsServerZoneAging -ComputerName <DNSServerName> -Name <ZoneName>
   ```
   — Expected result: aging settings for every zone in scope. — Capture: the returned objects per zone. — Stop/continue: continue; aging configuration is informational per step 5.1.6 above, not a pass/fail check.
5. File the console output/screenshots from all steps in the cycle's evidence location (Section 6). — Expected result: a complete file set covering every DNS server in scope for this cycle. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| DNS Server service stopped | Name resolution for the domain is degraded or unavailable from this server, which can cascade into logon, replication ([MRC-OPS-001](MRC-OPS-001.md)), and FSMO discovery ([MRC-OPS-005](MRC-OPS-005.md)) failures | **Escalate immediately** per Section 6; do not wait for the next cycle |
| Scavenging enabled but never run, or last run far past its interval | Stale DNS records (from decommissioned hosts, renamed computers, etc.) are not being cleaned up, risking IP-address reuse conflicts and inflated zone size over time | Escalate as a priority finding if scavenging has clearly stalled (not merely disabled by policy); log as routine if scavenging is intentionally disabled per organizational policy |
| Zone aging configuration differs across DNS servers for the same zone (found by comparing manual-path output across servers) | Inconsistent aging settings on different name servers hosting the same AD-integrated zone can cause records to age out inconsistently | Log as a routine finding; correct via planned change control to bring all servers hosting the zone into alignment |
| A zone is missing entirely from one DNS server's zone list but present on others | Replication or zone-transfer failure for that specific zone, or the zone was never properly created on this server | **Escalate immediately** — this is a functional DNS gap, not merely a scavenging/aging issue |

This table reflects general DNS Server role semantics for the assumed Windows Server/AD-integrated DNS baseline and is not exhaustive. For a finding not listed here, use organizational AD/DNS-support experience to judge urgency.
