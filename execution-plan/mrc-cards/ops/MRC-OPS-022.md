## 4. Safety / Handling Precautions

This is a read-only monitoring task performed entirely by viewing dashboards, queries, and System Tree properties in the ePO console. Do not use this review as an opportunity to delete, move, or re-tag systems in the System Tree — those are separate, deliberate directory-management actions with their own change-control expectations, and doing so during a routine coverage check risks accidentally removing a legitimately offline-but-still-inventoried asset (e.g. a system in long-term storage) from ePO's inventory. The one interactive action this card does describe — sending a manual "Wake Up Agent" call (Section 5.1, step 5) — is itself non-destructive: it only asks an agent to check in early and does not change any policy, task, or system-tree placement.

## 5. Procedure

This card assumes an ePO console account with at least read access to Queries & Reports and the System Tree for the groups being reviewed.

### 5.1 Console path (this task's only supported path)

1. Log in to the ePO web console.
2. Navigate to **Menu → Reporting → Queries & Reports**.
3. Locate and run the built-in **`MA: Agent Communication Summary`** query (default query shipped with the McAfee Agent extension). — Expected result: a Boolean pie chart of every managed system, split by whether its agent has communicated with the ePO server within the last day (the query's default window). — Capture: a screenshot or exported copy (csv/html/xhtml, via the query's **Export Data** action) of the resulting chart and its underlying system list. — Stop/continue: drill into the "has not communicated" slice by clicking it to get the specific list of affected systems, then continue to step 4.
4. Locate and run the built-in **`Inactive Agents`** query (default query; some organizations customize its inactivity threshold — see Section 5.3 for the best-practice reference). — Expected result: the list of systems whose agent has not communicated with the ePO server for longer than the query's configured threshold (commonly 30 days by default, but confirm the threshold actually configured for this organization's copy of the query before relying on it). — Capture: export the result list (csv/html/xhtml). — Stop/continue: cross-reference this list against the Section 5.1 step 3 drill-down — a system appearing in both is a stronger candidate for immediate follow-up than one appearing in only the `Inactive Agents` list, since the latter's threshold may be looser than this task's own review cadence.
5. For any system identified as not communicating, first attempt a manual re-check rather than assuming it is truly offline: in **Menu → Systems → System Tree**, locate the system (or its containing group), select it, go to the **Group Details** (or system-level) tab, then **Actions → Wake Up Agents**, choosing **Agent wake-up call** for the target system(s). — Expected result: if the system is actually online and simply hasn't checked in yet within its normal agent-server communication interval, it typically reports back within a few minutes. — Capture: note in the report whether the wake-up call succeeded (system checked back in) or the system remained unresponsive. — Stop/continue: a system that remains unresponsive after a wake-up call attempt is a confirmed finding; a system that checks back in successfully is not.
6. Optionally, for a more targeted view than the default queries provide (e.g. scoped to a specific System Tree group, or with a custom inactivity threshold matching this task's own weekly cadence), build a custom query: **Queries & Reports → New Query → Feature Group: System Management → Result Type: Systems**, add the **Last Communication** column, apply a filter such as "has not communicated in the last 7 days," and save it under a name identifying it as this MRC's review query for reuse in future cycles. — Expected result: a repeatable, cycle-specific view tailored to this task's weekly cadence rather than relying solely on the built-in queries' own default windows. — Capture: save this custom query for reuse; export its results this cycle same as steps 3–4.

### 5.2 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| A handful of systems not communicating, scattered with no pattern | Likely normal churn (systems powered off, in transit, or decommissioned but not yet removed from ePO) | Attempt the wake-up call (step 5); if still unresponsive after this cycle and the prior cycle, escalate as a possible decommissioned/lost asset needing inventory reconciliation |
| A cluster of systems in the same System Tree group/site all stopped communicating around the same time | Possible network segment issue (firewall change, VLAN/routing change) blocking agent-to-server communication for that whole group, rather than individual endpoint problems | Escalate to network/infrastructure review rather than treating each system as an individual endpoint issue |
| A system remains unresponsive to a wake-up call across multiple consecutive weekly cycles | Agent may be stopped, uninstalled, or the system itself may be offline/decommissioned | Escalate for endpoint-level investigation (physical/remote access check) or directory cleanup if confirmed decommissioned |
| `Inactive Agents` query threshold does not match this task's weekly cadence (e.g. still at a 30-day default) | The built-in query alone will under-report findings relative to a weekly review cadence | Use the custom query from step 6 (7-day threshold) as this task's primary source of truth rather than relying on the default `Inactive Agents` query's looser window |

This table reflects general practice for the assumed ePO baseline and is not exhaustive.

### 5.3 Future automation note (not implemented this cycle)

If this organization later decides to automate this check, the two viable API-based approaches identified during this card's authoring are: (1) a PowerShell script using `Invoke-Sqlcmd` against the ePO backend SQL Server database's `EPOLeafNode` table (which stores each managed system's last agent-to-server communication timestamp) and related tables, run read-only against a reporting replica or with least-privilege read access if run against the primary database; or (2) a script calling ePO's Remote Access Web API (`core.executeQuery` and related endpoints) over HTTPS with a dedicated, least-privilege API credential. Either approach would need database connection details or API credentials supplied as script parameters (never hard-coded), and should be scoped and reviewed the same as the PowerShell scripts used elsewhere in this repository before being adopted as this card's automated path.
