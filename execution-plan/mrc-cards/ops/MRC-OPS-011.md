## 4. Safety / Handling Precautions

This task is entirely **read-only** — it queries each GPO's version metadata via `Get-GPO` and never runs `gpupdate`, edits a GPO, or forces replication. Running it against the production domain on a monthly cadence carries no operational risk and does not require a change-control window. If a version mismatch is found, the appropriate remediation depends on the root cause: if it traces to a SYSVOL/DFSR replication backlog (see [MRC-OPS-004](MRC-OPS-004.md)), the fix is to resolve that underlying replication issue, not to touch the GPO directly; if it traces to actual GPO corruption, remediation (e.g., re-editing and re-saving the GPO to force a version bump, or restoring from a known-good backup) is a deliberate change-control action, never an automatic step of this check. Never delete or re-create a GPO shown as mismatched without first confirming the root cause — deleting a production GPO by mistake can have domain-wide policy-application consequences. If using the companion PowerShell script, review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT (Group Policy Management Tools) installed, and an account with read access to Group Policy Objects in the domain (a standard authenticated domain account can read GPO metadata by default via `Get-GPO`; no elevated rights are required for this read-only check).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a DC itself, open a PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-011.ps1`](../scripts/MRC-OPS-011.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-011.ps1
   ```
   — Expected result: the script queries every GPO in the current domain via `Get-GPO -All` and compares each GPO's AD-side version (`DSVersion`) against its SYSVOL-side version (`SysvolVersion`) for both the User and Computer halves, flagging any mismatch as `Fail`. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-011_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors before producing any report (e.g., the GroupPolicy module is not installed), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every GPO's DS and SYSVOL versions match; `1` = at least one mismatch, or the domain's GPOs could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail`, noting which of the User/Computer halves is mismatched and by how much (e.g., `DS=8/SYSVOL=3` indicates SYSVOL is 5 versions behind AD for that half). — Expected result: either a clean cycle (file the report and close) or an identified list of mismatched GPOs. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any mismatch, first check [MRC-OPS-004](MRC-OPS-004.md)'s most recent SYSVOL/DFSR backlog result (or re-run that card's script) before assuming GPO corruption — a replication backlog is the far more common root cause and self-resolves once replication catches up.

### 5.2 Manual path (fallback / spot-check verification)

1. On a DC or RSAT-enabled workstation, open PowerShell and check version consistency for every GPO:
   ```powershell
   Get-GPO -All | Select-Object DisplayName, Id,
       @{N='UserDS';E={$_.User.DSVersion}}, @{N='UserSysvol';E={$_.User.SysvolVersion}},
       @{N='ComputerDS';E={$_.Computer.DSVersion}}, @{N='ComputerSysvol';E={$_.Computer.SysvolVersion}} |
       Where-Object { $_.UserDS -ne $_.UserSysvol -or $_.ComputerDS -ne $_.ComputerSysvol }
   ```
   — Expected result: an empty list (no mismatches) or a list of GPOs where the AD-side and SYSVOL-side version numbers disagree. — Capture: the returned list. — Stop/continue: for a non-empty list, continue to step 2.
2. For any mismatched GPO, use the Group Policy Management Console (GPMC) to inspect its Details tab directly (`AD Version` and `Sysvol Version` fields), which presents the same information in the GUI for cross-verification. — Expected result: confirmation of the mismatch and its magnitude. — Capture: a screenshot or note of the GPMC Details tab. — Stop/continue: continue.
3. Check the most recent SYSVOL/DFSR replication status per [MRC-OPS-004](MRC-OPS-004.md) (or run `dfsrdiag backlog` directly per that card) to determine whether the mismatch is a transient replication lag rather than actual corruption. — Expected result: either a confirmed active backlog (transient — re-check after replication catches up) or clean replication status (points toward a real GPO health problem needing investigation). — Capture: the cross-check result. — Stop/continue: this cycle's data collection is complete; escalate per Section 5.3 if warranted.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Mismatch coincides with an active SYSVOL/DFSR backlog (per MRC-OPS-004) | Transient replication lag — the GPO itself is fine, SYSVOL just hasn't caught up yet | Log as a routine finding; re-check in the next cycle (or sooner) once the backlog clears; do not touch the GPO |
| Mismatch persists across multiple monthly cycles with no active replication backlog | Possible actual GPO corruption or a stuck replication state that DFSR isn't reporting as a backlog | **Escalate immediately** for investigation — this can mean the affected policy setting is not applying consistently domain-wide |
| A GPO with `DSVersion = 0` for both User and Computer | An empty/never-edited GPO (e.g., created but not yet configured) — not itself a problem, but worth confirming it is intentional | Log as a routine finding if unexpected; no action needed if it is a known placeholder GPO |
| Very large version-number gap (e.g., differing by dozens) on a GPO that was recently and heavily edited | Could indicate the SYSVOL copy has been stuck since before a series of edits, meaning **none** of the recent edits have actually propagated | **Escalate immediately** — the live-applied policy on clients does not reflect recent changes |

This table reflects general practice for the assumed Windows Server/AD baseline and is not exhaustive. Cross-reference with MRC-OPS-004 first in every case, since replication lag is the dominant real-world cause of this symptom.
