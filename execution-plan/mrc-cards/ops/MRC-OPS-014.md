## 4. Safety / Handling Precautions

This is a read-only diagnostic task. `Test-ReplicationHealth` and `Get-MailboxDatabaseCopyStatus` never change any configuration on their own — the companion script (Section 5.1) only runs these read-only cmdlets and never triggers a database copy switchover, evicts a DAG member, or alters cluster/quorum configuration. If this check reveals a database with no healthy redundant copy, do not attempt an ad-hoc manual failover or reseed outside the organization's standard incident process — a mistimed failover of the active copy of a database with no healthy standby can itself cause an outage. Escalate per Section 5.3/6 and let a deliberate, coordinated remediation follow.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to DAG, replication-health, and database-copy status information. `Test-ReplicationHealth` should be run locally on (or via a remote session directly to) each Mailbox server that is a DAG member, since it evaluates that server's own cluster/replication service state.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-014.ps1`](../scripts/MRC-OPS-014.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-014.ps1
   ```
   — Expected result: the script auto-discovers every Database Availability Group in the organization (or use `-DagName` to target one DAG), runs `Test-ReplicationHealth` against every member server (covering cluster service, replay service, Active Manager, tasks RPC/TCP listeners, DAG membership, cluster network, and quorum, plus per-database replication checks), and cross-checks that every database has at least two healthy copies. **It never triggers a failover or changes DAG/cluster configuration.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-014_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell, or the account lacks rights on a DAG member), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every replication-health check passes on every DAG member and every database has redundant healthy copies; `1` = any check fails, redundancy is reduced, or a member could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of replication-health or redundancy findings. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3; any Fail on a production DAG member warrants same-day escalation given this is a Daily check.

### 5.2 Manual path (fallback / spot-check verification)

1. On (or via a remote session to) each DAG member server, in Exchange Management Shell, run the built-in replication health diagnostic:
   ```powershell
   Test-ReplicationHealth -Identity <ServerName>
   ```
   — Expected result: every listed `Check` row shows `Result = Passed`. — Capture: the returned table for each member server. — Stop/continue: any `Result` other than `Passed` is a finding; note the specific failed check and its `Error` detail for escalation.
2. Confirm every database has redundant healthy copies:
   ```powershell
   Get-MailboxDatabaseCopyStatus -Identity * | Group-Object DatabaseName |
       Select-Object Name, @{N='HealthyCopies';E={($_.Group | Where-Object {$_.Status -in 'Mounted','Healthy'}).Count}}, @{N='TotalCopies';E={$_.Count}}
   ```
   — Expected result: `HealthyCopies` of at least 2 for every database that is meant to have DAG redundancy. — Capture: the returned table. — Stop/continue: a database with `HealthyCopies` of 0 or 1 is a finding — cross-reference [MRC-OPS-013](MRC-OPS-013.md) for the individual copy's specific status/content-index detail before escalating.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| `Test-ReplicationHealth` check `ClusterService`/`ReplayService`/`ActiveManager` fails | The underlying Windows Failover Clustering or Exchange replication service on that member is down or unhealthy | **Escalate same day**; the affected server cannot reliably host active or passive database copies until resolved |
| `Test-ReplicationHealth` check `DatabaseAvailability` fails (e.g., high copy/replay queue length) | A specific database copy on that member has fallen behind or stopped replicating | Cross-reference [MRC-OPS-013](MRC-OPS-013.md) and [MRC-OPS-017](MRC-OPS-017.md) for that database's copy status and log/disk-space health; escalate if the queue is growing rather than catching up |
| `Test-ReplicationHealth` check `ClusterNetwork`/`QuorumGroup` fails | The failover cluster itself is degraded — could affect the DAG's ability to fail over automatically at all | **Escalate immediately**; this affects every database in the DAG, not just one |
| A database shows fewer than 2 `HealthyCopies` | Reduced or zero redundancy — the next single-server failure could cause an outage for that database | **Escalate same day** given the Daily frequency of this check; do not delay to the next cycle |

This table reflects general practice for the assumed Exchange DAG baseline and is not exhaustive.
