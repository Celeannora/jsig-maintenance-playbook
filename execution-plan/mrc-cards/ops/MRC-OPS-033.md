## 4. Safety / Handling Precautions

This is a read-only verification task. The companion script (Section 5.1) never triggers a reboot, never modifies any registry value, and never changes any WSUS/patching configuration — it only calls `Get-CimInstance`, `Test-Path`, and `Get-ItemProperty`, all of which are query-only. Do not use a finding from this task as justification to reboot a production server immediately during the review — a pending-reboot or high-uptime finding should be scheduled through this organization's normal maintenance-window process, since an unplanned reboot of a production server (especially a domain controller, database, or clustered role holder) can itself cause an outage.

## 5. Procedure

This card assumes network access to each target host and, for remote targets, an account with WinRM/PSRemoting access already granted (the script uses `Invoke-Command` for any `-ComputerName` other than the local host).

### 5.1 Automated path (recommended)

1. On a Windows PowerShell host with network/WinRM access to the target server(s), obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-033.ps1`](../scripts/MRC-OPS-033.ps1) from this repository.
2. Run:
   ```powershell
   .\MRC-OPS-033.ps1 -ComputerName dc01.example.mil -MaxUptimeDays 30
   ```
   — Expected result: the script reads `Win32_OperatingSystem.LastBootUpTime` via `Get-CimInstance` and flags Warning if uptime exceeds `-MaxUptimeDays` (default 35), then checks the three standard pending-reboot indicators (Component Based Servicing, Windows Update Auto Update, and `PendingFileRenameOperations`) and flags Warning if any are present. **It never triggers a reboot or modifies any configuration.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-033_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script cannot reach a remote target (commonly a WinRM/firewall issue or an expired credential), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
3. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every check passed. `1` = any check returned Warning or could not be queried). — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 4.
4. Open the report file's `SUMMARY` table and locate every row with `Result = Warning` or `Fail`. — Expected result: either a clean cycle (file the report and close) or an identified high-uptime/pending-reboot issue needing a scheduled maintenance window. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any Warning/Fail, proceed to Section 5.3 for triage.

### 5.2 Manual path (fallback / spot-check verification)

1. On the target server, run `(Get-Date) - (Get-CimInstance Win32_OperatingSystem).LastBootUpTime` in a PowerShell session, or check **Task Manager → Performance → Up time** in the GUI. — Expected result: uptime under the organization's threshold (this card's default is 35 days). — Capture: the uptime value. — Stop/continue: uptime at or above the threshold is a finding.
2. Check the pending-reboot registry indicators directly: `Test-Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending'`, `Test-Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired'`, and `(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager' -Name PendingFileRenameOperations -ErrorAction SilentlyContinue).PendingFileRenameOperations`. — Expected result: all three return `$false`/`$null`. — Capture: which, if any, indicators are present. — Stop/continue: any indicator present is a finding — the host needs a scheduled reboot to complete pending patching.
3. Cross-reference against this organization's patch-cycle calendar to confirm whether the last scheduled maintenance window's reboot actually occurred on this host. — Expected result: the host's last boot time aligns with (or is more recent than) the last scheduled patch window. — Capture: note any mismatch. — Stop/continue: a host that missed its scheduled reboot window should be flagged for the next available window rather than left pending indefinitely.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| High uptime with no pending-reboot indicators | Host simply hasn't needed a reboot recently (patches applied cleanly without requiring one, or host wasn't included in a recent patch cycle) | Confirm the host is actually receiving patches on schedule (cross-check against MRC-OPS-029's backlog data) before assuming high uptime alone is benign |
| Pending-reboot indicator(s) present, uptime still low | A reboot occurred recently but a subsequent patch/install already re-flagged a pending reboot before this cycle's check | Schedule the next maintenance window promptly — the backlog of pending changes will keep growing until a reboot occurs |
| Pending-reboot indicator(s) present with high uptime | Host has gone an extended period without completing a required reboot | Escalate for a scheduled maintenance window — this is the core compliance gap this task exists to catch |
| Host missed its scheduled patch-window reboot per the patch-cycle calendar | Maintenance window was skipped (host was in use, change was deferred, or the automation that triggers scheduled reboots failed) | Investigate why the scheduled window was missed before simply rescheduling, in case the underlying automation itself needs attention |

This table reflects general practice for the assumed Windows Server/WSUS baseline and is not exhaustive.
