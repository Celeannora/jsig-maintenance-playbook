## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. The default `nltest.exe /sc_query` check used in this card queries only the locally cached secure channel state and is fully read-only against the network. The optional `/sc_verify` pass (Section 5.1 step 3, opt-in via `-Verify`) actively contacts the trusted domain's DC to confirm the trust password is in sync — this is still non-destructive, but it does generate authenticated network traffic to an external/partner domain, which is why it is not run by default every cycle. This card never resets a trust password (`nltest /sc_reset`) or creates/removes a trust relationship — those are separate, deliberate, documented change-control actions, typically requiring coordination with the administrators of the trusted domain/forest as well. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT: Active Directory Domain Services and Lightweight Directory Services Tools installed, and an account permitted to enumerate trusts (any authenticated domain user can read trust objects by default) and run `nltest.exe` (no special rights required for `/sc_query`; `/sc_verify` may require Domain Admins or an equivalent delegated right depending on domain trust configuration).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a domain controller itself, open an elevated PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-006.ps1`](../scripts/MRC-OPS-006.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-006.ps1
   ```
   — Expected result: the script enumerates every trust relationship for the current domain via `Get-ADTrust -Filter *`, then runs `nltest /sc_query:<TrustedDomain>` (cached secure channel state) for each one. If no trusts are configured, the script reports this and exits cleanly. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-006_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere). — Stop/continue: if the script errors before producing any report (e.g., `nltest.exe` is not on `PATH`, or the ActiveDirectory module is not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line (`Trust health check complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = no trusts configured, or every configured trust's secure channel query reports healthy; `1` = a trust's secure channel query failed, or trusts could not be enumerated). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section lists every trust's `Trust-SCQuery` result. Locate every row where `Result = Fail`. — Expected result: either a clean cycle (file the report and close) or an identified list of unhealthy trusts. — Capture: the full report file filed as this cycle's evidence. — Stop/continue: for any `Fail` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely.
6. Optional deeper check: if a trust's cached state looks healthy but there is another reason for concern (e.g., recent authentication failures reported by users of the trusted domain), run `.\MRC-OPS-006.ps1 -Verify` to additionally perform an active `nltest /sc_verify` pass against each trust. This is not required every month — use it when the cached-state check alone is insufficient to rule out a problem.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify every configured trust:
   ```powershell
   Get-ADTrust -Filter * | Select-Object Name, Direction, TrustType
   ```
   — Expected result: the full list of trust relationships, or an empty result if none are configured (in which case this cycle's check is complete — record "no trusts configured" and close). — Capture: the returned list. — Stop/continue: continue if any trusts exist.
2. For each trust, on a domain controller, open a Command Prompt and run:
   ```
   nltest /sc_query:<TrustedDomainName>
   ```
   — Expected result: output ending in "The command completed successfully," with a `Trusted DC Connection Status` of `Status = 0 0x0 NERR_Success`. — Capture: the output. — Stop/continue: continue to the next trust regardless of this trust's result; do not stop the cycle mid-way on a single trust's failure.
3. For a stronger check (opt-in, generates network traffic to the trusted domain — see Section 4), run:
   ```
   nltest /sc_verify:<TrustedDomainName>
   ```
   — Expected result: same "completed successfully" outcome as step 2. — Capture: the output. — Stop/continue: continue.
4. File the console output/screenshots from all steps in the cycle's evidence location (Section 6). — Expected result: a complete file set covering every configured trust for this cycle (or documented confirmation that no trusts exist). — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| `nltest /sc_query` reports a non-zero `Trusted DC Connection Status` (e.g. `ERROR_NO_SUCH_DOMAIN`, `RPC_S_SERVER_UNAVAILABLE`) | The secure channel to the trusted domain is broken — users/resources relying on this trust for cross-domain/cross-forest authentication will fail | **Escalate immediately** per Section 6; remediation (trust password reset via `nltest /sc_reset`, coordinated with the trusted domain's administrators) is a separate change-control action, not part of this routine check |
| `nltest /sc_query` succeeds but `nltest /sc_verify` fails | The cached state looked fine, but active verification found the trust password is out of sync between the two domains — this can still be causing intermittent authentication failures even though the cached state hadn't yet flagged it | **Escalate immediately** — treat this as equally urgent to a `/sc_query` failure |
| DNS resolution failure for the trusted domain name during either check | The querying DC cannot resolve the trusted domain's DNS name — this may be a DNS configuration issue rather than a trust-password issue; see [MRC-OPS-003](MRC-OPS-003.md) | Escalate if DNS resolution has been failing for more than one cycle; log as routine and retry next cycle if this appears to be a transient/one-off DNS issue |
| A trust unexpectedly disappears from `Get-ADTrust` output that was present last cycle, with no corresponding change-control record | The trust may have been removed, intentionally or otherwise, without going through documented change control | **Escalate immediately** for investigation — this has security-relevant implications and should additionally route through [`ESCALATION-MATRIX.md`](../../templates/ESCALATION-MATRIX.md) CAT tiers if the removal was unapproved |

This table reflects general Active Directory trust semantics for the assumed Windows Server/AD baseline and is not exhaustive. For a finding not listed here, use organizational AD-support experience to judge urgency.
