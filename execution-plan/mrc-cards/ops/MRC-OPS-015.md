## 4. Safety / Handling Precautions

This is a read-only reporting task. The companion script (Section 5.1) never resumes, suspends, or removes a queue, nor restarts the Transport service — any of those is a deliberate remediation action a human takes only after reviewing this report. Do not indiscriminately resume or remove a Suspended queue without first identifying why it was suspended (a Suspended queue is very often suspended for a reason, such as a detected loop or a deliberate hold) — removing a queue is also a destructive action that discards its messages, so review before acting. If executing this check requires touching a production Exchange server, follow the organization's standard change-control/maintenance-window process.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to transport queue and service information. `Get-Queue -Server` can be run against a remote transport server without an interactive session on that server itself, provided the operator's account has the necessary Exchange RBAC rights.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-015.ps1`](../scripts/MRC-OPS-015.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-015.ps1
   ```
   — Expected result: the script auto-discovers every transport server in the organization (falling back to the local host if that lookup fails), confirms the Microsoft Exchange Transport service is Running on each, and lists every queue's status/message count, flagging any Suspended queue as Fail and any Retry-status queue over 25 messages (default) as Warning. **It never resumes, suspends, or removes a queue, nor restarts a service.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-015_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = Transport service Running and no queue Suspended or over the Retry threshold on any server; `1` = a service is stopped, a queue exceeds the threshold, a queue is Suspended, or a server could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of service/queue findings. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3; given the Daily frequency, escalate any Fail the same day rather than waiting for the next cycle.

### 5.2 Manual path (fallback / spot-check verification)

1. Confirm the Transport service is running on each transport server:
   ```powershell
   Get-Service -ComputerName <ServerName> -Name MSExchangeTransport | Select-Object MachineName, Status
   ```
   — Expected result: `Status = Running` on every transport server. — Capture: the returned status per server. — Stop/continue: if `Status` is anything other than `Running`, this is an immediate finding — proceed to escalation without waiting for the queue check.
2. List queues on each transport server:
   ```powershell
   Get-Queue -Server <ServerName> | Select-Object Identity, Status, MessageCount, NextHopDomain
   ```
   — Expected result: no queue in `Suspended` status, and any `Retry`-status queue has a low, non-growing message count. — Capture: the returned table per server. — Stop/continue: a `Suspended` queue or a large/growing `Retry` queue is a finding — for a `Retry` queue, note the `NextHopDomain` since it usually identifies the specific destination the connection is failing to, which narrows the root-cause investigation.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Microsoft Exchange Transport service not Running | Mail is not being processed/relayed by this server at all | **Escalate immediately**; do not restart the service without following the organization's standard change process, since an ungraceful restart can itself cause message loss for in-flight mail |
| A queue in `Retry` status with a large/growing message count | Repeated connection failures to the `NextHopDomain` — could be a DNS issue, a firewall/network change, an expired certificate (see [MRC-OPS-016](MRC-OPS-016.md)), or the destination server being down | Log as a finding; investigate the specific `NextHopDomain`; escalate if the queue is growing rather than holding steady, or if it affects a business-critical destination |
| A queue in `Suspended` status | Manually or automatically suspended — will never clear on its own | **Escalate**; determine why it was suspended before resuming, since it may be intentionally held (e.g., a detected mail loop) |
| Queue count and Transport service both healthy but users report delayed mail | Delay may be occurring elsewhere in the path (a downstream relay, a third-party filtering service, or the recipient's own mail system) rather than on this organization's transport servers | Log as informational; this check alone does not confirm end-to-end delivery — escalate for a broader mail-flow trace if user reports persist |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
