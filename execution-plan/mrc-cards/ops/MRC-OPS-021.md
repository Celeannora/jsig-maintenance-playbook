## 4. Safety / Handling Precautions

This is a read-only verification task. The companion script (Section 5.1) never triggers, schedules, or cancels a backup job, and never truncates transaction logs directly — log truncation after a successful application-aware backup is performed automatically by Exchange/VSS as part of that backup process, never by this script or by manual log deletion (see [MRC-OPS-017](MRC-OPS-017.md) Section 4 for why manually deleting `.log` files is never an acceptable workaround). A plain file-level copy of the `.edb` database file (rather than a true VSS application-aware backup) does not update `LastFullBackup` and does not truncate logs — do not accept a "the files are copied somewhere" claim as satisfying this task; the verification specifically requires evidence of a completed application-aware backup, not merely file redundancy.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to mailbox database status, and local administrator access on each Mailbox server sufficient to run `vssadmin.exe list writers`.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-021.ps1`](../scripts/MRC-OPS-021.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-021.ps1
   ```
   — Expected result: the script checks every mailbox database's `LastFullBackup` timestamp (flagging Fail if null or older than 48 hours by default; adjust with `-MaxBackupAgeHours` to match this organization's actual backup schedule) and checks the Microsoft Exchange Writer VSS writer state on each Mailbox server that hosts a checked database (flagging Fail if not `Stable`/`No error`). **It never triggers a backup or truncates logs.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-021_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell, or because `vssadmin.exe` requires elevated/local-admin rights on a remote server), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every database's last backup is within threshold and every checked Exchange Writer is Stable; `1` = a database is missing a recent backup, a writer is unhealthy, or a target could not be queried). — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail`. — Expected result: either a clean cycle (file the report and close) or an identified database/server needing follow-up. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any Fail, proceed to Section 5.3 for triage; do not wait for the next weekly cycle if a database has never had a successful backup.

### 5.2 Manual path (fallback / spot-check verification)

1. In Exchange Management Shell, check each database's last application-aware backup timestamp:
   ```powershell
   Get-MailboxDatabase -Status | Select-Object Name, Server, LastFullBackup
   ```
   — Expected result: a recent `LastFullBackup` value for every database. — Capture: the returned table. — Stop/continue: a null value or one older than this organization's expected backup interval is a finding; proceed to step 2 regardless to check writer health.
2. On each Mailbox server hosting a checked database, check the Microsoft Exchange Writer's VSS state:
   ```powershell
   vssadmin.exe list writers
   ```
   — Expected result: the `Microsoft Exchange Writer` entry shows `State: [1] Stable` and `Last error: No error`. — Capture: the relevant portion of the command output. — Stop/continue: any other state or a non-"No error" last error is a finding, since it will likely cause the next backup attempt to fail even if the last completed backup looked fine.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| `LastFullBackup` is null | No application-aware backup has ever completed successfully for this database | Escalate immediately — verify the backup job is actually configured and targeting this database, not just assumed to exist |
| `LastFullBackup` older than the expected interval | Backup job may be failing silently, was disabled, or a recent one skipped this database | Check the backup software's own job history/logs for the specific failure reason before assuming an Exchange-side cause |
| Microsoft Exchange Writer state not `Stable` (e.g. `Failed`, `Waiting for completion`) | VSS writer is in a bad state, commonly caused by a previous backup being interrupted or another VSS operation (e.g. a snapshot-based antivirus scan) conflicting | A writer in a persistently bad state after a fresh reboot may require the backup vendor's documented recovery steps; do not attempt to force-reset VSS writers without following vendor guidance, since an improper reset can itself disrupt a database |
| Backup completing per third-party software logs but `LastFullBackup` still null/stale | The backup product may not actually be performing a true Exchange-aware VSS backup despite appearing to succeed | Verify with the backup vendor that Exchange application-awareness (the VSS writer integration) is actually enabled for this backup job, not just a file-level copy |

This table reflects general practice for the assumed Exchange + Windows Server Backup baseline and is not exhaustive.
