## 4. Safety / Handling Precautions

This is a read-only reporting task. The companion script (Section 5.1) only reads message tracking logs — it never resends, redirects, or deletes any message, and never modifies the message tracking log configuration itself (e.g. its retention/circular-logging settings). Message tracking logs frequently contain the full recipient address and delivery status of every message that flowed through transport, which may include information about individuals covered by the organization's privacy/handling requirements — treat the exported report with the same handling precautions as any other document containing personal or sensitive routing information, and follow the organization's data-handling policy for storage, retention, and access to the report file.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to message tracking logs on each transport server.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-020.ps1`](../scripts/MRC-OPS-020.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-020.ps1
   ```
   — Expected result: the script auto-discovers every transport server in the organization (falling back to the local host if that lookup fails), queries the past 7 days (default; adjust with `-LookbackDays`) of message tracking logs, summarizes event volume by `EventId`, lists every `FAIL` event with its recipient and status detail, and flags the cycle as Warning if the total `FAIL` count exceeds 50 (default; adjust with `-FailCountWarning`). **It only reads log data.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-020_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = total FAIL count within threshold on every target; `1` = FAIL count exceeds threshold, or a target could not be queried). — Capture: console output. — Stop/continue: proceed to step 5 regardless of exit code — the report always lists every individual `FAIL` event for review even when the total is within threshold.
5. Open the report and review the listed `FAIL` events for any recognizable pattern (e.g. repeated failures to the same domain, or a spike correlated with a known change). — Expected result: either isolated one-off bounces (routine, no further action) or an identified pattern warranting deeper investigation. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for a Warning result or a recognizable pattern, proceed to Section 5.3 for triage.

### 5.2 Manual path (fallback / spot-check verification)

1. On each transport server, in Exchange Management Shell, pull the event-volume summary for the review window:
   ```powershell
   Get-MessageTrackingLog -Server <ServerName> -Start (Get-Date).AddDays(-7) -ResultSize Unlimited |
       Group-Object EventId | Sort-Object Count -Descending
   ```
   — Expected result: a count of messages by event type (`DELIVER`, `FAIL`, `DEFER`, `SEND`, etc.) for the window. — Capture: the returned table. — Stop/continue: proceed to step 2 to inspect `FAIL` events specifically.
2. List the individual `FAIL` events:
   ```powershell
   Get-MessageTrackingLog -Server <ServerName> -Start (Get-Date).AddDays(-7) -ResultSize Unlimited -EventId FAIL |
       Select-Object Timestamp, Recipients, RecipientStatus
   ```
   — Expected result: every failed-delivery message with its recipient and failure status. — Capture: the returned table. — Stop/continue: an unusually high count relative to prior cycles, or a repeated failure to the same destination, is a finding.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Isolated `FAIL` events with `550 5.1.1 user unknown` or similar to varied recipients | Routine bounces from mistyped addresses or departed employees at recipient organizations | Log as informational; no action needed unless volume is unusually high |
| Repeated `FAIL` events to the same external domain | Possible block/reputation issue with that specific recipient domain, or a legitimate change on their end (e.g. they retired an address) | Investigate the specific domain's response codes; if it references a reputation/blocklist issue, this may require the organization's mail-relationship or DNS/SPF/DKIM configuration to be reviewed separately |
| Sudden spike in total `FAIL` count correlated with a recent change | A recent transport rule, connector, or DNS change may be misrouting or blocking mail | Cross-reference [MRC-OPS-019](MRC-OPS-019.md)'s most recent findings and any recent change record before assuming an external cause |
| High volume of `FAIL` events all citing the same internal recipient | A specific mailbox may be over quota, disabled, or misconfigured | Direct the finding to the mailbox owner's help-desk/support channel rather than treating it as a transport-wide issue |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
