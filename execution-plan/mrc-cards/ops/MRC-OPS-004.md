## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. The `dfsrdiag.exe replicationstate` and `dfsrdiag.exe backlog` commands used in this card are read-only diagnostic queries — they do not force a resync, change replication schedules, or restart the DFS Replication (DFSR) service. Do not run `dfsrdiag.exe` with any state-changing switch (e.g. a forced polling interval change) as part of this routine check. If a finding calls for remediation (e.g., a stuck replication or persistent backlog requiring a non-authoritative or authoritative SYSVOL resync), that is a separate, deliberate, documented change-control action outside this card's routine cadence — non-authoritative/authoritative resyncs carry real risk of data loss if performed incorrectly. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT: DFS Management Tools installed, and an account permitted to query DFSR state (local Administrators on the target DC, or an equivalent delegated read-level account per organizational RBAC).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a domain controller itself, open an elevated PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-004.ps1`](../scripts/MRC-OPS-004.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-004.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain via `Get-ADDomainController -Filter *` (requires the ActiveDirectory PowerShell module), confirms the DFSR service is running on each, checks replication state via `dfsrdiag replicationstate`, and checks the SYSVOL Share replication group's backlog between every DC pair via `dfsrdiag backlog`. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-004_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere). — Stop/continue: if the script errors before producing any report (e.g., `dfsrdiag.exe` is not on `PATH`, or the ActiveDirectory module is not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line (`SYSVOL/DFSR replication check complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = every DC's DFSR service is running with zero backlog everywhere; `1` = a stopped service, a non-zero backlog, or an unreachable target). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section lists every check as a table with `Target`, `CheckName`, and `Result` columns. Locate every row where `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of failing/warning replication pairs. — Capture: the full report file filed as this cycle's evidence. — Stop/continue: for any `Fail` or `Warning` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely. By default the script flags a `Fail` above 50 backlogged files (`-MaxBacklogFiles`, adjustable) and a `Warning` for any smaller non-zero backlog.
6. If a specific DC pair shows a persistent (not just transient) backlog across two or more consecutive weekly cycles, treat this as an escalation regardless of the raw file count — a backlog that does not clear on its own over a week indicates a stuck replication, not a normal in-flight transfer.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify every domain controller in scope:
   ```powershell
   Get-ADDomainController -Filter * | Select-Object HostName
   ```
   — Expected result: the full list of DC hostnames. — Capture: the returned list. — Stop/continue: continue.
2. On each DC, confirm the DFS Replication service is running:
   ```powershell
   Get-Service -Name DFSR
   ```
   — Expected result: `Status = Running`. — Capture: the returned status. — Stop/continue: if the service is not running on any DC, this is an immediate escalation (Section 5.3) for that DC.
3. Check overall replication state for a given DC:
   ```
   dfsrdiag.exe replicationstate /Member:<DCName>
   ```
   — Expected result: output listing the replicated folders (including SYSVOL Share) with no error/failure text. — Capture: the output. — Stop/continue: continue to step 4 regardless.
4. Check the SYSVOL Share backlog between each pair of DCs (run once per ordered pair, i.e. both directions):
   ```
   dfsrdiag.exe backlog /RGName:"Domain System Volume" /RFName:"SYSVOL Share" /SendingMember:<DC-A> /ReceivingMember:<DC-B>
   ```
   — Expected result: a `Backlog File count` of `0`, or a small transient number that clears on a re-check a few minutes later. — Capture: the output for each pair, both directions. — Stop/continue: a persistently high or non-zero count (per Section 5.3) is a finding.
5. File the console output/screenshots from all steps in the cycle's evidence location (Section 6). — Expected result: a complete file set covering every DC pair in scope for this cycle. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| DFSR service stopped on a DC | That DC is not replicating SYSVOL (Group Policy objects, logon scripts) at all — Group Policy may fail to apply consistently for users/computers authenticating against it | **Escalate immediately** per Section 6; do not wait for the next cycle |
| High or growing backlog file count between a specific DC pair | Replication is falling behind — could be network latency/bandwidth constraints between sites, a stalled DFSR service, or a large recent SYSVOL change (e.g. many new GPOs) still propagating | Escalate if the backlog is above the script's `-MaxBacklogFiles` threshold or persists across consecutive weekly cycles; log as routine if a small backlog clears on its own within the same check |
| `dfsrdiag replicationstate` reports an error/failure for a replicated folder | The DFSR replication group itself has an operational problem beyond simple backlog (e.g. a corrupted DFSR database on that member) | **Escalate immediately** — this typically requires DFSR database recovery (`dfsrdiag ReplicationState` combined with the DFSR event log), which is out of scope for this routine check |
| Related `FrsEvent`/`DFSREvent` failures also seen in [MRC-OPS-002](MRC-OPS-002.md)'s DCDIAG output | Confirms the same underlying replication issue from a different diagnostic angle — cross-reference both cards' findings for the same DC/cycle | Treat as the same incident; do not double-log as two unrelated findings |

This table reflects general DFSR/SYSVOL replication semantics for the assumed Windows Server/AD baseline and is not exhaustive. For a finding not listed here, use organizational AD-support experience to judge urgency.
