## 4. Safety / Handling Precautions

This task is entirely **read-only** — it queries service state via `Get-Service` and never starts, stops, or restarts any service. Running it against production domain controllers on a daily cadence carries no operational risk and does not require a change-control window. A stopped core service (Netlogon, KDC, or DNS Server) on a DC is a significant availability finding, but the response to it — restarting the service — is **not** performed automatically by this check. A service that has stopped unexpectedly often indicates an underlying problem (resource exhaustion, a dependency failure, a recent configuration change) that should be understood before simply restarting it, since a blind restart can mask the root cause or, in some failure modes, make diagnosis harder. Restarting a stopped service on a production DC is a deliberate action taken by a human, following the organization's standard operational/change-control process. If using the companion PowerShell script, review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation able to query service state remotely, and an account with local read access on each target DC (a standard authenticated domain account with local admin, or membership in an equivalent delegated group, is sufficient to query service state — no special rights beyond that are required for this read-only check).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a DC itself, open a PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-010.ps1`](../scripts/MRC-OPS-010.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-010.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain (requires the ActiveDirectory PowerShell module; falls back to the local host if unavailable) and checks the Netlogon, Kdc, and DNS service state on each. A DC that is not running the DNS Server role reports that specific check as `Skipped` rather than `Fail`. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-010_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors before producing any report, fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every applicable service Running on every target; `1` = at least one service not Running, or an unreachable target). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail`. — Expected result: either a clean cycle (file the report and close) or an identified list of stopped services per DC. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any `Fail` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately (which for this card's three services, is nearly always the case — see Section 5.3).

### 5.2 Manual path (fallback / spot-check verification)

1. On each target DC (or remotely, specifying `-ComputerName`), open PowerShell and check the three services:
   ```powershell
   Get-Service -Name Netlogon, Kdc, DNS -ErrorAction SilentlyContinue |
       Select-Object Name, Status, StartType
   ```
   — Expected result: `Status = Running` for `Netlogon` and `Kdc` on every DC, and for `DNS` on every DC that runs the DNS Server role (a "Cannot find any service" error for `DNS` on a non-DNS DC is expected and not a failure). — Capture: the returned table. — Stop/continue: continue.
2. If a service is not `Running`, check its last few related System-log events before taking any action:
   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName='System'; ProviderName='Service Control Manager' } -MaxEvents 20 |
       Where-Object Message -like "*<ServiceName>*" | Select-Object TimeCreated, Id, Message
   ```
   — Expected result: context on why/when the service stopped (e.g., a crash, a manual stop, a dependency failure). — Capture: the relevant events. — Stop/continue: use this context plus the triage table in Section 5.3 to decide escalation urgency; do not restart the service as part of this cycle's data-collection step.
3. Repeat steps 1–2 for every DC in scope, and file the combined output as this cycle's evidence. — Expected result: a complete data set covering every DC. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Netlogon not Running | Blocks user/computer authentication and Group Policy processing referencing that DC — a direct availability impact | **Escalate immediately** |
| Kdc (Kerberos Key Distribution Center) not Running | Blocks Kerberos ticket issuance from that DC — clients typically fail over to another DC, but if this is the only reachable DC for a site, authentication fails entirely for that site | **Escalate immediately** |
| DNS not Running on a DC that hosts the DNS Server role | Clients configured to use this DC for DNS cannot resolve AD-integrated records (SRV records for site/service discovery, in particular), which can cascade into broader authentication and replication failures | **Escalate immediately** |
| DNS reported `Skipped` | Expected and not a finding — this DC does not run the DNS Server role | No action; this is the correct/expected result |
| A service is `Running` but with `StartType = Manual` or `Disabled` instead of `Automatic` | The service would not restart automatically after a reboot, creating latent risk even though it is currently up | Log as a routine finding; correct the start type to `Automatic` per standard change-control at the next opportunity |

This table reflects general practice for the assumed Windows Server/AD baseline and is not exhaustive. All three services stopping unexpectedly (as opposed to being intentionally stopped for planned maintenance) should be treated as an availability-impacting event by default even if the underlying cause turns out to be benign.
