## 4. Safety / Handling Precautions

This is a read-only monitoring task. The companion script (Section 5.1) never restarts a service, changes a virtual directory authentication or binding setting, or modifies any client access configuration — it only reads service state and runs Exchange's built-in synthetic-transaction cmdlets, which authenticate against the organization's existing configured test mailbox and do not touch any real user's mailbox or credentials. If a synthetic transaction fails, do not immediately restart IIS or the Client Access services as a first response on a production server during business hours — an uncoordinated service restart interrupts active user sessions. Follow the organization's standard change-control process for any corrective service restart, and prefer restarting outside business hours or during an approved maintenance window unless the failure is already causing a live outage.

## 5. Procedure

This card assumes access to an Exchange Management Shell session with read permissions to service and connectivity-test information on each Client Access server, and assumes the organization's standard test-mailbox configuration required by `Test-OwaConnectivity`/`Test-ActiveSyncConnectivity` is already in place.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-018.ps1`](../scripts/MRC-OPS-018.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-018.ps1
   ```
   — Expected result: the script auto-discovers every Client Access server in the organization (falling back to the local host if that lookup fails), checks that every service required for each server's Exchange roles is running via `Test-ServiceHealth`, and runs `Test-OwaConnectivity`/`Test-ActiveSyncConnectivity` synthetic logon transactions against each. **It never modifies any service state or client access configuration.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-018_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every required service running and both synthetic transactions succeeded on every server; `1` = a required service is stopped, a synthetic transaction failed, or a server could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail`. — Expected result: either a clean cycle (file the report and close) or an identified failing server/service/transaction. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any failure, proceed to Section 5.3 for triage before taking any corrective action.

### 5.2 Manual path (fallback / spot-check verification)

1. On each Client Access server, in Exchange Management Shell, check required-service health:
   ```powershell
   Test-ServiceHealth -Server <ServerName>
   ```
   — Expected result: a `ServicesNotRunning` property that is empty for every listed role. — Capture: the returned table. — Stop/continue: any non-empty `ServicesNotRunning` is a finding; proceed to step 2 regardless to also check the synthetic transactions.
2. Run the OWA synthetic transaction:
   ```powershell
   Test-OwaConnectivity -ClientAccessServer <ServerName>
   ```
   — Expected result: `Result = Success`. — Capture: the returned object including `Latency` and `Error`. — Stop/continue: any result other than `Success` is a finding.
3. Run the ActiveSync synthetic transaction:
   ```powershell
   Test-ActiveSyncConnectivity -ClientAccessServer <ServerName>
   ```
   — Expected result: `Result = Success`. — Capture: the returned object including `Latency` and `Error`. — Stop/continue: any result other than `Success` is a finding.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Required service (e.g. IIS application pool for OWA) not running | Client access role service crashed, was stopped, or failed to start after a patch/reboot | Escalate; a coordinated service restart per change-control is typically the resolution, but confirm no underlying cause (e.g. disk full, corrupted app pool config) first |
| `Test-OwaConnectivity`/`Test-ActiveSyncConnectivity` fails with an authentication/logon error | Test-mailbox credential expired or was changed, or an authentication provider (e.g. Kerberos, a load balancer's pre-authentication) is misconfigured | Verify the test-mailbox account is not locked/expired before assuming a service-side fault |
| `Test-OwaConnectivity`/`Test-ActiveSyncConnectivity` fails with a certificate/TLS error | The bound certificate is expired, not trusted, or missing a required SAN | Cross-reference [MRC-OPS-016](MRC-OPS-016.md)'s most recent result — this is the most common root cause of this specific failure signature |
| High latency but `Result = Success` | Performance degradation short of an outage | Log as informational; investigate if latency trend worsens across consecutive cycles |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
