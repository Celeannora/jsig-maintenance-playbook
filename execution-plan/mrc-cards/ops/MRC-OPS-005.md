## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. This card is strictly a verification/reporting check — it identifies the current holder of each of the five FSMO roles (Schema Master, Domain Naming Master, RID Master, PDC Emulator, Infrastructure Master) and confirms that holder is online and its directory service is running. It does not transfer or seize any FSMO role. FSMO role transfer (a planned, graceful move) or seizure (a forced move used only when the original holder cannot be recovered) is a high-impact, deliberate, documented change-control action, explicitly out of scope for this routine monthly check — an incorrect seizure while the original role holder is still reachable can cause USN rollback and directory corruption. If a role holder is found unreachable, follow the escalation path in Section 6; do not attempt seizure as part of this card's procedure. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation with RSAT: Active Directory Domain Services and Lightweight Directory Services Tools installed, and an account permitted to read forest/domain configuration (any authenticated domain user can read FSMO role-holder assignments by default; no elevated rights are required for this read-only check).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a domain controller itself, open a PowerShell session (elevation not required for the read-only checks; elevation may be required for the remote service query in step 3 below depending on local firewall/WinRM configuration).
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-005.ps1`](../scripts/MRC-OPS-005.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-005.ps1
   ```
   — Expected result: the script queries `Get-ADForest` (Schema Master, Domain Naming Master) and `Get-ADDomain` (RID Master, PDC Emulator, Infrastructure Master) for the current holder of each of the five roles, then pings each holder and, where reachable, queries its NTDS (Active Directory Domain Services) service state. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-005_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere). — Stop/continue: if the script errors before producing any report (e.g., the ActiveDirectory module is not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line (`FSMO role holder verification complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = all five roles identified and their holders reachable with NTDS running; `1` = a role holder could not be identified, is unreachable, or its NTDS service is not confirmed running). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section lists each of the five `FSMO-<RoleName>` checks with a `Target` (the current holder's hostname) and `Result`. Locate every row where `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (five `Pass` rows, one per role, file the report and close) or an identified list of unreachable/degraded role holders. — Capture: the full report file filed as this cycle's evidence, including the recorded current holder of each role (useful baseline reference even on a clean cycle). — Stop/continue: for any `Fail` or `Warning` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely.
6. Compare this cycle's recorded role holders against last cycle's evidence. — Expected result: role assignments are normally stable between cycles. — Capture: note any change in which DC holds a given role. — Stop/continue: an unexpected/unplanned role holder change (i.e., not the result of a documented, approved transfer) is itself a finding — investigate whether an unplanned seizure event occurred (Section 5.3).

### 5.2 Manual path (fallback / spot-check verification)

1. Identify the current FSMO role holders. On any domain-joined host, open a Command Prompt and run:
   ```
   netdom query fsmo
   ```
   — Expected result: the hostname of the current holder for each of the five roles. — Capture: the returned output. — Stop/continue: continue.
   Alternatively, in PowerShell:
   ```powershell
   Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster
   Get-ADDomain | Select-Object RIDMaster, PDCEmulator, InfrastructureMaster
   ```
2. For each role holder identified, confirm it is online:
   ```powershell
   Test-Connection -ComputerName <RoleHolderName> -Count 2
   ```
   — Expected result: successful ping replies. — Capture: the output. — Stop/continue: if a role holder does not respond, treat as an immediate escalation candidate (Section 5.3) before assuming the tool itself is at fault (confirm via a second method, e.g. RDP or console access, before escalating).
3. Where remote service query is feasible, confirm the Active Directory Domain Services (NTDS) service is running on each role holder:
   ```powershell
   Get-Service -ComputerName <RoleHolderName> -Name NTDS
   ```
   — Expected result: `Status = Running`. — Capture: the returned status. — Stop/continue: if remote service query fails due to firewall/WinRM restrictions rather than the service itself, note this as a tooling limitation, not a finding, and rely on the ping-reachability result plus other cards (e.g. [MRC-OPS-001](MRC-OPS-001.md), [MRC-OPS-002](MRC-OPS-002.md)) run against that same DC this cycle for corroboration.
4. File the console output/screenshots from all steps in the cycle's evidence location (Section 6). — Expected result: a complete file set covering all five FSMO roles for this cycle. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| A role holder does not respond to ping and cannot be reached by any other method | That DC is down or unreachable — this is most urgent for the **PDC Emulator** (affects time sync and password/lockout authority domain-wide) and **RID Master** (a prolonged outage can eventually exhaust RID pools domain-wide) | **Escalate immediately** per Section 6; do not attempt FSMO seizure as part of this card — that decision and action belongs to a separate, higher-authority change-control process |
| Role holder is reachable, but its NTDS service is not running | The DC is up but Active Directory Domain Services itself is degraded on it — the FSMO role is technically assigned there but non-functional | **Escalate immediately** |
| An FSMO role has moved to a different DC since the last cycle, with no corresponding change-control record | Either an undocumented planned transfer occurred, or (more concerning) a seizure occurred without going through proper approval — seizures are sometimes performed reactively during an outage and not always immediately documented | **Escalate immediately** for investigation — determine whether this was an approved action; if unapproved, this may also have security-relevant implications requiring [`ESCALATION-MATRIX.md`](../../templates/ESCALATION-MATRIX.md) CAT-tier routing |
| Script or `netdom` cannot determine the role holder for one specific role (returns empty/error) while others resolve fine | Possible DNS resolution issue for that role holder specifically, or an AD replication/metadata problem — see also [MRC-OPS-003](MRC-OPS-003.md) (DNS) and [MRC-OPS-001](MRC-OPS-001.md) (AD replication) | Escalate if it persists after a DNS/replication cross-check; log as routine if it resolves after a retry (transient lookup failure) |

This table reflects general FSMO-role semantics for the assumed Windows Server/AD baseline and is not exhaustive. For a finding not listed here, use organizational AD-support experience to judge urgency.
