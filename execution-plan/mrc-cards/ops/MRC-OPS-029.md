## 4. Safety / Handling Precautions

This is a read-only verification task. The companion script (Section 5.1) never approves, declines, or deploys any update, and never changes WSUS server or synchronization configuration — it only calls `Get-WsusServer`/`GetSubscription()`/`GetLastSynchronizationInfo()` and `Get-WsusUpdate`, all of which are query-only. Run the script from a host with the `UpdateServices` PowerShell module installed (present on the WSUS server role itself, or installable as a standalone RSAT-style feature on an administrative workstation with network access to the WSUS server). Do not use a finding from this task as justification to approve updates directly during the review — approval and deployment of functional updates is a separate, deliberate change-management action with its own testing/staging expectations, not something to perform ad hoc while triaging this check.

## 5. Procedure

This card assumes network access to the target WSUS server and a Windows PowerShell session (not PowerShell 7+, since the `UpdateServices` module is Windows PowerShell-only) with the `UpdateServices` module available, either on the WSUS server itself or a workstation with the WSUS administration console/RSAT feature installed.

### 5.1 Automated path (recommended)

1. On a Windows PowerShell (5.1) host with the `UpdateServices` module available and network access to the WSUS server's admin port (default 8530 HTTP / 8531 HTTPS), obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-029.ps1`](../scripts/MRC-OPS-029.ps1) from this repository.
2. Run:
   ```powershell
   .\MRC-OPS-029.ps1 -WsusServer wsus01.example.mil -PortNumber 8531 -UseSSL
   ```
   — Expected result: the script connects via `Get-WsusServer`, checks the last synchronization result/age via `(Get-WsusServer).GetSubscription().GetLastSynchronizationInfo()` against `-MaxSyncAgeDays` (default 7), and queries `Get-WsusUpdate` for approved updates in the non-Critical/non-Security ("WSUS") classification bucket with a Failed-or-Needed status, flagging Warning if the count meets or exceeds `-FailedOrNeededThreshold` (default 1). **It never approves, declines, or deploys any update.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-029_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script cannot connect (commonly a firewall/admin-port issue, an expired credential context, or the `UpdateServices` module not installed on this host), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
3. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every check passed. `1` = any check returned Warning or could not be queried). — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 4.
4. Open the report file's `SUMMARY` table and locate every row with `Result = Warning` or `Fail`. — Expected result: either a clean cycle (file the report and close) or an identified stale-sync/backlog issue needing follow-up. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any Warning/Fail, proceed to Section 5.3 for triage.

### 5.2 Manual path (fallback / spot-check verification)

1. On the WSUS server (or a host with the WSUS administration console), open the **Update Services** MMC console, expand the server node, and select **Options → Synchronizations** or the server's home dashboard. — Expected result: the **Last Synchronization** panel shows a **Succeeded** result within the last several days (this task's cadence is monthly, but a WSUS server should be synchronizing far more frequently — daily is typical). — Capture: a screenshot of the synchronization status. — Stop/continue: a synchronization result of anything other than **Succeeded**, or a last-sync timestamp older than roughly a week, is a finding worth investigating even outside this task's monthly cadence.
2. In the console, navigate to **Updates**, then use the built-in view filters (or **All Updates → search/filter**) to show updates **Approved: Yes**, **Status: Failed or Needed**, and **Classification** set to any bucket other than **Critical Updates** and **Security Updates** (i.e., **Update Rollups**, **Feature Packs**, **Drivers**, **Definition Updates** excluded per local policy, etc.). — Expected result: a list (ideally empty or small) of approved functional/non-security updates that are still outstanding across the managed computer population. — Capture: export or screenshot the filtered list, noting the count. — Stop/continue: a non-trivial or growing count is this task's core finding — functional updates are being approved but not applied.
3. Cross-reference against the prior cycle's report (if available) to see whether the backlog count is shrinking, holding steady, or growing. — Expected result: a stable or shrinking backlog indicates client-side update application is keeping pace. — Capture: note the trend in this cycle's findings. — Stop/continue: a growing backlog across multiple consecutive monthly cycles should be escalated per Section 5.3 even if any single cycle's count alone would not warrant it.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Last synchronization result is `Failed` or missing entirely | WSUS server cannot reach Microsoft Update (or its configured upstream server), often a proxy/firewall/certificate issue | Check WSUS server network egress and the synchronization log (`%ProgramFiles%\Update Services\LogFiles\SoftwareDistribution.log`) before assuming a Microsoft-side outage |
| Last synchronization is older than `-MaxSyncAgeDays` but reports `Succeeded` from an earlier attempt | The synchronization schedule itself may be disabled or misconfigured, not necessarily failing | Verify the scheduled synchronization is still configured and enabled in **Options → Synchronizations** |
| Approved Failed-or-Needed backlog present in the "WSUS" classification bucket | Functional/non-security updates are approved in WSUS but not yet applied client-side — could be a deployment ring/maintenance-window gap, WMI/BITS issue on affected clients, or the updates were approved too recently to have applied yet | Cross-reference against the client-side patch compliance reporting used for the *security*-patch cadence to see if the same hosts are also behind on security patches (broader client health issue) or only on this "WSUS" bucket (targeted functional-update rollout gap) |
| Backlog count growing across multiple consecutive monthly cycles | Functional updates are being approved but never actually reaching clients — a systemic deployment issue, not isolated stragglers | Escalate for a deployment-ring/maintenance-window review rather than continuing to re-approve the same updates each cycle |

This table reflects general practice for the assumed WSUS baseline and is not exhaustive.
