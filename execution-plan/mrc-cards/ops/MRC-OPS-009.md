## 4. Safety / Handling Precautions

This task is entirely **read-only** — it queries disk free space via CIM/WMI and reads (never clears) the System, Application, and Directory Service event logs. It does not delete files, clear logs, or change any configuration. Running it against production domain controllers on a daily cadence carries no operational risk and does not require a change-control window. Any remediation triggered by a finding (freeing disk space, investigating a specific recurring event ID) is a separate, deliberate action taken through the organization's standard process — do not, for example, delete arbitrary large files to relieve a low-disk-space Fail without first confirming those files are safe to remove. If using the companion PowerShell script, review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to a Windows Server domain controller, or a management workstation able to reach each DC remotely (CIM/WMI and remote event log access), and an account with at least local read access on each target DC (a standard authenticated domain account with local admin or the built-in Performance Log Users / Event Log Readers group membership is sufficient — Domain Admin rights are not required for these read-only checks).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a DC itself, open a PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-009.ps1`](../scripts/MRC-OPS-009.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-009.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain via `Get-ADDomainController -Filter *` (requires the ActiveDirectory PowerShell module; falls back to the local host if unavailable), checks free space on every fixed disk (Fail below 10% free, Warning below 20% free by default), and counts Critical/Error events in the System, Application, and Directory Service logs over the last 24 hours (Warning above 25 events in a single log by default) on each DC. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-009_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors before producing any report, fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every disk and log within threshold on every target; `1` = at least one Fail, Warning, or unreachable target). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of low-disk-space and/or high-error-count findings per DC. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3 before deciding escalate-now vs. log-routine.
6. If a specific DC's threshold needs adjusting for its known workload (e.g., a DC that also hosts a large DFS namespace root and legitimately runs with less free space), re-run with adjusted parameters, e.g. `.\MRC-OPS-009.ps1 -ComputerName DC03 -CriticalFreePercent 5`, and document the deviation in this cycle's evidence rather than silently accepting a recurring Fail.

### 5.2 Manual path (fallback / spot-check verification)

1. On each target DC (or remotely via `-ComputerName`), open PowerShell and check disk free space:
   ```powershell
   Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3" |
       Select-Object DeviceID, @{N='FreeGB';E={[math]::Round($_.FreeSpace/1GB,1)}}, @{N='SizeGB';E={[math]::Round($_.Size/1GB,1)}}, @{N='PercentFree';E={[math]::Round(($_.FreeSpace/$_.Size)*100,1)}}
   ```
   — Expected result: free space, total size, and percent free for every fixed disk. — Capture: the returned table. — Stop/continue: continue.
2. Check recent Critical/Error events in the three relevant logs:
   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName='System','Application','Directory Service'; Level=1,2; StartTime=(Get-Date).AddHours(-24) } |
       Group-Object LogName | Select-Object Name, Count
   ```
   — Expected result: a per-log count of Critical/Error events in the last 24 hours. — Capture: the returned counts. — Stop/continue: if any log's count seems high relative to the DC's normal baseline, list the individual events for review:
   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName='System'; Level=1,2; StartTime=(Get-Date).AddHours(-24) } | Select-Object TimeCreated, Id, ProviderName, Message
   ```
3. Repeat steps 1–2 for every DC in scope, and file the combined output as this cycle's evidence. — Expected result: a complete data set covering every DC. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Free space below the Fail threshold (default <10%) | AD/SYSVOL/NTDS operations can fail unpredictably if the volume fills up; a DC has historically stopped responding to writes when its system volume runs out of space | **Escalate immediately**; identify and remove/relocate non-essential data, or extend the volume, per standard change-control |
| Free space in the Warning band (10–20% by default) | Trending toward a Fail — worth proactive attention before it becomes urgent | Log as a routine finding; trend it across cycles and investigate if the trend is worsening |
| High Critical/Error count in the Directory Service log specifically | Often correlates with an underlying AD health issue (replication, FSMO, or database problem) already covered by other MRC-OPS cards | Cross-check against [MRC-OPS-001](MRC-OPS-001.md) (replication), [MRC-OPS-002](MRC-OPS-002.md) (DCDIAG), and [MRC-OPS-012](MRC-OPS-012.md) (ntds.dit health) for this cycle; if those checks are also failing, escalate as a combined finding |
| High Critical/Error count in System or Application log unrelated to AD | Could be a driver, hardware, application, or unrelated service issue | Log as a routine finding; review the individual events (Section 5.2 step 2) for root cause and route to the appropriate owner if not AD-related |

This table reflects general practice for the assumed Windows Server/AD baseline and is not exhaustive. Use the specific event IDs and messages surfaced, together with organizational context, to judge urgency for anything not listed here.
