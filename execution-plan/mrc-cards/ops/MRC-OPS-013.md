## 4. Safety / Handling Precautions

This is a read-only reporting task. The companion script (Section 5.1) never dismounts a database, forces a database copy switchover/failover, or runs an online/offline defragmentation pass — those are all separate, deliberate, change-controlled actions a human takes only after reviewing this report's findings. If whitespace is persistently high, do not schedule an online defragmentation pass (`eseutil /d`) or any offline maintenance without first confirming a maintenance window and, for a DAG member database, coordinating with the DAG's failover schedule so the maintenance does not remove the last healthy copy of that database. If executing this check requires touching a production Exchange server, follow the organization's standard change-control/maintenance-window process.

## 5. Procedure

This card assumes access to an Exchange Management Shell session (either directly on an Exchange server or via a remote PowerShell session to one) with read permissions to mailbox database and database-copy status information.

### 5.1 Automated path (recommended)

1. On a workstation or server with Exchange Management Shell available, open that shell (not a standard Windows PowerShell console — the `Get-MailboxDatabase`/`Get-MailboxDatabaseCopyStatus` cmdlets require the Exchange snap-in or an Exchange remote session).
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-013.ps1`](../scripts/MRC-OPS-013.ps1) from this repository.
3. Run:
   ```powershell
   .\MRC-OPS-013.ps1
   ```
   — Expected result: the script reads every mailbox database's size and available whitespace (flagging Warning above 20% whitespace by default) and every database copy's status and content-index state (flagging Fail on any copy not `Mounted`/`Healthy`, Warning on a degraded content index). **It never dismounts a database or forces a copy switchover.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-013_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script errors immediately (commonly because it was run outside Exchange Management Shell), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
4. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every database's whitespace within threshold and every copy healthy; `1` = a whitespace threshold exceeded, a copy unhealthy, or a database could not be queried). — Expected result: exit code `0`. — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file's `SUMMARY` table and locate every row with `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of whitespace/copy-health findings. — Capture: the full report filed as this cycle's evidence. — Stop/continue: check each finding against the triage table in Section 5.3.

### 5.2 Manual path (fallback / spot-check verification)

1. In Exchange Management Shell, list database size and whitespace:
   ```powershell
   Get-MailboxDatabase -Status |
       Select-Object Name, DatabaseSize, AvailableNewMailboxSpace,
           @{N='WhitespacePercent';E={[math]::Round(($_.AvailableNewMailboxSpace.ToBytes()/$_.DatabaseSize.ToBytes())*100,1)}}
   ```
   — Expected result: size and whitespace percentage for every mailbox database. — Capture: the returned table. — Stop/continue: continue.
2. Check database copy status (for databases in a Database Availability Group):
   ```powershell
   Get-MailboxDatabaseCopyStatus -Identity * | Select-Object Name, Status, ContentIndexState, CopyQueueLength, ReplayQueueLength
   ```
   — Expected result: `Status` of `Mounted` or `Healthy` and `ContentIndexState` of `Healthy` for every copy, with low/zero `CopyQueueLength`/`ReplayQueueLength`. — Capture: the returned table. — Stop/continue: any copy not `Mounted`/`Healthy` or with a growing queue length is a finding — cross-reference against [MRC-OPS-014](MRC-OPS-014.md)'s replication-health results before escalating, since the two checks often surface the same underlying issue.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Whitespace consistently above the Warning threshold (default >20%) | Large volume of recent deletions/moves not yet reclaimed by background maintenance; database file is larger on disk than the actual data requires | Log as a routine finding; if trending upward over several cycles, consider scheduling an online defragmentation maintenance window — this is a separate, planned action, never automated here |
| Database copy `Status` not `Mounted`/`Healthy` (e.g., `FailedAndSuspended`, `Disconnected`) | The copy has stopped replicating or has failed outright; redundancy for that database is reduced or gone | **Escalate**; cross-reference [MRC-OPS-014](MRC-OPS-014.md) for the underlying replication-health cause before attempting any resume action |
| `ContentIndexState` not `Healthy` (e.g., `Failed`, `Crawling`) | Search indexing for that copy is broken or catching up; affects Search/OWA search functionality on that copy, not mail delivery | Log as a finding; if `Crawling` persists across multiple cycles rather than completing, escalate for review |
| Growing `CopyQueueLength`/`ReplayQueueLength` | Passive copy is falling behind on receiving or replaying logs — an early warning sign before a copy is marked unhealthy | Log as a finding; monitor trend; escalate if queue length is growing rather than holding steady or shrinking |

This table reflects general practice for the assumed Exchange baseline and is not exhaustive.
