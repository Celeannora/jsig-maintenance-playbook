## 4. Safety / Handling Precautions

No physical hazard is inherent to this task. `wbadmin.exe get versions` (used throughout this card) is a read-only query against existing backup history — it does not start a new backup, delete backup history, or modify backup schedules. This card verifies that a System State backup exists and is recent/successful; it does not perform a restore or a restore test. If a finding calls for triggering a new backup (`wbadmin start systemstatebackup`) as remediation, that is a normal operational action but should still be logged and, if run outside the DC's normal backup window, coordinated to avoid resource contention with other maintenance windows. Do not use this card's steps to initiate an actual System State restore — a restore is a separate, high-impact, deliberate, documented change-control action (typically only performed during incident recovery, per organizational DR procedures), never as part of routine verification. If using the companion PowerShell script (Section 5.1), review it and test in a non-production environment first — see the disclaimer in [`scripts/README.md`](../scripts/README.md) and the script's own `.NOTES` block.

## 5. Procedure

This card assumes access to each domain controller (locally, or via remote PowerShell/`wbadmin -machine:` where supported) with an account permitted to query backup history (local Administrators on the target DC, or an equivalent delegated read-level account per organizational RBAC).

### 5.1 Automated path (recommended)

1. On a domain-joined management workstation or a domain controller itself, open an elevated PowerShell session.
2. Obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-007.ps1`](../scripts/MRC-OPS-007.ps1) from this repository (copy it locally if the repository is not directly reachable from the management host).
3. Run:
   ```powershell
   .\MRC-OPS-007.ps1
   ```
   — Expected result: the script auto-discovers every domain controller in the current domain via `Get-ADDomainController -Filter *` (requires the ActiveDirectory PowerShell module) and, for each one, runs `wbadmin get versions` (locally if run on that DC, or with `-machine:<DC>` otherwise) to find the most recent backup version that includes System State, checking both that one exists and that it is within `-MaxAgeHours` (default 168 hours / 7 days) old. — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-007_<yyyyMMdd-HHmmss>.txt` by default (note the exact path printed to the console at the end of the run; use `-OutputPath` to direct it elsewhere). — Stop/continue: if the script errors before producing any report (e.g., `wbadmin.exe`/Windows Server Backup is not installed on a target, or this organization uses a third-party backup product instead — see the banner above), fall back to the manual path in Section 5.2, or that product's own reporting, for this cycle and log the tooling gap as a routine finding.
   
   Note: `wbadmin get versions -machine:<DC>` querying a *remote* machine's backup catalog requires that catalog to be reachable/shared appropriately in this organization's environment; in many environments this script is instead run locally on each DC (e.g. via a scheduled task) with results centrally collected, rather than queried remotely from one workstation. Adapt the invocation method to this organization's actual remote-management configuration.
4. Read the script's console summary line (`System State backup verification complete. X passed / Y failed / Z warning(s).`) and check `$LASTEXITCODE` (`0` = every target has a recent, successful System State backup; `1` = a target is missing one, its most recent one failed/is stale, or it could not be queried). — Expected result: exit code `0`. — Capture: console output (screenshot or copy/paste into the evidence package). — Stop/continue: if exit code is `1`, proceed to step 5.
5. Open the report file. Its `SUMMARY` section lists every DC's `SystemState-Backup` check with `Result` and a `Detail` showing the backup age. Locate every row where `Result = Fail` or `Result = Warning`. — Expected result: either a clean cycle (file the report and close) or an identified list of DCs with missing/stale/failed backups. — Capture: the full report file filed as this cycle's evidence. — Stop/continue: for any `Fail` or `Warning` row, check it against the triage table in Section 5.3 below before deciding whether to escalate immediately or log routinely.

### 5.2 Manual path (fallback / spot-check verification)

1. Identify every domain controller in scope:
   ```powershell
   Get-ADDomainController -Filter * | Select-Object HostName
   ```
   — Expected result: the full list of DC hostnames. — Capture: the returned list. — Stop/continue: continue.
2. On each DC (locally, or remotely if this organization's tooling supports it), open an elevated Command Prompt and run:
   ```
   wbadmin get versions
   ```
   — Expected result: a list of backup version blocks, each showing a `Backup time`, `Version identified`, and a `Can Recover:` line. — Capture: the output. — Stop/continue: continue to step 3.
3. In the output, find the most recent version block whose `Can Recover:` line includes `System State`. — Expected result: at least one such block exists, with a `Backup time`/`Version identified` timestamp within the last 7 days (matching this task's weekly cadence). — Capture: note the timestamp of the most recent qualifying backup. — Stop/continue: if no block includes `System State` at all, or the most recent one is older than roughly 7 days, treat as a finding (Section 5.3).
4. If this organization uses a third-party enterprise backup product instead of Windows Server Backup, consult that product's console, report, or API for the equivalent information (most recent successful System State-inclusive backup job per DC and its timestamp) instead of steps 2–3. — Expected result: equivalent confirmation via that product's own reporting. — Capture: exported/screenshotted confirmation from that product.
5. File the console output/screenshots (or third-party tool exports) from all steps in the cycle's evidence location (Section 6). — Expected result: a complete file set covering every DC in scope for this cycle. — Capture: the evidence bundle. — Stop/continue: this cycle's data collection is complete.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| No backup history found at all for a DC | Backups were never configured, or backup storage/scheduling has failed silently on that DC — a total loss of that DC with no backup means full rebuild/reprovisioning rather than restore | **Escalate immediately** per Section 6; do not wait for the next cycle |
| Backup history exists, but no version includes System State | Backups are running (e.g., a scheduled full-server or file-level backup) but System State specifically is not included in the backup scope — a configuration gap, not necessarily a total backup failure | **Escalate immediately** — this specifically defeats AD/DC disaster-recovery capability even though other backups may be succeeding |
| A System State backup exists but is older than the `-MaxAgeHours` threshold (default 7 days) | Backups may have stopped succeeding recently, or the schedule/retention configuration has changed | Escalate if this is a new development (last cycle was current); log as a routine finding and monitor closely if there's a known, documented, temporary reason (e.g., a maintenance window that paused backups) |
| Most recent backup version's `Can Recover:` line is present but the job otherwise reported failure/incomplete status in Windows Server Backup's own event log or console | The backup attempt did not complete successfully even though a version entry exists | **Escalate immediately** — treat an incomplete/failed backup the same as a missing one for recovery-planning purposes |

This table reflects general Windows Server Backup semantics for the assumed baseline and is not exhaustive. For a finding not listed here, use organizational backup/DR-support experience to judge urgency.
