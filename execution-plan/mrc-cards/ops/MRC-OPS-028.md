## 4. Safety / Handling Precautions

This is a read-only monitoring task performed entirely by viewing dashboards and status pages in the out-of-band management console. Do not use this review as an opportunity to apply firmware updates, clear a foreign RAID configuration, discard preserved cache, or perform any RAID-level migration during the routine check — those are separate, deliberate maintenance actions with their own change-control and (for firmware) reboot/downtime expectations, and performing them opportunistically during a health check risks an unplanned outage. The one exception is the read-only navigation described in Section 5.1; if a finding requires remediation (e.g. a failed physical disk), open a separate change-managed maintenance action rather than acting on it inside this card's session. Out-of-band management interfaces (iDRAC/iLO) are themselves privileged, network-reachable administrative surfaces — access them only from an authorized management network/jump host per this organization's network segmentation policy, never directly from a general user segment.

## 5. Procedure

This card assumes a hardware management console account (iDRAC or iLO, or the equivalent OEM console) with at least read access to the System/Health and Storage views, and network access to that console from an authorized management segment.

### 5.1 Console path (this task's only supported path — pick the branch matching this server's OEM)

**Dell iDRAC (iDRAC9/iDRAC8):**

1. Log in to the iDRAC web console for the target server.
2. Navigate to the **Dashboard** (System summary landing page). — Expected result: no active health alerts or warnings shown; review the dashboard's health-alert indicators, running jobs, and recent system log entries for anomalies. — Capture: a screenshot of the dashboard health-alert summary. — Stop/continue: any active warning/critical alert is a finding; drill into it via the referenced sub-page before escalating.
3. Navigate to **System → Cooling**. — Expected result: fan status/speeds within normal range and CPU/memory/inlet/exhaust temperatures within their configured warning/critical ranges. — Capture: the thermal summary. — Stop/continue: any sensor outside its normal range is a finding.
4. Navigate to **System → Memory**. — Expected result: every populated DIMM reports a healthy status, with no unexpected empty slots relative to the expected configuration. — Capture: the memory health summary. — Stop/continue: any DIMM in a non-healthy state is a finding.
5. Navigate to **System → Power**. — Expected result: all installed power supplies report healthy status with normal input voltage. — Capture: the power-supply health summary. — Stop/continue: any power supply in a non-healthy or failed state is a finding — this is typically urgent since it reduces (or eliminates) power redundancy.
6. Navigate to **Storage → Summary**, then **Storage → Physical Disks** and **Storage → Virtual Disks**. — Expected result: overall storage health is healthy, every physical disk reports a healthy (not predictive-failed or failed) status, and every virtual disk (RAID array) reports a healthy/optimal state with no rebuild in progress (or, if a rebuild is in progress, that it is progressing normally rather than stalled). — Capture: the storage/physical-disk/virtual-disk health summaries. — Stop/continue: any physical disk in a predictive-failed or failed state, or any virtual disk in a degraded state, is a finding requiring prompt escalation — RAID redundancy may already be reduced.
7. Navigate to **Maintenance → Lifecycle Log** (and optionally the **System Event Log**). — Expected result: no new critical or warning entries since the prior cycle's review. — Capture: any new critical/warning entries, filtered by date range since the last review. — Stop/continue: review any new critical/warning entry against Section 5.2 before closing this cycle.

**HPE iLO:**

1. Log in to the iLO web console for the target server.
2. Navigate to **Information → System Information**, then the **Summary** tab (Health Summary page). — Expected result: no active alerts across monitored subsystems and devices. — Capture: a screenshot of the Health Summary page. — Stop/continue: any subsystem/device flagged as degraded or failed is a finding; drill into the relevant tab before escalating.
3. On the same **System Information** page, review the **Fans**, **Temperatures**, **Memory**, and **Power** tabs. — Expected result: all fans/temperatures within normal range, all memory DIMMs healthy, all power supplies healthy with normal redundancy. — Capture: the relevant tab's status for any subsystem flagged in step 2. — Stop/continue: any subsystem reporting degraded status is a finding.
4. Navigate to **Information → System Information → Storage** tab. — Expected result: the Smart Array/storage controller, logical drives (RAID arrays), and physical drives all report healthy status. — Capture: the Storage tab's summary (use **Expand All** to review every logical/physical drive). — Stop/continue: any logical drive in a degraded state, or physical drive in a predictive-failure or failed state, is a finding requiring prompt escalation.
5. Navigate to **Information → Integrated Management Log** (IML). — Expected result: no new critical or caution entries since the prior cycle's review. — Capture: any new critical/caution entries, filtered by date range since the last review. — Stop/continue: review any new critical/caution entry against Section 5.2 before closing this cycle.

**Either console — out-of-band connectivity confirmation (applies to both):**

6. Independently of the console session itself succeeding (which already confirms basic reachability), confirm the out-of-band controller's own network configuration has not silently reverted to a default/unexpected state: check the configured management IP/VLAN under the console's network settings page (iDRAC: **iDRAC Settings → Network**; iLO: **Administration → Network**) matches what this organization's inventory expects. — Expected result: management IP, VLAN, and DNS settings match the expected/documented configuration. — Capture: a screenshot of the network settings page. — Stop/continue: an unexpected network configuration change is a finding — it may indicate the controller was reset (e.g. after a firmware update or battery/NVRAM issue) and could affect subsequent OOB reachability, including remote KVM/virtual media access during an actual incident.

### 5.2 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| Physical disk predictive-failure or failed status | Drive is degrading or has failed | Open a change-managed hardware replacement action; check whether the affected virtual disk/RAID array has redundancy remaining before treating this as non-urgent |
| Virtual disk (RAID array) degraded state | One or more member physical disks failed or is missing, redundancy reduced or lost | Escalate promptly — a second disk failure on a degraded array can cause data loss depending on RAID level |
| Power supply failed or non-redundant | PSU failure, or a PSU unseated/unplugged | Escalate promptly if this reduces the server below its designed power redundancy |
| Memory DIMM in non-healthy state | DIMM failure or seating issue (often surfaced after correctable ECC errors accumulate) | Schedule a change-managed DIMM reseat/replacement; note the affected DIMM's total capacity impact if it must be removed |
| Console network settings do not match documented configuration | Controller reset (firmware update, NVRAM/battery issue) reverted network settings to defaults, or an undocumented change was made | Reconcile the actual vs. documented configuration before the next incident that would need remote/virtual-media access to this controller |
| Cannot reach the console at all | Management network path down, controller itself unresponsive/hung, or credentials expired | Attempt access from a different point on the management network before assuming the controller itself has failed; a completely unreachable OOB controller on a production server should be treated as a priority finding regardless of the host OS's own apparent health |

This table reflects general practice for Dell iDRAC and HPE iLO consoles and is not exhaustive; consult the specific OEM's documentation for hardware not covered by either.

### 5.3 Future automation note (not implemented this cycle)

If this organization standardizes on a single OEM and firmware baseline, the most promising automation path is the vendor-neutral [DMTF Redfish standard](https://www.dmtf.org/standards/redfish), which both iDRAC (iDRAC9 firmware 3.00.00.0+) and iLO (iLO4 firmware 2.30+, iLO5+) implement as a RESTful HTTPS/JSON API. A PowerShell script using `Invoke-RestMethod` against each vendor's Redfish endpoints (e.g. `/redfish/v1/Systems/{id}` for overall health, `/redfish/v1/Systems/{id}/Storage` for RAID/physical-disk health) could be built, but would still need per-vendor schema handling (Dell and HPE extend the base Redfish schema differently for some storage properties) and should be scoped, tested against this organization's actual hardware generation, and reviewed the same as the PowerShell scripts used elsewhere in this repository before being adopted as this card's automated path.
