## 4. Safety / Handling Precautions

This is a read-only verification task. The companion script (Section 5.1) never starts, stops, restarts, or reconfigures any service — it only calls `Get-Service`, which is query-only. Do not use a finding from this task as justification to restart a stopped service on a production host during the review without first understanding *why* it stopped — some services (e.g. Print Spooler) fail for a benign, self-recovering reason, while others stopping unexpectedly (e.g. a security agent's service) can itself be a security-relevant event warranting investigation before simply restarting it. The default service list in Section 2 is a general baseline — tailor `-ServiceNames` to the actual roles each host serves (e.g. add the DNS Server service on a domain controller, or exclude services for roles a given host does not run) before treating "not found" results as findings.

## 5. Procedure

This card assumes network access to each target host and, for remote targets, an account with WinRM/PSRemoting access already granted (the script uses `Invoke-Command` for any `-ComputerName` other than the local host, since `Get-Service -ComputerName` was removed starting in PowerShell 6).

### 5.1 Automated path (recommended)

1. On a Windows PowerShell host with network/WinRM access to the target server(s), obtain [`execution-plan/mrc-cards/scripts/MRC-OPS-034.ps1`](../scripts/MRC-OPS-034.ps1) from this repository.
2. Run:
   ```powershell
   .\MRC-OPS-034.ps1 -ComputerName dc01.example.mil -ServiceNames RpcSs,EventLog,Netlogon,W32Time,DNS
   ```
   — Expected result: the script checks each named service via `Get-Service`, flagging Fail if a named service is found but not `Running`, and Warning if a named service is not found on that host at all (may indicate an expected role difference, or a missing feature). The default `-ServiceNames` list (`RpcSs, EventLog, Dnscache, LanmanServer, LanmanWorkstation, Netlogon, W32Time, Schedule`) is a general baseline — override it to match the specific roles installed on each target, as shown in the example above for a domain controller (adding `DNS`). **It never starts, stops, or modifies any service.** — Capture: the script writes a timestamped report to `.\reports\MRC-OPS-034_<yyyyMMdd-HHmmss>.txt` by default; use `-OutputPath` to direct it elsewhere. — Stop/continue: if the script cannot reach a remote target (commonly a WinRM/firewall issue or an expired credential), fall back to the manual path in Section 5.2 for this cycle and log the tooling gap as a routine finding.
3. Read the script's console summary line and check `$LASTEXITCODE` (`0` = every named service is found and Running. `1` = any service is stopped, not found, or could not be queried). — Capture: console output. — Stop/continue: if exit code is `1`, proceed to step 4.
4. Open the report file's `SUMMARY` table and locate every row with `Result = Warning` or `Fail`. — Expected result: either a clean cycle (file the report and close) or an identified stopped/missing service needing follow-up. — Capture: the full report filed as this cycle's evidence. — Stop/continue: for any Warning/Fail, proceed to Section 5.3 for triage.

### 5.2 Manual path (fallback / spot-check verification)

1. On the target server, open **Services** (`services.msc`), or run `Get-Service` in a PowerShell session on the host. — Expected result: every service on this organization's tracked list for that host's role shows **Status: Running**. — Capture: a screenshot of the Services console filtered/sorted by Status, or the `Get-Service` output. — Stop/continue: any tracked service showing **Stopped** (or any other non-Running status) is a finding.
2. For any service reporting **Stopped**, check its **Startup Type** column. — Expected result: services this organization expects to run continuously should show **Automatic** (or **Automatic (Delayed Start)**). — Capture: the Startup Type value. — Stop/continue: a critical service set to **Manual** or **Disabled** when it should be Automatic is itself a finding distinct from the immediate stopped-state issue, since it may not restart automatically after the next reboot.
3. Check the **System** event log (`eventvwr.msc → Windows Logs → System`) for Service Control Manager entries around the time the service stopped, if the stop time can be determined. — Expected result: a clear reason for the stop (e.g. a crash, a dependency failure, or a manual/administrative stop). — Capture: the relevant event log entry. — Stop/continue: proceed to Section 5.3 to triage based on the specific service and reason.

### 5.3 Common failure signatures (triage reference, not exhaustive)

| Finding | Typical meaning | Immediate action |
|---|---|---|
| A core service (e.g. RPC, Event Log) is stopped | Often indicates a deeper system problem, since most other services depend on these | Treat as a priority finding — investigate immediately rather than simply restarting, since a stopped RPC or Event Log service can also prevent this script itself from running cleanly on subsequent cycles |
| A role-specific service (e.g. Netlogon on a non-domain-controller) reports "not found" | Expected — that role isn't installed on this host | Confirm the `-ServiceNames` list passed for this host actually matches its intended roles; adjust the list going forward rather than re-flagging the same expected absence every cycle |
| A service is stopped with Startup Type still Automatic | Service crashed or was stopped manually without updating its startup configuration | Investigate the crash/stop reason via the System event log before restarting; if it's a recurring crash, escalate rather than repeatedly restarting the same failure |
| A security-relevant service (e.g. an endpoint protection agent) is unexpectedly stopped | Could indicate tampering, a licensing/update issue, or a legitimate maintenance action | Escalate promptly via the CAT-tier routing in [`ESCALATION-MATRIX.md`](../../templates/ESCALATION-MATRIX.md) rather than treating this the same as a routine operational service stop |

This table reflects general practice for the assumed Windows Server baseline and is not exhaustive.
