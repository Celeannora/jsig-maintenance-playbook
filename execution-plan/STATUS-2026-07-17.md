# Project Status — 2026-07-17

Snapshot of the JSIG Section 1.5 execution-plan build, written at the end of the session that added STIG nested-zip bulk import and CVE mirror tooling. Read this before resuming work — it says exactly what's done, what's tested, and what's next.

## What's done and tested this session

1. **STIG bulk-import now handles nested zips.** `execution-plan/tools/stig_reference_builder.py`'s zip extraction is now recursive (`MAX_ZIP_DEPTH = 6`), so it can ingest either a single official per-product `.zip`, or DISA's quarterly **SRG-STIG Library Compilation** `.zip` ([public.cyber.mil/stigs/compilations](https://public.cyber.mil/stigs/compilations/)) which bundles every current STIG as nested per-product zips inside one outer zip. This is the official "download all STIG IDs in one shot, repeatable" mechanism the user asked about.
   - Tested end-to-end against a synthetic nested compilation zip (outer zip -> two per-product zips -> XCCDF files + a decoy PDF) — both products extracted correctly, decoy ignored.
   - Regression-tested against the real Windows 11 STIG (`stig_intake/U_MS_Windows_11_STIG_V2R8_Manual-xccdf.xml`) in a mixed intake alongside a nested zip — still parses to the same 256 findings, no regression.

2. **CVE mirror tooling added.** `execution-plan/tools/cve_reference_builder.py` gained two new subcommands alongside the existing `fetch`/`fetch-list`/`lookup`:
   - `mirror` — one-shot full bulk download of the entire NVD CVE catalog (367,067 records confirmed live as of this session) via paginated, unfiltered `/cves/2.0` calls (no date-range limit applies without date filters). ~184 pages at 2,000/page; ~20 min unauthenticated, ~2 min with an `NVD_API_KEY`. Prints an exact `--start-index` resume hint on failure.
   - `mirror-update` — repeatable incremental refresh using `lastModStartDate`/`lastModEndDate`, auto-chunked into ≤119-day windows to respect NVD's confirmed-live 120-day date-range limit. Only advances its saved timestamp after every chunk succeeds (fail-closed; safe to blindly re-run on any failure since upserts are idempotent by CVE ID).
   - Both write to a **separate** file (`data/cve_mirror.json`, gitignored) from the small curated `data/cve_reference.json` (built by `fetch`/`fetch-list`, meant to be committed). `save_db` auto-switches to compact JSON above 2,000 records to control file size at full-mirror scale.
   - Tested live end-to-end: `mirror` with tiny page caps (proved pagination + resume-by-`--start-index`), `mirror-update` against a real 2-day recent window (1,237 real records fetched and cached), and the 119-day chunking logic against a synthetic 563-day gap (correctly produced 5 chunks).
   - All test artifacts/output files were written to `/tmp` and cleaned up — nothing test-related was left in the repo.

3. **Docs updated to match:** `execution-plan/tools/README.md` now documents both STIG import options (targeted vs. Library Compilation) and the full CVE tooling section (targeted vs. mirror workflows, sizing/gitignore guidance, CVSS→CAT/KEV-floor cross-reference). Created the previously-missing `execution-plan/tools/cve_intake/` folder with a `.gitkeep` and an example CVE list file. Added `execution-plan/tools/data/cve_mirror.json` to `.gitignore`.

## Key facts worth not re-deriving

- NVD's `/cves/2.0` date-range filter (`lastModStartDate`/`lastModEndDate` or `pubStartDate`/`pubEndDate`) is capped at **120 days per request** — confirmed live (>120 days → HTTP error, ≤120 days → succeeds). No such limit applies to unfiltered pagination.
- NVD total catalog size as of 2026-07-17: **367,067 CVE records**.
- DISA's quarterly Library Compilation zip nests per-product zips one level deep inside the outer zip — confirmed via the official STIG Viewer 3.x user guide and STIG Manager docs; `stig_reference_builder.py`'s recursive extractor (depth cap 6) now handles this and any deeper nesting safely.
- CISA KEV: BOD 22-01 (flat ~14-day remediation) was revoked June 10, 2026 and replaced by BOD 26-04 (4-variable risk model, 3-day-to-deferred windows). The tooling deliberately does not model either directive's day-count logic — it surfaces NVD's own `cisaActionDue`/`cisaRequiredAction` fields verbatim, since the new model needs asset-specific facts (internet exposure, etc.) the tool can't know. See `ESCALATION-MATRIX.md` Section 6.
